# 17.2. Tally & Resolution

**Status:** Not started
**Depends on:** 17.1 (votes and ballots exist), 16.2 (the lifecycle this unfreezes), **D2 (Cloud Functions setup)** · **Blocks:** nothing

> **This ticket is entirely server-side and it is the most error-prone thing in the roadmap.** A wrong tally doesn't crash — it returns a plausible winner nobody questions. Every acceptance criterion below is an emulator test against seeded ballots, not something you check by looking at the app.
>
> **The tally is not a preference, it is forced by the code.** `votingLogic.ts` breaks ties with `Math.random()` in both functions, so two devices tallying identical ballots produce different winners. Client-side tallying is not viable in a multi-user vote, full stop.

---

**1 - User Story**

As a User, I want the group's answer to actually land — the plan updates itself, everyone sees the same result, and nobody has to tally anything or chase the last person — so that deciding together doesn't cost more than the thing we're deciding.

---

**2 - The Architecture & Technical Details**

**Target Database Collections:** `Chats/{chatId}/Votes` (read ballots, write `status` and the result) · `Events` (read candidates, write the winner onto the original, delete losers) · `Users/{uid}/Free_Busy` (indirectly — see below)

**Data model changes:**

- ➕ **`winning_option_id` (String) on `Votes`** — set at close.
- ➕ **`closed_at` (Timestamp) and `close_reason` (String) on `Votes`** — `"majority"` · `"all_voted"` · `"timer"`. The reason is not decoration: when a result looks wrong, the first question is always which path closed it.
- ➕ **`final_counts` (Map) on `Votes`** — `option_id` → count, frozen at close so the closed card renders without recomputing anything.
- **Nothing else.** Every other field is 17.1's.

**Closing — three conditions, whichever comes first:**

| Condition | Rule |
|---|---|
| **Majority** | One option holds more than half of the **invitees** (`shared_with` on the linked event, or the chat's `participants` for a freeform vote). At that point no remaining ballot can change the winner, so closing early is mathematically safe rather than merely convenient. |
| **All voted** | Every invitee has cast a ballot. |
| **Timer** | `resolves_at` passes. Set once at creation to `created_at + 24h` and never moved, including when options are added. |

**Why all three:** the majority path means the group isn't waiting on someone who is never going to answer; the all-voted path means a responsive group gets an instant answer; the timer means a plan can't be held hostage by one person's silence. Same reasoning as 16.2's window, and deliberately the same 24 hours so there is one number in the system rather than two.

**A running result is maintained, not just a final one.** 17.1's card shows live counts to anyone who has already voted, so the counts have to be current between closes.

`[DECISION: what maintains the running counts. Either (a) the client computes them from the ballot maps it is already listening to — free, no writes, but it means tally logic exists on the client again, which is the thing this ticket exists to prevent; or (b) the same Function that evaluates the close conditions writes a running_counts map on every ballot — one Function invocation per vote cast, and one source of truth. (a) is cheap and (b) is honest; the risk of (a) is that a client-side "display" tally drifts from the server's real one and nobody notices until they disagree.]`

**What runs the clock:** the **same scheduled sweep as 16.2**, extended to also query `Votes where status == "open" and resolves_at <= now`. One scheduled Function, two queries, one deploy. Do not add a second scheduler.

**Evaluating the close on every ballot** needs a trigger, and it is the same open question 16.2 carries — see that ticket's bracket. Whatever is chosen there, this uses it. **A trigger that writes to the document it watches must guard on the incoming status, or it re-fires on its own write.**

**The tally — one function, one call site.**

- **Pick-one:** count `normal_votes` values by `option_id`. Highest wins.
- **Ranked: instant-runoff.** Count first choices among still-active options; if one has more than half, it wins; otherwise **eliminate exactly one option — the single lowest — and recount**, transferring each ballot to its highest-ranked surviving option.
  - **The prototype eliminates every option tied for last simultaneously, and that inverts winners.** Concrete case: A=2, B=2, C=3, where A- and B-voters rank each other second. The existing code eliminates A and B together, leaving C. Correct IRV eliminates one, transfers, and B wins with 4 of 7. **Eliminate one at a time. If several are tied for last, the tie-break below picks which one goes.**
- **Tie-break, everywhere it is needed: the earliest option wins.** The option added first — which in an alternative vote is the original plan. Deterministic, explainable in one sentence, and it biases toward the plan that already exists, which is the right default: an alternative that merely ties has not made the case for changing anything.
- **`Math.random()` appears nowhere in this ticket.** That is a grep in the verification list, not a suggestion.

**The IRV hedge, and how to keep it available.** IRV is the intended algorithm. If it proves too expensive to get right, the fallback is a Borda count — points by position, one pass, deterministic. **That only stays a cheap swap if the tally lives behind one function with one call site from day one.** Do not thread ranking logic through the trigger, the sweep, or the card.

`[DECISION: how a stale ranked ballot is tallied — a ballot cast at options_revision 2 when the vote closed at 4. Either treat the options it never saw as ranked last, which is exactly the silent misreading the re-rank prompt exists to prevent, or exclude that ballot from the ranked tally, which throws away a real preference because someone missed a prompt. 17.1 stores the revision either way; this is where it gets interpreted.]`

**Applying the winner — mutate the original, keep the people:**

- The winning candidate's fields are written onto the **original** Event. Anything the alternative did not change stays as it was.
- **`rsvps` is preserved exactly.** Someone who said `going` to mini golf stays `going` when it becomes bowling.
  > **Known and accepted.** The group is told through Project 20's RSVP/plan-change notification, and anyone who no longer wants in changes their answer or the plan gets cancelled by hand. The alternative — resetting the yes votes — would push a confirmed event back below its confirmation bar, which is a backwards transition, and the lifecycle is forward-only everywhere else.
- **The event's own clock restarts when the vote closes.** While a vote was open, 16.2's sweep skipped the event entirely; on close it becomes eligible again. `[DECISION: whether "restarts" means a fresh full window or the remainder of the original one. A fresh window is simpler and gives the changed plan a real chance to be answered; the remainder is stricter and keeps the original promise about when a plan resolves.]`
- **If the winner is the original option, nothing is written to the Event at all** beyond unfreezing it. A vote that confirms the status quo should be a no-op, not a rewrite with identical values.

**Losing candidates are deleted.** The vote keeps its `options` — with `label` and `final_counts` — so the closed card can still show what was on the ballot. The candidate `Events` documents themselves are removed, so nothing accumulates in a collection every planner query touches. **This is why 17.1 requires `label` to be self-describing.**

**`Free_Busy` is not written here.** The event may confirm later on its own clock, and 16.2 owns that write. If the winning option changed the time on an **already-confirmed** event, the blocks 16.2 wrote are now wrong — `[DECISION: whether 17.2 rewrites those blocks, or whether an alternative simply cannot be raised against a confirmed event. The second is already the rule — alternatives only while "proposed" — so this may be unreachable. Confirm it is, rather than assuming it.]`

**Known bugs and patterns to avoid:**

- **Delete `utils/votingLogic.ts`.** Both functions, and the dead `PollOption`/`Vote` types if nothing else uses them. There were four tally implementations across the codebase using three tie policies; this ticket leaves exactly one, server-side.
- **Delete `SocialDashboard.getRankedResults`** (line 45). It is a Borda count living inside a feature named ranked-choice, and it is what actually runs today.
- **The sweep must be idempotent.** Resolve only votes still `"open"`; a retried or overlapping invocation has to be harmless.
- **A close trigger that writes `status` will re-fire on its own write** unless it guards on the incoming value.
- Every timestamp comparison is against a Firestore `Timestamp`.

**3 - The UI and Layout Requirements**

Nothing new is built here. This ticket changes which state existing components are in.

- **Closed vote card:** the winner marked, `final_counts` per option with names, no live buttons, and a line saying how it closed — "Most people picked Friday", "Everyone voted", "Time ran out".
- **A vote that closed on the original option:** says the plan didn't change, rather than showing nothing.
- **The linked event card:** stops saying it is being decided and returns to its normal proposal or confirmed rendering, with whatever the vote changed already applied.
- **Planner:** the ghost or solid event now shows the winning details. Losing candidates were never on the planner.
- **No spinner and no waiting state anywhere.** Resolution happens on a server on a timer; the UI renders what the listener delivers.

**4 - Security and Scope**

**In scope**

- The three close conditions, and `close_reason`.
- The pick-one and IRV tallies, in one function with one call site.
- The earliest-option tie-break.
- Writing `status`, `winning_option_id`, `closed_at`, `close_reason`, and `final_counts`.
- Applying the winner to the original Event and unfreezing it.
- Deleting losing candidate Events.
- Extending 16.2's sweep with the votes query.
- Deleting `votingLogic.ts` and `getRankedResults`.

**Explicitly out of scope**

- Creating votes, casting ballots, adding options, and every piece of the card — **17.1**.
- Notifying anyone that a vote closed or that a plan changed — **Project 20**, hanging off this ticket's write so it isn't built twice.
- Cancelling a vote, unless 17.1's status bracket lands on a cancelled state.
- Any change to the Events lifecycle itself — 16.2 owns it.
- Vote history, past-results browsing, analytics.
- Re-running a closed vote, or reopening one. Closed is terminal, same as the Events lifecycle.

**Files this ticket may modify**

- `functions/` — the close trigger and the extended sweep
- `utils/votingLogic.ts` — **delete**
- `components/SocialDashboard.tsx` — the closed-vote states, and removing `getRankedResults`
- `components/DraggableEvent.tsx` — only if a changed event needs a different render
- `firestore.rules` — the `Votes` update rule only
- `firestore.indexes.json`
- `types.ts` — removing the dead poll types

**Security rules changes**

- **Votes `update` — `status`, `winning_option_id`, `closed_at`, `close_reason`, `final_counts`:** **Admin SDK only. No client allowance at all.** This single rule is what makes every result in the app trustworthy.
- **Votes `update` — ballots:** 17.1's rule already gates on `status == "open"`, so closing locks the ballots with no additional clause.
- **Events `update`:** the winner is applied by the Admin SDK, which bypasses rules. No client allowance is added.
- **Events `delete`:** losing candidates are deleted by the Admin SDK. **Do not add an `allow delete` clause** — 16.1 and 16.2 both say an event is cancelled, never deleted, and that stays true for anything a client can touch.
- **No new read allowances.**

**5 - Acceptance Criteria**

Every one of these is an emulator test against seeded ballots.

- [ ] A pick-one vote where one option holds more than half the **invitees** closes immediately, with `close_reason: "majority"`.
- [ ] A vote where every invitee has voted but no option has a majority closes with `close_reason: "all_voted"`.
- [ ] A vote with two of five invitees voted stays open until `resolves_at`, then closes with `close_reason: "timer"`.
- [ ] Adding an option at hour 23 does not extend the close time.
- [ ] **The IRV inversion case:** ballots A=2, B=2, C=3 with A- and B-voters ranking each other second returns **B**, not C.
- [ ] IRV eliminates exactly one option per round. A test with three options tied for last eliminates one, not three.
- [ ] A tie at any stage resolves to the option added first, and re-running the tally on identical data returns the same winner every time.
- [ ] `grep -rn "Math.random" functions/` returns nothing.
- [ ] The winning candidate's changed fields are applied to the original Event; unchanged fields are untouched.
- [ ] `rsvps` on the original Event is byte-identical before and after the winner is applied.
- [ ] A vote won by the original option writes no field changes to the Event.
- [ ] Losing candidate Events no longer exist; the closed vote card still renders every option's label and count.
- [ ] The linked event becomes eligible for 16.2's sweep again once the vote closes, and was skipped by it while the vote was open.
- [ ] Running the sweep twice over the same closed vote changes nothing.
- [ ] The close trigger does not re-fire on its own write — verified by a log line count.
- [ ] A client cannot write `status`, `winning_option_id`, or `final_counts` — all denied in the Rules Playground.
- [ ] A client cannot delete an Event — denied.
- [ ] `utils/votingLogic.ts` no longer exists, and `getRankedResults` is gone from `SocialDashboard.tsx`.
- [ ] Exactly one tally implementation exists in the codebase — a grep for counting logic finds one function.

**Verification commands**

```
npm run lint
npm test
firebase emulators:start --only firestore,functions
grep -rn "Math.random" .                     # expect zero
grep -rn "votingLogic\|getRankedResults" .   # expect zero
grep -rn "calculatePickOne\|calculateRanked" . # expect one implementation, in functions/
```
