# 4.4. Friends List & Pending Requests

**Status:** Drafted 2026-10-07, all decisions ruled 2026-10-07. Unreviewed as a whole.
**Depends on:** 4.3 (the tab it lives on), `*3.2` (the `Friends` read rule).
**Blocks:** nothing. Project 5 writes the data this reads; until it lands, the only `Friends` documents are ones added by hand in the Console.

---

**1 - User Story**

As a user, I want to see my friends and my incoming friend requests on the same tab where I search for people, so that managing my network happens in one place.

---

**2 - The Architecture & Technical Details**

> **The model, in three lines.** `Users/{uid}/Friends/{friendId}` holds exactly one field, `status`: one of `"request_sent"`, `"pending"`, `"friend"`, `"close_friend"`. The document ID is the other person's uid and there's no name or picture on it (Master Schema Q3), so every row needs a read of that person's `Users` document. Those names are cached for the session, which is what makes sorting by name affordable.

- **Target Database Collections:** `Users/{uid}/Friends` (read), `Users/{friendId}` (read).
- **Data model changes:** None. One local type is added — see below.

**Reads, exactly**

- **Friends list:** `Users/{uid}/Friends` where `status` is `"friend"` or `"close_friend"` — one query.
- **Pending requests:** `Users/{uid}/Friends` where `status == "pending"` — one query.
- **Names:** one read of `Users/{friendId}` per person, **only if that person isn't already in the session cache.**
- One-time reads, not listeners. The app's three listeners are already spoken for (chat list, open thread, events).

**The session name cache**

- **A shared module, `services/userProfileCache.ts`.** 15.2's sender names reuse it later instead of building a second cache.
- Holds each person's `name` and `name_lowercase` after the first read. In memory only.
- Belongs to the signed-in user: when the uid changes (sign out, sign in as someone else), it starts empty.

**Sorting and pagination**

- **Friends list:** close friends first, then everyone else; alphabetical by `name_lowercase` within each group.
- **Pending requests:** alphabetical too. There's no timestamp on a `Friends` document, so newest-first isn't possible.
- Sorting by name means every name has to be known first, so the lists read all names (minus cached ones), sort, then **render in pages of 10 as you scroll** — about a screen's worth plus a few. Pagination here saves rendering, not reads. The cache is what saves reads on later visits.

**Refresh**

- **Every time the Search tab comes into focus:** both queries run again; names come from the cache, and only new people are read. (4.1's navigator unmounts a tab when you leave it, so this happens naturally.)
- **Pull down to refresh:** both queries run again **and** the cache is cleared, so names are re-read too. That's how someone sees a friend's name change.

**Deleted users.** A `Friends` document whose `Users` document doesn't exist renders as "Deleted user" with `InitialsAvatar` given an empty name (its person glyph). It sorts last. Per `CLAUDE.md`, never build a second placeholder.

**`close_friend` is one-sided.** `Users/A/Friends/B == "close_friend"` alongside `Users/B/Friends/A == "friend"` is valid. This list shows **your** copy. Don't build a mutuality check.

**The type.** Add a schema-shaped `FriendDocument` (`status` as the four-value string) to `types.ts`. **Leave the old `Friend` interface alone:** `EventPlanner`, `SocialDashboard`, `CreateEventModal`, `useEventCreation` and `MOCK_FRIENDS` in `constants.ts` all still use it. It goes when those screens move to real data.

**Keep the logic pure.** `services/friendsList.ts` holds the status split, the sort, the badge count and the deleted-user fallback as plain functions — no Firestore, no React — tested first. `services/FriendsService.ts` runs the two queries.

**3 - The UI and Layout Requirements**

Two sections on the Search tab, under the search bar:

1. **Pending Requests** — rows of initials avatar + name, with a red notification badge carrying the count. **Hidden entirely when there are none** — not rendered empty, absent from the screen.
2. **Friends** — rows of initials avatar + name + star. **Filled star for `close_friend`, outline star for `friend`.**

**While a search is showing results, both sections are hidden.** A search works like opening a separate page; clearing it brings them back.

- **Loading:** `<SkeletonCard variant="list-row" />` rows, per section, independently.
- **Empty:** Pending is absent at 0. Friends at 0 shows `<EmptyState />` with a suggested action toward searching.
- **Error:** `<ErrorState />` per section, with retry. One section failing doesn't blank the other.
- **Deleted user:** as above, in both sections.
- **Tapping a row does nothing until Project 7. Tapping the star does nothing until Project 5.** Both are display-only here.

Badge in `danger` with the `micro` type style; star in `primary`. Everything else from `useTheme()`.

- `__tests__/` — new tests for the pure module and the cache.
- `firestore-tests/friends.test.ts` — the query case below.
- `DEVICE_TESTS.md` — a 4.4 section. `CLAUDE.md`, `README.md` — lines this ticket makes stale.

Nothing else. In particular not `components/ProfilePage.tsx` — its mock friends modal stays until D6 — and not `constants.ts`.

**In scope**

- Both sections, read-only, from Firestore.
- The session name cache, the sort, the pagination, the refresh behavior.
- The `FriendDocument` type.

**Explicitly out of scope**

- **Every write.** Accept, decline, unfriend, star and unstar are all Project 5.
- What a row tap opens (Project 7).
- Profile pictures (Project 6).
- The Profile tab's friends modal (D6).
- Sorting by who you interact with most — maybe later, not now.
- Blocking, mutual-friend counts.

**Security rules changes: No changes needed.**

`firestore.rules` has `allow read: if signedIn();` on `Users/{userId}/Friends/{friendId}` and on `Users/{userId}`, so both queries and the name reads are allowed. This ticket writes nothing, so it adds no client-side friend-acceptance path — the condition `*3.4` checks for. Adds one rules test: a signed-in user can query their own `Friends` by `status`.

**Stop and ask** if: a row needs any field on a `Friends` document other than `status` (there are none); something seems to need writing a name onto `Friends` (Q3, closed); or a fix needs a file outside the list.

**5 - Acceptance Criteria**

Verified by `npm test` and `npm run test:rules`, plus **one device against test accounts whose `Friends` documents are added by hand in the Console.**

**Tests are written before the implementation.**

- Four fixture `Friends` documents, one per status, give exactly one Pending row and exactly two Friends rows.
- In the Friends list, close friends come first, then alphabetical by name, ignoring capitalization. Pending is alphabetical.
- Only the `close_friend` row gets a filled star.
- A `Friends` document with no matching `Users` document becomes "Deleted user" and sorts last, without throwing.
- `status` is compared as a string; no boolean anywhere.
- A second load of the same person makes no new `Users` read; after the cache is cleared, it does.
- The cache starts empty when the signed-in uid changes.
- Rules: a signed-in user's query of their own `Friends` by `status` is allowed.
- On the device: zero pending requests, and the Pending section isn't on screen at all.
- On the device: three pending requests, and the badge reads "3".
- On the device: the Friends list shows close friends first, then the rest alphabetically, with the right stars.
- On the device: with more than 10 friends, more rows load on scroll.
- On the device: change a test friend's `status` in the Console, leave the tab and come back, and the list reflects it.
- On the device: change a test friend's `name` in the Console, pull down, and the new name shows.
- On the device: tapping a row or a star does nothing; the Profile tab is unchanged. While a search is showing results, neither section is on screen.
- `grep -rn "isCloseFriend\|MOCK_FRIENDS\|isDarkMode" components/FriendsList.tsx components/PendingRequests.tsx services/FriendsService.ts services/friendsList.ts services/userProfileCache.ts` returns no results.
- `npm test` and `npm run test:rules` pass. `npm run lint` reports no errors in the touched files.
