# 15.2. Messaging & Real-Time Listeners

**Status:** Not started
**Depends on:** 0.1 (boot path), 1 (auth), 15.1 (chat creation), **D2 (Cloud Functions setup)** · **Blocks:** 16, 17, 20

> **Note on the Running Order:** this ticket is listed there as "genuinely blocked by J1." That's stale. J1 resolved to `react-native-firebase`, so offline persistence and listener reconnection come from the native SDK and nothing here has to be hand-built. What did change is that D2 is now a **hard** dependency — see the send path in Section 2.

---

**1 - User Story**

As a User, I want to send and receive messages in my Knect chats in real time, so that coordinating a hangout stays continuous and never *requires* leaving Knect to do it. The point isn't to relocate the group text — it's to minimize the coordination itself, because the plan, the people, and the activity are already here.

**2 - The Architecture & Technical Details**

**Target Database Collections:** `Chats/{chatId}/Messages` (read and write) · `Chats` (read for the list; the preview fields are written by a Cloud Function, never by the client) · `Users/{uid}` (read, for live sender name and picture) · `Users/{uid}/Private_info/main` (read, own document only, for `blocked_users`)

**Data model changes:**

- **`message_type` is enumerated exactly, and this is the one place it gets defined.** Five values, snake_case: `"text"` · `"system"` · `"activity"` · `"event_proposal"` · `"vote"`. The prototype's kebab-case (`event-proposal`) is dropped — nothing else in the schema uses it. **15.2 writes only `"text"`.** `"activity"` and `"event_proposal"` are 16's; `"vote"` is 17's; `"system"` is reserved and nothing writes it yet (see Section 4). This closes Master Schema Q5 for `message_type` — 17 still owns `vote_type`, `change_type`, and Vote `status`.
- ➕ **`deleted_at` (Timestamp) on Messages** — set on a tombstone, absent on a normal message. See "Deleting" below.
- ➕ **`recent_message_sender_id` (String) on `Chats`** — written by the preview Function alongside the other two preview fields. **Two things need it and neither works without it.** The block filter has to know who wrote the preview before it can decide whether to hide it. And 15.1's group-chat subtitle (`Jordan: sounds good`) has no field to source that name from today — the `Chats` document stores the message text and nothing about who sent it. Without this field both features need a read of the last message per chat row, which is a read per row on every chat-list render.
- **No `unread_counts` on `Chats`, and no read state on `Messages`.** Unread is device-local. See "Unread state."
- `sender_name` and `sender_profile_pic_url` are already removed from the schema (Q3, resolved 8/30). Do not reintroduce them.
- Nothing else changes.

**Firebase configuration — this settles Project 0 §3 and §9's open decision:**

**Offline persistence is ON, at the SDK's default cache size, set explicitly in one Firestore config module.** The native SDKs likely default to this already; setting it by hand means it reads as a decision rather than a default nobody chose, and it gives the next person one file to look at. Everything below assumes persistence is on — the optimistic send in particular depends on it.

**Listeners — two, and never more:**

1. **Chat list.** `Chats where participants array-contains uid orderBy recent_message_timestamp desc`. Live.
2. **Open thread.** `Chats/{chatId}/Messages orderBy timestamp desc limit 25`. Live, newest page only.

Only one thread listener exists at a time; opening a second chat tears the first one down.

**Teardown is part of the ticket, not an implementation detail.** Both unsubscribe on unmount and on app background, and resubscribe on foreground. An `onSnapshot` nobody unsubscribed is the most common leak in this kind of code, and it keeps billing reads while the app is closed. There is not one `onSnapshot` in the repo today, so there is no existing pattern to copy — this ticket establishes it.

**Pagination:**

- 25 messages on open, live.
- Scrolling back fetches 25 more with a one-time `get()`, using the oldest loaded document as a `startAfter` cursor. Those are appended below the live window as static data.
- The thread listener's `limit` stays at 25 forever. It does not grow as you page back. (The alternative — re-subscribing with a bigger limit each time — re-delivers everything already loaded on every page, so read cost grows roughly quadratically. Fine at 50 messages, painful at 800.)
- **Consequence, stated so nobody treats it as a bug:** two data paths live in one screen. A tombstone applied to a message older than the newest 25 won't appear until the thread is reopened.

**Sending:**

- The client writes the message document. **It does not touch the parent chat document at all.**
- A Cloud Function on `Chats/{chatId}/Messages/{messageId}` writes `recent_message`, `recent_message_timestamp`, and `recent_message_sender_id` on the parent. **It fires on create *and* on update** — see "Deleting" below for why the update half matters. Push notifications (Project 20) hang off the create half of the same trigger, so it isn't built twice.
- **The UI is optimistic.** The bubble renders as sent the moment the user hits send — no clock, no "sending" state, nothing distinguishing it from a confirmed message. With persistence on, the write lands in the local cache immediately and the thread listener fires from cache, so this is close to what's actually happening rather than a lie.
- **Known consequence, accepted:** the sender's own chat-list row lags their message by the Function's round trip — a second or more, longer on a cold start. The thread is the screen they're looking at, and everyone already expects a beat between hitting send and it being *sent*.
- **Failure:** if the write is permanently rejected (rules denial, malformed document), the bubble flips to a failed treatment — tap to retry, long-press to discard. **Notifying a user about a failure they've already navigated away from is Project 20's job, not this ticket's.** Do not build a notification path here.

**Message content:**

- Text only. No images, no attachments.
- **2,000 character cap, enforced in the security rule as well as in the input field.** Enforcing it only in the UI means it isn't enforced — anyone hitting the API directly can write a document big enough to bloat the listener payload and the offline cache for every participant.

**Deleting — tombstone, not removal:**

- Sender-only. Sets `text` to `""` and `deleted_at` to the server timestamp. **The document is not removed.**
- Renders "Message deleted" in place, so the thread's continuity and the consecutive-sender grouping don't break around a hole.
- This is an `update`, not a `delete` — there is no `allow delete` on Messages, and there shouldn't be.
- **The preview Function fires on update too, so tombstoning the most recent message clears the preview.** Create-only would be cheaper, but it would leave the chat list displaying the exact text the user just deleted — that reads as a privacy failure, not as lag. The extra invocation per tombstone is worth it. A tombstoned latest message leaves the preview empty until the next message is sent; do not backfill it with the message before it (that means a query, on every delete, to fix something nobody is looking at).

**Sender identity resolution:**

- Nothing is denormalized onto the message. Resolve `name` and `profile_picture_url` from `Users/{sender_id}`.
- **Dedupe by sender and cache for the session in one shared module.** A 200-message thread from 5 people costs 5 user reads, not 200.
- **"Deleted user" fallback is required, not optional.** A message whose sender's Users document no longer exists renders "Deleted user" plus a placeholder avatar. This is a standing decision across every screen that shows a person; here it's load-bearing, because old messages outlive accounts.

**Unread state — device-local:**

- Store a last-read timestamp per chat on the device (AsyncStorage), written when a thread is opened and refreshed while it stays open.
- The chat list shows an unread dot when the chat's `recent_message_timestamp` is newer than the stored last-read. A dot, not a count.
- No schema field and no shared-document writes. (An `unread_counts` map means every participant writes the same document on every message, which walks straight into Firestore's ~1 write/sec per-document ceiling in an active group chat.)
- **Known limits, stated so nobody files them as bugs:** it does not sync across devices, and reinstalling clears it. Acceptable for a single-device iOS MVP.

**Blocking — the receive side is the part that matters:**

- **You do not see messages from anyone in your own `blocked_users`.** Filter on `sender_id` at render time, in three places: the thread, the conversation-list preview, and the unread dot. Because the filter is per-sender it covers group chats too, not only 1-on-1s.
- **This is client-side, and that's fine here.** Unlike a send-side gate, the only person who can bypass a receive-side filter is the person it protects. It's how iMessage behaves, and it's what Apple's Guideline 1.2 ("the ability to block abusive users from the service") is actually checking for.
- **The send-side gate stays too:** if you've blocked the other participant in a 1-on-1, your input bar is disabled with a line of copy. That one is a courtesy rather than a protection — `blocked_users` is owner-only, so a client can only ever see the blocks *it* made, never the ones made against it.
- **What none of this does is stop the write.** A blocked user's messages are still created, still stored, and still delivered to your device before being filtered out. Real denial needs a rule backed by a readable block record, and **Project 3 owns it** as part of the rules realignment. Do not describe blocking as enforced anywhere until that lands.
- **Assumed here, implemented elsewhere: blocking removes the friendship.** Ruled 8/30; it belongs to Project 5, and 15.2 does not touch `Friends`. One consequence worth knowing rather than discovering: if the pair later unblock and re-friend, 15.1's find-or-create returns the *same* chat with its full history intact. That's the right behavior, but it should be a decision and not a surprise.
- **Not this ticket, and currently unowned:** Guideline 1.2 also requires "a mechanism to report offensive content and timely responses to concerns." Nothing in the roadmap owns that. It's a launch blocker and it needs its own ticket.

**Known bugs and patterns to avoid:**

- **`services/ChatService.ts` gets deleted, not extended.** It's a local-blob-store API with no concept of a listener or a pagination cursor. Replace it with a Firestore repository module; move every call site in `SocialDashboard.tsx` over.
- Project 0.1 converts that same file to proper async against AsyncStorage, and 15.2 throws it away. That's accepted, not an oversight — 0.1 is what stops the Circle tab red-screening so anything is testable in the meantime, and it forces the call sites async, which they have to be either way.
- `utils/storage.ts` named an async API `localStorage`, which is the root cause of most of the current crashes. 0.1 renames it. **Do not reintroduce the pattern** — every Firestore call in here is async by default.
- `SocialDashboard.tsx:865` is a comment where a vote write should be (`// In real app: ChatService.sendVote(...)`). Leave it. That's Project 17.
- `types.ts` currently puts RSVPs on a chat message (`Message.eventDetails.rsvps`). The schema moved them to `Events.rsvps`. **Do not carry the message-embedded shape forward** when reshaping `Message`. That's Project 16.
- **Do not rewrite the chat UI.** The inverted FlatList, consecutive-sender bubble grouping, group avatars, and input bar are finished and keepable. This is a data-layer ticket with a small number of UI additions.

**3 - The UI and Layout Requirements**

- **Loading state:** the grey skeleton pattern that 15.1 made the app-wide standard, shaped for a thread — placeholder bubble blocks alternating left and right.
- **Empty state:** a chat with no messages yet (which every freshly created chat is). "No messages yet. Say hi." centered, gray. This is *not* the conversation-list empty state — 15.1 owns that one.
- **Error state:** the shared component from Appendix B (circle with `!`), copy "Sorry, we couldn't load anything right now." Per Project 0 §9 — do not write new copy for this.
- **Success state (mostly already built — reuse it):** inverted FlatList, consecutive-sender grouping, sender name shown once per run in group chats and never in 1-on-1s, avatars resolved live from the Users document.
- **Sent state:** renders immediately and looks identical to a confirmed message. That's deliberate.
- **Failed state:** red-tinted bubble with "Tap to retry" beneath it. Long-press to discard.
- **Deleted state:** "Message deleted" in italic gray, in place. No gap, no avatar change.
- **Blocked state:** input bar disabled, with a line above it — "You've blocked this person. Unblock them to send a message."
- **Unread indicator:** a dot on the conversation-list row. No count.
- **Character cap:** the input stops accepting at 2,000 characters, and a remaining-character count appears only under 100 left.
- **Removed:** the search affordance comes out of both the conversation list and the thread. Firestore has no substring search, so any version of it would either silently miss everything past your scroll position or need a search service we haven't picked. A zero-result users trust is worse than no search box.

**4 - Security and Scope**

**In scope**

- Reading and writing `Chats/{chatId}/Messages` against Firestore.
- The two listeners, with explicit teardown on unmount and on background.
- 25-message pagination with a `startAfter` cursor; static tail below a fixed live window.
- Optimistic send, and the failed-message state.
- The Cloud Function that writes `recent_message` and `recent_message_timestamp`, firing on both create and update.
- Tombstone delete.
- Live sender name/picture resolution, deduped and session-cached, with the "Deleted user" fallback.
- Device-local unread state.
- The receive-side block filter (thread, conversation-list preview, unread dot), and the send-side input gate on 1-on-1 chats.
- The Firestore persistence config module.
- Deleting `services/ChatService.ts` and replacing it with a repository module.
- Removing the chat search affordance.

**Explicitly out of scope**

- **System messages.** `"system"` is in the enum and nothing writes it. Rename and leave (15.1) stay silent for now.
- **Rendering `"activity"`, `"event_proposal"`, or `"vote"` messages.** The enum values are defined here; 16 and 17 write and render them.
- Typing indicators and read receipts. Both need per-keystroke or per-view writes to a shared document, which is exactly the contention pattern the schema warns about.
- Images, attachments, reactions, replies, and editing a sent message.
- Push notifications, and any notification of a send failure — Project 20.
- Manual chat creation, and add/remove member — 15.1.
- Rules-level enforcement of blocking, and the full `Chats` update-rule tightening — Project 3.
- Removing the friendship when someone is blocked — Project 5.
- Any content reporting or flagging mechanism — currently unowned, see Section 2.
- In-thread message search.

**Files this ticket may modify — anything not on this list is out of scope by default**

- `services/ChatService.ts` — **delete**
- New: a message repository module (e.g. `services/messageRepository.ts`)
- New: a Firestore config module (e.g. `services/firestore.ts`) for the persistence setting
- `components/SocialDashboard.tsx`
- `types.ts` — the `Message` shape only
- `functions/` — the `onCreate` trigger (the project itself is created by D2)
- `firestore.rules` — the `Messages` match block only
- `firestore.indexes.json` — if the chat-list query needs a composite index

Specifically **do not** touch `EventPlanner.tsx`, `CreateEventModal.tsx`, `votingLogic.ts`, `ChatEventWidget.tsx`, or anything in the auth path.

**Security rules changes — required before any code is written**

- **Messages `read`:** requester's UID must be in the parent chat's `participants`, via a `get()` on `Chats/{chatId}`. **Keep the parent `get()`** rather than denormalizing `participants` onto every message — membership stays in exactly one place, so leaving a chat cuts off message reads immediately, and a copied array would go stale the moment anyone left. *[Likely] Firestore caches identical `get()` calls within a single rule evaluation, so a 25-message page costs roughly one extra read, not 25. The Change List's "a billed read per rule evaluation" overstates it. **Verify this in the emulator before anyone repeats it as fact.***
- **Messages `create`:** requester must be a participant, `request.resource.data.sender_id == request.auth.uid`, `text.size() <= 2000`, and `message_type == "text"` — 15.2 writes nothing else, so the rule should permit nothing else. 16 and 17 widen it when they need to.
- **Messages `update`:** sender only, and only the tombstone shape — `diff().affectedKeys().hasOnly(['text', 'deleted_at'])` with `text` set to `""`.
- **Messages `delete`:** none. No `allow delete` clause at all.
- **`Chats` preview fields:** written by the Function through the Admin SDK, which bypasses rules, so no client-side allowance is needed. **Worth confirming rather than assuming** — if any preview write ends up staying client-side, the rule has to permit those two fields and only those two.

**Security exposure carried forward, not resolved here**

- The current `Chats` update rule lets any participant modify any field on the chat document, including `recent_message`. 15.1 flagged it and **Project 3 owns the fix.** It is not resolved by this ticket, and nothing should describe it as resolved — a participant can still overwrite the preview with anything.
- Blocking is enforced entirely on the client in this ticket (Section 2). The receive-side filter is sound in the sense that only the protected user could defeat it, but the blocked user's messages are still written and still stored. Nobody should read this as an access control until Project 3 lands the rule.

**5 - Acceptance Criteria**

- [ ] Sending a message from device A makes it appear on device B without either app being reopened.
- [ ] A sent message renders in the sender's own thread immediately, with no intermediate "sending" treatment.
- [ ] With the network off, three messages can be sent; restoring the network delivers all three, in order, with no user action.
- [ ] `recent_message` and `recent_message_timestamp` are written by the Cloud Function. A grep finds no client-side write to either field.
- [ ] Opening a thread loads exactly 25 messages. Scrolling to the top loads 25 more.
- [ ] The thread listener's `limit` is 25 and does not change as you page back.
- [ ] Navigating away from a chat calls the unsubscribe — verified by a log line, not by reading the code.
- [ ] Backgrounding the app tears down both listeners; foregrounding restores them and the thread is current.
- [ ] A thread with 100 messages from 4 senders issues 4 `Users` reads, not 100.
- [ ] A message whose sender's `Users` document does not exist renders "Deleted user" and a placeholder avatar — not a blank, not a crash.
- [ ] Deleting your own message shows "Message deleted" to every participant, and the document still exists with `deleted_at` set.
- [ ] Deleting the most recent message in a chat clears that chat's preview in the conversation list — the deleted text does not remain visible there.
- [ ] A user cannot tombstone another user's message — denied by rules, verified in the Rules Playground.
- [ ] A 2,001-character message is rejected by the security rule, not only by the input field.
- [ ] A non-participant cannot read any message in a chat — Rules Playground deny case.
- [ ] A message with `sender_id` set to someone else's UID is rejected on create.
- [ ] A chat whose `recent_message_timestamp` is newer than the device's stored last-read shows an unread dot; opening the chat clears it.
- [ ] Blocking a user hides every message they have sent, in every chat shared with them, group chats included.
- [ ] Blocking a user whose message is the newest in a chat removes that text from the conversation-list preview and clears that chat's unread dot.
- [ ] Blocking the other user in a 1-on-1 chat disables your input bar; the rest of the thread's history stays visible.
- [ ] `recent_message_sender_id` is written by the Function and by nothing else — a grep finds no client write.
- [ ] `services/ChatService.ts` no longer exists and nothing imports it.
- [ ] Every `onSnapshot` in the codebase has a corresponding unsubscribe.
- [ ] Firestore persistence is enabled by an explicit call in the config module, not inherited from a default.
- [ ] No search affordance remains in the conversation list or in a thread.
- [ ] `message_type` is defined as a union in exactly one place, with the five values, and only `"text"` is ever written.
