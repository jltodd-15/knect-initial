**1 - User Story**

As a user, I want a Search tab where I can look people up by name, so that I can find the people I know on Knect.

---

**2 - The Architecture & Technical Details**

> **The model, in three lines.** `Users/{uid}.name_lowercase` is a stored field, written with `.toLowerCase()` at signup by `*2.2` (`services/UsersRepository.ts:27`). Firestore has no case-insensitive search, so this is a range query against that stored field, never a lowercase done at query time. Every `Users` document is readable by any signed-in user, which is why nothing private lives on it.

- **Target Database Collection:** `Users` (read only).
- **Data model changes:** None. The schema-shaped `UserDocument` type already exists in `types.ts` (from `*2.2`) — use it, don't add another.

**The query, exactly**

- Lowercase what the user typed to get `q`.
- `Users` where `name_lowercase >= q` and `name_lowercase < q + ''`, limit 10. `''` is a very high Unicode character, so the range covers every name that starts with `q`.
- No read until 3 characters are typed. 300ms debounce on the input. Both save database reads.
- The signed-in user is filtered out **after** the read, on the phone. Firestore can't combine `!=` with a range on the same field, so a search can show 9 of the 10 it fetched. That's correct, not a bug.
- **Only the latest search's results render.** If an older, slower response comes back after a newer one, it's dropped.
- Firestore is `db` from `services/firestore.ts`. Import it from there and nowhere else.

**This is prefix-only, on purpose for MVP.** "smith" does not find "John Smith" — the match starts at the beginning of the stored name. Substring search needs a search service (Algolia, Typesense). Worth watching once real users are searching; if people keep looking for friends by last name, that's the signal to revisit.

**Keep the logic pure.** `services/userSearch.ts` holds the bounds builder, the 3-character gate, the debounce, the self-filter and the latest-wins check as plain functions — no Firestore import, no React. `services/UserSearchService.ts` is the thin Firestore wrapper that uses them. The part that can be wrong without looking wrong gets tested on its own first.

**Offline isn't supported, on purpose.** Knect is a social app and doesn't need to work without a connection. With persistence on, an offline search answers from the phone's cache — usually empty — and shows the no-matches state. That's accepted; don't build offline handling.

**3 - The UI and Layout Requirements**

Top to bottom, on the Search tab from 4.1:

1. **Banner** — "Search", the `display` type style, matching the other tab headers.
2. **Search bar** — placeholder "Search for friends..." that disappears when the bar is selected.
3. **Results** — one row per person: `InitialsAvatar` and their name. **Tapping a row does nothing until Project 7.**

- **Fewer than 3 characters:** no results area at all. That's not an empty state.
- **Loading:** `<SkeletonCard variant="list-row" />` rows.
- **No matches:** `<EmptyState />` with the copy "No one found".
- **Error:** `<ErrorState />` with retry.
- **Success:** the rows, at most 10.

All colors and type come from `useTheme()`.

**4 - Security and Scope**

**Files this ticket may modify**

- `components/SearchTab.tsx` — filling in 4.1's placeholder.
- `services/userSearch.ts` — **new.** Pure functions only.
- `services/UserSearchService.ts` — **new.** The Firestore wrapper.
- `__tests__/userSearch.test.ts` — **new.**
- `firestore-tests/users.test.ts` — the two query cases below.
- `DEVICE_TESTS.md` — a 4.3 section. `CLAUDE.md`, `README.md` — lines this ticket makes stale.

Nothing else. Not `types.ts`, not `ProfilePage.tsx`, nothing under `android/` or `ios/`.

**In scope**

- The search bar, the query and its cost controls, the self-filter, the result rows and their states.

**Explicitly out of scope**

- Substring or last-name search. Prefix-only is the MVP decision above.
- Search by email or username.
- Anything beyond initials and name on a row: no picture (Project 6), no bio, no friend-status marker.
- What a tap does (Project 7).
- Every friend-request write (Project 5).
- The friends list and pending requests (4.4).
- Offline handling.

**Security rules changes: No changes needed.**

`firestore.rules` has `allow read: if signedIn();` on `Users/{userId}`. One `read` clause covers both reading a single document and querying the collection, so this search is already allowed. The consequence worth repeating: **every field on a `Users` document is readable by any signed-in user**, which is why `email`, `location` and `geohash` live in `Private_info`.

The rules tests have never covered a query, only single-document reads, so this ticket adds two: a signed-in user can run this range query on `Users`, and a signed-out user can't.

**Stop and ask** if: the query is denied (that's a rules regression, not a query bug); some `Users` documents have no `name_lowercase` (that's a `*2.2` backfill, never something to compute on the phone); or a fix needs a file outside the list.

**5 - Acceptance Criteria**

Verified by `npm test` and `npm run test:rules`, plus **one device with two test accounts**.

**Tests are written before the implementation.** Each of the first seven criteria is a test in `__tests__/userSearch.test.ts` that exists and fails before `services/userSearch.ts` does.

- 2 characters produce no query.
- 3 characters produce exactly one query.
- Five keystrokes inside 300ms produce one query, not five.
- "KYS" and "kys" produce identical query bounds.
- The upper bound is the lowercased input plus `''`.
- A result set containing the signed-in user's uid comes back one shorter, without them.
- A response for an older search that arrives after a newer one is ignored.
- Rules: a signed-in user's range query on `Users` is allowed; a signed-out user's is denied.
- On the device: searching a name prefix finds the other test account no matter how its name is capitalized.
- On the device: never more than 10 rows.
- On the device: 3+ characters with no match shows "No one found", not `<ErrorState />`.
- On the device: tapping a row does nothing.
- `grep -rn "localStorage\|isDarkMode" components/SearchTab.tsx services/userSearch.ts services/UserSearchService.ts` returns no results.
- `grep -rnE "#[0-9a-fA-F]{3,8}\b" components/SearchTab.tsx` returns no results.
- `npm test` and `npm run test:rules` pass. `npm run lint` reports no errors in the touched files.
