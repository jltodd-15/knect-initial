# 2.3. Signup Write States & Missing-Profile Detection

**Status:** Not started. Drafted 2026-09-07.
**Depends on:** `*2.2`
**Blocks:** 1.4

---

**1 - User Story**

As a new user, I want the app to tell me what it's doing while my account is being created and to recover honestly when it fails, so I never end up with a login that works and a profile that doesn't exist.

---

**2 - The Architecture & Technical Details**

> **The model, in three lines.** Two documents get written by `*2.2`, and the user has to be held still until both land. If they don't, the account exists in Auth with no profile behind it — a state that is reachable, invisible, and permanent unless something looks for it. This ticket is the waiting, the failure path, and the one read on app open that catches the users who fell through anyway.

- **Target Database Collection:** `Users` — **read only.** This ticket writes nothing.
- **Data model changes:** None.

### The transition

`handleProfileComplete` (`App.tsx:60–64`) currently calls the native write and flips state synchronously in the next two lines — it does not await anything, so the user reaches the tab tree whether or not a write succeeded. By the time this ticket starts, 1.2 has made that function receive the payload and await the auth call, and `*2.2` has added the repository call. **This ticket makes the transition wait on that call and reflect it.**

- The submit button disables and shows a submitting label for the duration of the real call. No timer.
- **Double-submit is impossible while the write is in flight.** The button at `CreateProfilePage.tsx:205–207` is disabled today only by `!name || !role`, so a second tap during the write is currently free.
- The user reaches the tab tree **only after both documents are confirmed written.** Land them wherever `App.tsx:18` already defaults (`AppTab.PLANNER`) — **do not build routing.** The five-tab decision and the React Navigation migration are real and belong to other tickets; `types.ts:136–141` still has four tabs and the switch at `App.tsx:162–185` is hand-rolled. Leave all of it.

### What can actually fail here — and what can't

**This is not a validation failure path.** Nothing the user could type differently makes the write succeed, so retrying is the only sensible offer. The three things that can actually fail:

1. **No connectivity, or a connection that drops mid-write.** The most likely one by far.
2. **A permission denial from the security rules.** Shouldn't happen — the published rules already permit both writes (see `*2.2`) — but a rules deploy could change that, and it fails as a rejected promise, not as a hang.
3. **A Firestore-side error** — quota, an internal failure, a malformed batch.

**Field validation is not this ticket's, and it happens before the write.** The submit button at `CreateProfilePage.tsx:205–207` is already gated on `!name || !role`, and **1.4 owns the full validation rules** for that screen, including the password rule and the interests picker. This ticket assumes the payload is complete by the time the button is tappable. If a required field can reach the write empty, that is a 1.4 bug, not a retry case — **do not add field validation here.**

> ⚠️ **[Likely] Offline does not fail — it hangs, and that is the state most likely to be built wrong.** With persistence on (2.1), the native SDK writes a batch into the local cache immediately, but `commit()` only resolves once the server acknowledges it. On a device with no connection the promise **stays pending indefinitely** — it does not reject. So a signup attempted offline would sit in the submitting state forever unless something bounds it. Verify this behavior on a device before building around it; if it holds, the submitting state needs a timeout that falls into the retry treatment below, and the timeout is what turns "offline" into a failure the user can see.

### The failure path

**Retry twice, then sign the user out** (Round 10 §11).

**The retry is manual and it reuses the submit button.** On a failed profile write the button gains a **red outline** and **red "Try Again" text** renders with it. Nothing the user typed is cleared and nothing is re-entered — they tap the same button and the write runs again. There is no automatic retry, no toast, no modal, and no separate retry control.

**Two attempts total.** The initial submit is the first; "Try Again" is the second. If the second fails, the user is signed out. Two is enough to clear a dropped connection and short enough that a genuinely broken state doesn't leave someone tapping a red button.

Two things follow from reusing the button rather than adding one. It leaves its disabled/submitting treatment and becomes tappable again, and every tap runs the same guarded write — so the double-submit rule above applies to each attempt, not just the first.

**There is no sign-out copy. After the second failure the user is simply returned to the login screen.** No message, no interstitial, no explanation of why.

That reads harsh written down, and it is deliberate. The recovery this ticket is built around is the one the user reaches for anyway: they land on the login screen, and the natural instinct is to try again. Either path works.

- **They try to sign up again** → `auth/email-already-in-use`, which 1.2 already handles. That message tells them the account exists, so they sign in.
- **They sign in** → it succeeds, because the Auth account was created before the profile write failed. `onAuthStateChanged` fires, the `Users/{uid}` read below comes back empty, and the missing-profile state puts them back into the profile step with their credentials already good.

**That loop is the whole reason detection exists**, and it is why a message at sign-out would be doing less work than it looks — by the time it mattered the user has already moved, and the state they land in explains itself better than a toast would.

⚠️ **One dependency this creates.** 1.2's `email-already-in-use` copy is now load-bearing for this recovery — it is the only thing telling a bounced user to sign in rather than assume the signup never happened. That string is inside 1.2's open error-copy bracket. **Worth answering it with this path in mind.**

**Accepted cost, recorded so it isn't a surprise:** a user who gives up at the login screen without trying either path is stranded with an account they don't know exists. Judged acceptable because the failure needs two consecutive write failures to reach at all.

### ⚠️ Signing out does not free the email — this is why detection exists

After a failed profile write the **Auth account survives the sign-out.** Signing up again with that address fails with `auth/email-already-in-use`, and signing *in* succeeds and lands an authenticated user with **no `Users` document**. Without something looking for that state, the account is permanently stuck and the "sign out" recovery is a trap rather than a fix.

**Detection, and where the line sits.** Round 10 §11 split this deliberately: **Project 2 owns detection, 1.4 owns the routing into onboarding.**

- Once 1.2's `onAuthStateChanged` subscription reports a signed-in user, read `Users/{uid}` once.
- Document present → normal app.
- Document absent → the app is in the missing-profile state, and that state is what this ticket produces.
- **One read per app open**, on a document the app will want anyway. Do not add a listener — this is a `get()`, not an `onSnapshot`.

**Interim behavior, one line, and 1.4 replaces it.** Until 1.4's sequence exists, a user in the missing-profile state renders the existing `CreateProfilePage` (already wired at `App.tsx:84–91`) instead of the tab tree. That is the whole of it — **do not build an onboarding sequence, a recovery screen, or any routing beyond that single branch.** 1.4 owns what actually happens there.

### Known bug in this exact path

**`App.tsx:44` writes `knect_session` and nothing ever reads it.** 1.2 deletes that write. If it is still present when this ticket starts, do not build the missing-profile check on top of it — the source of truth for signed-in is `onAuthStateChanged`, and the source of truth for profile-exists is the Firestore read above. A third stored flag is a third thing that can disagree with the other two.

**3 - The UI and Layout Requirements**

- **Idle.** The create-account form as it renders today.
- **Submitting.** Button disabled, label swapped to a creating/loading treatment, form inputs locked. Driven by the real call's duration.
- **Write failed, retry available.** The submit button gets a **red outline**, **red "Try Again" text** renders with it, and nothing the user typed is cleared. Tapping the same button retries the write. This is the whole treatment — no toast, no modal, no separate retry control.
- **Retry exhausted.** After the second failed attempt the user is signed out and the login screen renders. **No message, no interstitial** — see the failure path above for why, and do not add one.
- **Success.** The tab tree renders on `AppTab.PLANNER`.
- **Missing profile on sign-in.** The interim branch above — `CreateProfilePage` rather than the tab tree. No new screen, no new copy.
- **Checking.** There is a moment on cold start after `onAuthStateChanged` reports and before the `Users` read resolves. Neither the tab tree nor the login screen is right during it — this is the same class of state 1.2 calls *Restoring*, and it is the one most likely to be skipped. Flashing the signup screen at a user who has a perfectly good profile is the bug this state prevents.

**4 - Security and Scope**

**In scope**

- The submitting state and the double-submit guard around `*2.2`'s write.
- Gating the transition to the tab tree on a confirmed write.
- The retry-then-sign-out failure path, capped at two attempts.
- Bounding the submitting state so an offline write cannot hang in it forever.
- The one-time `Users/{uid}` read after auth state resolves, and the missing-profile state it produces.
- The single interim branch that renders `CreateProfilePage` for a user in that state.

**Explicitly out of scope**

- **Writing any Firestore field.** `*2.2` owns the write; this ticket reads.
- **The onboarding sequence, the interests picker, the step machine, the password rule and everything else on `CreateProfilePage`.** 1.4. This ticket's edit to that file is the submitting state on the button and its prop, and nothing else.
- **Routing a missing-profile user through recovery.** 1.4.
- **Auth calls of any kind, including the sign-out call itself** — 1.2 owns `signOut`; this ticket triggers it, it does not implement it.
- **Auth error copy.** 1.2 owns that mapping. This ticket's copy is the profile-write failure only.
- **Field validation on the signup form.** 1.4 owns every rule on that screen. This ticket does not add, change or duplicate a validation check.
- **React Navigation, the fifth tab, and any routing work.** Other tickets.
- **Security rules.** Project 3.

**Security rules changes:** No changes needed. This ticket adds one read of a document the signed-in user owns.

**Security note.** The missing-profile read must key off the UID from `onAuthStateChanged` and nothing else. A check that trusts a locally stored id — `knect_session` or otherwise — is a check that can be pointed at another user's document.

**Files allowlist — touch nothing else.**

```
App.tsx
components/CreateProfilePage.tsx   — the submitting prop on `Props` and the button at :205–207 ONLY
```

A small hook or helper for the profile-exists check is fine — put it where Project 0's conventions say.

**Stop and ask** rather than improvising if: the edit to `CreateProfilePage` starts reaching past the submit button; the missing-profile branch starts becoming a screen; or the check appears to need a listener rather than a one-time read.

**5 - Acceptance Criteria**

Verified by one method: **one Android device or emulator, signing up and signing in by hand.**

- While the account is being created, the submit button is disabled and shows a submitting state.
- Tapping the submit button repeatedly during the write produces **exactly one** Auth user and **exactly one** `Users` document.
- The tab tree appears only after both documents exist in the Firebase Console, and lands on the Planner tab.
- With the write forced to fail, the submit button shows a red outline and red "Try Again" text, and nothing the user typed is cleared.
- Tapping that button retries the write, and a retry that succeeds lands the user on the Planner tab exactly as a first-attempt success does.
- With the write forced to fail twice, the user is signed out and returned to the login screen with no message — and the Auth account still exists in the Firebase Console afterwards.
- **The recovery loop closes, end to end.** With the write no longer failing, signing in with that same account lands the user back in the profile step rather than the tab tree, and completing it writes both documents and reaches the Planner tab.
- **Submitting with the device offline does not leave the button stuck in the submitting state.** It reaches the retry treatment within a bounded time.
- Delete a test user's `Users` document in the Console, then sign in as them: **the tab tree does not render** — `CreateProfilePage` does.
- Restore that document and sign in again: the tab tree renders normally.
- On cold start with a valid session, the signup screen never flashes before the tab tree.
- No Firestore document is written by any path in this ticket — confirmed in the Console.
- `grep -n "setTimeout" App.tsx` returns nothing in the signup path.
- `npm run lint` passes.
- `npm test` passes.
