# 16.2. Proposal Resolution

**Status:** Not started
**Depends on:** 16.1 (proposals exist), **D2 (Cloud Functions setup)**, 3 (the `/Events/` rule) · **Blocks:** 17, 18

> **Read `Knect_Project_16_Phase1_Decisions.md` before this ticket.** The lifecycle rules here are Kyson's, and the reasoning behind each one lives there.
>
> **This is the half of Project 16 that fails silently.** 16.1 fails on a screen where you can see it. Everything here happens in a Cloud Function, on a timer, on documents nobody is looking at — so the acceptance criteria lean on the emulator rather than on the app.

---

**1 - User Story**

As a User, I want a plan to become real once someone actually commits to it, and to stop hanging around if nobody does, so that I'm not waiting on people who were never going to answer and I'm not looking at a calendar full of things that never happened.

---

**2 - The Architecture & Technical Details**

**Target Database Collections:** `Events` (read and update `status`) · `Users/{uid}/Free_Busy` (write, via the Admin SDK) · `Chats` (read only, if the confirmation notice is written as a message — see out of scope)

**Data model changes:** **None.** Every field this ticket needs — `created_at`, `resolves_at`, the four-value `status`, and the alternative-open field — is written by 16.1. This ticket only ever changes `status` and writes `Free_Busy` blocks.

**The lifecycle, as a table. Spec this before any prose gets written into code.**

| From | Trigger | To |
|---|---|---|
| `proposed` | ≥1 `going` from someone other than `owner_id`, **and** no open alternative | `confirmed` |
| `proposed` | `resolves_at` passes with ≥1 non-owner `going` and no open alternative | `confirmed` |
| `proposed` | `resolves_at` passes with **zero** non-owner `going` | `expired` |
| `proposed` or `confirmed` | The proposer cancels | `cancelled` |

**`confirmed`, `expired` and `cancelled` are terminal. Nothing ever transitions back to `proposed`.** That is the whole reason alternatives are only allowed while a proposal is still open — it keeps this table forward-only, and a state machine that can go backwards is roughly twice the work to get right and far more than twice the work to test.

**The 24-hour window, restated so it isn't re-derived:** `resolves_at = min(created_at + 24h, event_time)`, written once by 16.1 and never recomputed. It can't drift, because 16.1 disables drag/resize on proposed events specifically so `event_time` can't change while a proposal is open.

**What runs the clock — a scheduled Function sweep.** Nothing client-side can flip a state while the app is closed.

- Query: `Events where status == "proposed" and resolves_at <= now`. One equality, one inequality, one composite index.
- Every document it finds resolves to `confirmed` or `expired` by the table above.
- `[DECISION: the sweep interval. Every 15 minutes bounds the lag at 15 minutes and costs 96 invocations a day. Every 5 minutes is tighter and 288. Every hour is cheap and means a plan can sit unresolved for 59 minutes past its own start time when event_time is the binding constraint.]`

**What confirms a proposal the moment someone says yes — this is not settled and it matters:**

`[DECISION: the immediate-confirmation mechanism. Three options.`
`(a) A Firestore onUpdate trigger on Events. Fires on every RSVP write, evaluates the rule, confirms. Instant, which is what "it stops being a proposal" implies. Costs one Function invocation per RSVP, and it MUST guard on status == "proposed" or it re-fires on its own write and loops.`
`(b) The sweep only. No trigger; confirmation waits for the next sweep. Cheapest and simplest, and the only mechanism to test. But saying yes does nothing visible for up to the sweep interval, which reads as broken on the one screen people watch.`
`(c) The client writes status when its own RSVP satisfies the rule. No Function at all. But the rule then has to let a participant write status, two clients can race, and it puts a lifecycle decision in the least trustworthy place in the system.]`

**Confirmation writes `Free_Busy`.** For each uid whose `rsvps` value is `going`, write a block to `Users/{uid}/Free_Busy` with the event's `start_time` and `end_time`.

- **Use the Event's id as the Free_Busy document id.** It is the only way to find and remove the block later without querying every block a user has. Cancellation depends on this.
- A `going` RSVP by itself writes nothing — 16.1 is explicit about that. The block exists because the event is real, not because someone tapped a button.
- **Consequence of the bracket below:** if someone who never answered can still say yes *after* confirmation, their block has to be written then too, so the Free_Busy write cannot live only at the moment of confirmation.

**🔴 Two Phase 1 rulings disagree with each other, and this ticket cannot be built until one gives:**

- "RSVPs are changeable while proposed, **locked once it resolves**."
- "Someone who never answered keeps a live ghost **and live buttons, indefinitely**."

Both can't be true. `[DECISION: the reconciliation. Either (a) the lock applies only to CHANGING an existing answer — a pending user may still answer for the first time after confirmation, which makes both rulings true and is probably what was meant; or (b) resolution locks the whole map, and the "live buttons" ruling only holds for the window before resolution. (a) means the Free_Busy write and confirmed_participants keep moving after confirmation; (b) means a non-responder's ghost is permanently frozen and their buttons are decorative.]`

**Cancellation:**

- Proposer only. `status` becomes `"cancelled"`.
- The event drops off every planner. **The chat message is not tombstoned** — the card renders as cancelled in place, so the thread keeps its continuity and nobody has to wonder what the conversation was about. Same reasoning 15.2 used for message deletion.
- **Every `Free_Busy` block the event wrote has to be removed.** This is why the block id is the event id.
- Cancel is a client write, not a Function — it is one field, by one known person, with a rule that can express it exactly.

**Expiry:**

- `status` becomes `"expired"`. Off every planner, card renders as expired.
- No `Free_Busy` was ever written, since the event never confirmed. Nothing to clean up.

**Known bugs and patterns to avoid:**

- **A Firestore trigger that writes to the document it is watching will re-fire on its own write.** If option (a) above is chosen, the first line of the handler is a guard on the incoming status. This is the most common way a Function like this turns into a billing incident.
- **The sweep must be idempotent.** An overlapping or retried invocation has to be harmless — resolve only documents still at `"proposed"`, and let the write be a no-op otherwise.
- **`utils/votingLogic.ts` breaks ties with `Math.random()`**, which is why tallying can't be client-side. Nothing in 16.2 tallies anything, but the same reasoning is why resolution lives in a Function here: **two clients evaluating the same rule must not be able to reach different answers.**
- **Do not write `confirmed_participants`.** It stays derived from `rsvps`, and 16.1 already says so.
- Every timestamp comparison is against a Firestore `Timestamp`, not `Date.now()`.

**3 - The UI and Layout Requirements**

Almost nothing here is new UI — this ticket mostly changes which state an existing card is in.

- **Loading / empty / error states:** unchanged from 16.1. No new patterns.
- **Confirmed:** the planner ghost goes solid for anyone whose RSVP is `going`. The chat card drops its GOING/NO buttons for anyone who already answered and shows the final headcount.
- **Expired:** off the planner. The chat card renders as spent — grey, no buttons, one line of copy. `[DECISION: the copy. Something like "Nobody was able to make it" is honest but reads as a small social failure; "This plan expired" is neutral and slightly cold.]`
- **Cancelled:** off the planner. The chat card renders in place as cancelled, with who cancelled it. **Not** removed from the thread.
- **Declined:** the event is already off the planner of anyone who said no — that's 16.1 behavior, unchanged here.
- **Never answered:** the ghost stays. See the 🔴 bracket in Section 2 for whether the buttons stay live with it.
- **No spinner, no progress state, and nothing that implies the app is waiting.** Resolution happens on a server on a timer; the UI just renders whatever state the listener delivers.

**4 - Security and Scope**

**In scope**

- The scheduled sweep Function and its composite index.
- Whichever immediate-confirmation mechanism the bracket in Section 2 resolves to.
- The `Free_Busy` write on confirmation, and its removal on cancellation.
- Cancellation, as a client write with a rule.
- Locking the `rsvps` map at resolution, to whatever degree the 🔴 bracket resolves to.
- The confirmed / expired / cancelled card and planner renderings.

**Explicitly out of scope**

- **Creating anything.** Proposals, messages, Events, RSVP seeding — all 16.1.
- **Notifying anyone that a plan confirmed or expired.** That is Project 20, and it hangs off whichever trigger this ticket lands on so it isn't built twice. **Do not build a notification path here.**
- Writing a `"system"` message into the chat when a plan resolves. `"system"` is in the enum and still nothing writes it — 15.2's ruling stands until something takes ownership.
- Alternatives, votes, and anything that would reopen a resolved event — Project 17, and by ruling, alternatives can only be raised while a proposal is still open.
- External calendar sync — 19.
- Any retroactive cleanup of events created before this ticket ships.

**Files this ticket may modify**

- `functions/` — the scheduled sweep, and the confirmation trigger if the bracket lands there
- `services/eventRepository.ts` — the cancel call only
- `components/SocialDashboard.tsx` — the resolved card states
- `components/DraggableEvent.tsx` — solid vs. ghost, and the cancelled/expired case
- `firestore.rules` — the `Events` update rule only
- `firestore.indexes.json`

Specifically **do not** touch the create path, the batch write, or the entry points. Those are 16.1's and they are finished by the time this runs.

**Security rules changes**

- **Events `update` — `status`:** two allowances and nothing else.
  1. The Admin SDK writes `confirmed` and `expired`, which bypasses rules entirely. **No client-side allowance for those two values.** Worth confirming rather than assuming — if any resolution path ends up client-side, the rule has to permit it explicitly, and option (c) in Section 2's bracket is exactly that case.
  2. `cancelled` may be written by a client when `request.auth.uid == resource.data.owner_id`, the affected keys are `status` alone, and the new value is exactly `"cancelled"`.
- **Events `update` — `rsvps`:** 16.1's rule already gates on `resource.data.status == "proposed"`. Whether that stays as written depends on the 🔴 bracket. If a pending user may answer after confirmation, the condition has to widen to permit writing a key whose current value is `"pending"` on a `confirmed` event — **and it must still forbid changing a key that already holds an answer.**
- **`Free_Busy`:** written by the Admin SDK. The existing permissive read rule is unchanged, and its "this is UI-gating, not security" caveat still holds.
- **No new `delete` allowances anywhere.** An event is cancelled, never deleted.

**5 - Acceptance Criteria**

- [ ] A proposal with one non-owner `going` and no open alternative reaches `status: "confirmed"` — verified in the emulator, not by reading the code.
- [ ] A proposal where only the owner is `going` does **not** confirm, no matter how long it sits.
- [ ] With `resolves_at` in the past and zero non-owner `going`, the sweep sets `status: "expired"`.
- [ ] With `resolves_at` in the past and one non-owner `going`, the sweep sets `status: "confirmed"`.
- [ ] Running the sweep twice over the same data changes nothing the second time.
- [ ] A confirmed event writes one `Free_Busy` block per `going` participant, and the block's document id is the event id.
- [ ] An expired event writes no `Free_Busy` block for anyone.
- [ ] Cancelling an event removes every `Free_Busy` block it wrote.
- [ ] Cancelling leaves the chat message in place, rendering as cancelled — it is not tombstoned and the thread has no gap.
- [ ] A non-owner cannot cancel — denied by rules, verified in the Rules Playground.
- [ ] A client cannot write `status: "confirmed"` or `status: "expired"` directly — both denied.
- [ ] A confirmed event cannot return to `proposed` by any path, including an RSVP flipping to `not_going`.
- [ ] The confirmation Function does not re-fire on its own write — verified by a log line count, not by reading the guard.
- [ ] A proposal created 90 minutes before its own start time resolves at the start time, not 24 hours later.
- [ ] The sweep query uses the `status` + `resolves_at` composite index and does not read every proposed event in the database.
- [ ] `confirmed_participants` still has no client write anywhere — grep returns reads only.
- [ ] Whatever the 🔴 bracket resolves to is enforced in the rule, and the opposite case is an explicit deny test in the Rules Playground.
