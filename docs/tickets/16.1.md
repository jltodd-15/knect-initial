**Status:** Not started

**1 - User Story**

As a User, I want to put an activity in front of my friends as a real plan — with a time on it, in the chat we already have, showing up on everyone's calendar — so that "we should do this sometime" turns into something on a specific day without a thread of back-and-forth messages.

**2 - The Architecture & Technical Details**

**Target Database Collections:** `Events` (create, read, and update the `rsvps` map) · `Chats/{chatId}/Messages` (create only) · `Chats` (read, for `participants`) · `Users/{uid}` (read, for live name and picture) · `Activities/{id}` (read, for the card's title and picture)

**Data model changes — `Events`:**

- ➕ **`created_at` (Timestamp).** The Events document records when the event *happens* and nothing about when it was *made*. 16.2's window has nothing to measure from without it.
- ➕ **`resolves_at` (Timestamp).** Set at write to **`min(created_at + 24h, event_time)`**. 16.1 writes it; 16.2 reads it. Storing it means the sweep is one indexed query instead of two, or a multi-inequality.
- ✏️ **`status` gains two values — four total:** `"proposed"` · `"confirmed"` · `"expired"` · `"cancelled"`. 16.1 only ever writes `"proposed"`; the other three belong to 16.2.
- ➕ **A field expressing "an alternative is open."** 16.1 defines it and treats it as always-empty; **Project 17 is the only thing that ever writes it.**
  - `[DECISION: the shape. Either open_alternative_vote_id (String, empty when none) — which doubles as the pointer 17 needs anyway — or has_open_alternative (Boolean), which is smaller but tells you nothing about which alternative is open. Pick when 17 is written, not after.]`
- ✏️ **`activity_id` is explicitly optional.** A freeform proposal ("dinner at my place Friday") is the same document with no activity behind it. Every read of this field tolerates its absence.
- ✏️ **`confirmed_participants` is derived, not maintained** — the uids whose `rsvps` value is `going`. Do not write it as a separate list.
- **`linked_chat_id` stays singular.** One chat per proposal. Multi-send is a later feature and this field is not an array.

**Data model changes — `Messages`:**

- ➕ **`event_id` (String).** The proposal message needs a pointer to its Event, and the schema had none — a card can't find its RSVPs without one. The prototype already has `Message.eventId` in `types.ts`; this is that field, renamed to snake_case.
- Everything else a proposal message uses — `message_type`, `activity_id`, `event_title` — 15.2 already defined.

**The three-way link, stated once so nothing re-derives it:** a proposal message points at its Event via `event_id`. An Event points back at its vote via `linked_vote_id`, and a Vote points at its Event via `linked_event_id`. **Both of those already exist in the schema.** 16.1 writes `event_id`; Project 17 writes the vote pair.

**Creating a proposal — the flow, in order:**

1. The user picks an activity (or types a freeform title), picks a time, and picks the chat.
2. **One `WriteBatch` writes both documents** — the `Events` document and the proposal message. They are in different collections, which a batch handles fine.
   - **Do not write them as two separate calls.** If the message write fails after the Event write succeeds, you get an Event nobody can see or RSVP to, sitting as a ghost on five calendars with no way to resolve it. That's the single worst failure state this ticket can produce.
   - Generate the Event's document ID client-side before the batch, so the message's `event_id` can be set inside the same batch.
3. The Event is written with `status: "proposed"`, `owner_id` = the proposer, `shared_with` = the chat's current `participants`, `rsvps` seeded with **every participant as `"pending"` and the proposer as `"going"`**, `created_at` and `resolves_at` set.
4. **The message's `text` is set to `📅 Event Proposed: {event_title}`.** This is not cosmetic. 15.2's preview Function copies the message's `text` onto the chat document, so a proposal with an empty `text` produces a blank chat-list row and an unread dot pointing at nothing. `ChatService.ts:161` already writes exactly this string — keep it.

**Three entry points, and two of them already have routes in the code:**

1. **From the Planner.** `EventPlanner.tsx:139` — creating an event with participants already calls `findOrCreateConversation` and sends an `event-proposal` message. This is the existing flow; it gets repointed at Firestore.
   - **Note the intended behavior, so nobody "fixes" it:** proposing to four people out of a six-person chat creates (or finds) a four-person chat. The other two don't see it. That's correct — if you only invited four people, the plan belongs in a room with four people in it.
2. **From a chat.** `SocialDashboard.tsx:902` already calls `onPlanActivity(null, selectedConvo.participants)`, which opens the create flow prefilled with that chat's people. The chat is known, so `linked_chat_id` is already decided.
3. **From Discover.** `DiscoveryFeed.tsx:154` calls `onPlanActivity(selectedItem)` from the detail modal — Project 12's "Make This An Event." **This becomes a chooser: Planner or chat.** Choosing a chat lands in the same create flow with the activity prefilled. There is no share affordance on a Discover *card* today, so that part is greenfield.

**`shared_with` tracks chat membership.** Anyone in the chat is an invitee. **Consequence for 15.1: add/remove-member now has to write `Events.shared_with` and the `rsvps` map for every open proposal in that chat** — adding someone seeds them `pending`, removing someone drops their key. That is scope 15.1 does not currently have, and it needs to be added there rather than hidden here.

**RSVPs:**

- A participant writes exactly one key — their own — in the `rsvps` map. Same shape as `normal_votes`, so dedup is structural and the rule is one line.
- Changeable freely while `status == "proposed"`. **Locked once the event resolves** — 16.2 enforces that in the rule.
- 16.1 does **not** write `Free_Busy`. That write happens on confirmation and belongs to 16.2.

**Live state — one app-wide Events listener, and this is a deliberate exception:**

- `Events where shared_with array-contains uid`, live, in **one shared repository module** that both the Planner and the chat cards read from.
- **15.2 committed to "two listeners, and never more." This makes three.** The exception is on purpose: the planner ghost and the chat card are two renderings of the same document, and the alternative is two independent sources of truth for one Event. One listener, one index, one answer.
- **Same teardown discipline as 15.2's** — unsubscribe on unmount and on background, resubscribe on foreground. `EventPlanner.tsx:97` is currently the comment `// TODO: Create listener for new events`. This is that listener.
- **It needs a date bound** or it loads every event you have ever been invited to. `[DECISION: what bound. The current calendar window forward is the obvious answer, but the planner's 12-month view can scroll past it, and a proposal for next year is still a live proposal.]`

**Drag and resize — personal events only, and write down why:**

- Drag and resize stay on **personal** events (no participants), as a way to move your own calendar around.
- They are **disabled on `proposed` events**, because changing the time is meant to be an alternative proposal and that route belongs to 17.
- Confirmed group events don't drag either. The owner cancels and re-proposes.
- **The reason matters more than the rule:** with the time locked while a proposal is open, `event_time` is immutable, so **`resolves_at` can never go stale.** Anyone who re-enables dragging on a proposed event without knowing that silently breaks 16.2's sweep.

**Timestamps.** Every date in the prototype is epoch milliseconds — `timestamp: number`, `endTime: number`. The schema is Firestore `Timestamp` throughout. Convert at the boundary; do not carry `Date.now()` values into a document.

**Known bugs and patterns to avoid:**

- **`types.ts` puts RSVPs on a chat message** — `Message.eventDetails.rsvps`. **Do not carry that shape forward.** RSVPs live on the Event (O18). A message carries a pointer and nothing else. `ChatService.updateMessageRSVP` goes away with `ChatService.ts` in 15.2.
- **`components/ChatEventWidget.tsx` is dead and wrong** — nothing imports it, and it uses a third RSVP vocabulary (`'yes' | 'no'`) that disagrees with the live card's `'going' | 'not_going'`. **Delete it.** It is a deletion, not a reconciliation.
- **`CalendarEvent.attendees[]` is dead code** — never written, never read, and a fourth vocabulary for "who's coming." Do not implement against it.
- **`EventPlanner.tsx:111`** already decides proposal vs. personal by `participants.length > 0`. Keep that rule; it is correct.
- **Do not rewrite the planner UI.** The week/day grid, 12-month view, now-line, cluster overlap layout, and the 4-step create modal are roughly 1,800 lines of working code. This is a data-layer ticket with a small number of UI additions.
- **Do not rewrite the proposal card.** `SocialDashboard.tsx:615` onward is the most complete feature in the prototype — proposer attribution, invitee avatars with per-person status badges, GOING/NO buttons. Keep it; repoint it.

**3 - The UI and Layout Requirements**

- **Loading state:** the grey skeleton pattern that is now the app-wide standard — a placeholder card block in the thread, and faded blocks on the planner grid.
- **Empty state:** not applicable to a proposal itself. The planner's own empty state is D3's.
- **Error state:** the shared component from Appendix B (circle with `!`), copy "Sorry, we couldn't load anything right now." Do not write new copy.
- **Proposal card — the existing one, with states driven by `rsvps[myUid]`:**
  - `pending` → GOING and NO both inactive, buttons live.
  - `going` → GOING filled, check icon, per `SocialDashboard.tsx:691`.
  - `not_going` → NO filled, and the "Can't make it? Propose a change instead!" block appears beneath it, exactly as `SocialDashboard.tsx:708` already does. **Saying no is what unlocks proposing an alternative** — that conditional is the intended social logic, not an accident. Keep it.
- **Propose Change button:** stays exactly as built, and **stays unpersisted.** It opens the event menu and the vote creator, and the vote dies on reload — `SocialDashboard.tsx:865` is still `// In real app: ChatService.sendVote(...)`. **Project 17 makes it persist. 16.1 writes no `Votes` document.** Say this in the code with a comment, not just in the doc.
- **Invitee avatars:** resolved live from `Users/{uid}`, deduped and session-cached through the same module 15.2 built for message senders. A 6-person proposal costs 6 user reads once, not 6 per render. **"Deleted user" plus a placeholder avatar is required** — same standing rule as everywhere else.
- **Planner ghost:** proposed events render at 20% opacity — `DraggableEvent.tsx:242` already does this (`${event.color}33`). Solid once confirmed.
- **Someone who never answered keeps a live ghost and live buttons, indefinitely.** Silence is not read as a no. This is deliberate and it is not a bug.
- **Share card (`message_type: "activity"`):** the activity's picture and name in a chat bubble, tapping opens the detail page. No RSVPs, no Event, no buttons. This is a third variant of the activity card — add it to Appendix B.
- **"Make This An Event" becomes a chooser** — Planner or chat — rather than routing straight to the Planner.
- **Time is required.** The create flow will not submit a proposal without one. Enforced in the UI here; there is no rule-level enforcement in this ticket.

**4 - Security and Scope**

**In scope**

- Writing the `Events` document and the proposal message as one batch, with `event_id` linking them.
- The three entry points, including the chooser on "Make This An Event."
- Seeding and collecting RSVPs; a participant writing their own key.
- The app-wide Events listener and its repository module, with teardown.
- The planner ghost render, and disabling drag/resize on anything that is not a personal event.
- The share card for `message_type: "activity"`.
- Live invitee-avatar resolution through 15.2's session cache, with the "Deleted user" fallback.
- Deleting `components/ChatEventWidget.tsx`.
- The `Events` and widened `Messages` rules below.

**Explicitly out of scope**

- **Everything that resolves a proposal** — the confirmation rule, the 24-hour sweep, expiry, cancel, and the `Free_Busy` write. All of that is **16.2**. 16.1 ships proposals that only ever sit at `"proposed"`, and that is expected, not incomplete.
- **Persisting a vote or an alternative.** The Propose Change route stays local — Project 17.
- **Multi-chat proposals.** One chat per proposal.
- Editing a proposal after it is sent — no time change, no title change, no invitee edits from inside the card.
- Recurrence, reminders, and anything calendar-sync — 18 and 19.
- Push notifications — Project 20. **Including notifying a group that someone changed their RSVP**, which is the thing that makes a late flip survivable.
- Add/remove chat member writing to `Events` — that belongs in **15.1**, flagged here.
- A self-join path for group chats. **This has no ticket anywhere** — see Section 2.

**Files this ticket may modify — anything not on this list is out of scope by default**

- `components/ChatEventWidget.tsx` — **delete**
- New: an events repository module (e.g. `services/eventRepository.ts`)
- `components/EventPlanner.tsx`
- `components/CreateEventModal.tsx`
- `components/DraggableEvent.tsx`
- `components/SocialDashboard.tsx`
- `components/DiscoveryFeed.tsx`
- `App.tsx` — the `onPlanActivity` route only
- `types.ts` — the `CalendarEvent` and `Message` shapes only
- `firestore.rules` — the `Events` match block and the `Messages` create rule only
- `firestore.indexes.json`

Specifically **do not** touch `utils/votingLogic.ts` (Project 17 owns it, dead as it is), the auth path, or anything in `services/` that 15.2 already replaced.

**Security rules changes — required before any code is written**

- **`/Calendars/` becomes `/Events/` first.** Project 3 owns this and nothing in 16.1 runs until it lands.
- **Events `create`:** `request.auth != null && request.resource.data.owner_id == request.auth.uid`. Anyone may create an event; nobody may create one in someone else's name.
- **Events `read`:** `request.auth.uid in resource.data.shared_with`.
- **Events `update` — `rsvps`:** a participant may write **only their own key**, and only while `resource.data.status == "proposed"`. One line, same pattern the schema already chose for `normal_votes`.
- **Events `update` — `shared_with`:** **any participant of `linked_chat_id` may write it**, verified with a `get()` on the chat.
  - *Known and accepted, stated so nobody files it as a bug:* one participant can remove another person from a plan, and nothing records who did it. The exposure is bounded — it can only ever be someone already in that chat.
- **Messages `create` widens to values only:** `"text"`, `"activity"`, `"event_proposal"`. No shape checks, no ownership `get()`.
  - **15.2's rule permits only `"text"`, so without this change every proposal message is denied.** That is the first thing to verify in the emulator.
  - *Known and accepted:* nothing stops a malformed proposal message pointing at no event. It renders as a broken card rather than being rejected.

**Composite indexes** — `shared_with array-contains` plus whatever date bound the listener uses. `firestore.indexes.json` still has no owner in the implementation order (F8); this ticket needs it to exist.

**5 - Acceptance Criteria**

- [ ] Proposing an activity from the Planner writes one `Events` document and one proposal message, in a single batch. Killing the network mid-write leaves neither, not one.
- [ ] The proposal message's `event_id` matches the created Event's document ID.
- [ ] The created Event has `status: "proposed"`, `owner_id` equal to the proposer, `created_at` set, and `resolves_at` equal to the earlier of `created_at + 24h` and `event_time`.
- [ ] A proposal made for 90 minutes from now has `resolves_at` equal to `event_time`, not `created_at + 24h`.
- [ ] `rsvps` is seeded with every chat participant as `"pending"` and the proposer as `"going"`.
- [ ] The proposal's chat-list preview reads `📅 Event Proposed: {title}` — not blank.
- [ ] The proposal appears as a ghost on every invitee's planner without either app being reopened.
- [ ] Tapping GOING on device A updates the invitee badge on device B without a reload.
- [ ] Proposing to a subset of a group chat's members puts the proposal in a chat containing exactly those members — the uninvited members never see it.
- [ ] A proposal with no `activity_id` (freeform title only) renders correctly in both the chat card and the planner.
- [ ] The "Make This An Event" button on the activity detail page offers Planner or chat, rather than routing straight to the Planner.
- [ ] A proposal with 6 invitees issues 6 `Users` reads for avatars, not 6 per render.
- [ ] An invitee whose `Users` document does not exist renders "Deleted user" and a placeholder avatar.
- [ ] Dragging or resizing is possible on a personal event and impossible on a proposed one.
- [ ] `confirmed_participants` is never written by the client — a grep finds no client write. It is computed from `rsvps`.
- [ ] Navigating away from the Planner and backgrounding the app both tear down the Events listener; foregrounding restores it.
- [ ] Every `onSnapshot` in the codebase still has a matching unsubscribe.
- [ ] `components/ChatEventWidget.tsx` no longer exists and nothing imports it.
- [ ] No RSVP data is written to any message document — a grep for `eventDetails` returns nothing.
- [ ] Tapping NO reveals the "Propose a change instead" block; using it creates a vote that does not survive a reload, and the code says so in a comment.
- [ ] **Rules Playground, deny cases run explicitly:** a non-invitee reading an Event · a participant writing another user's key in `rsvps` · creating an Event with someone else's `owner_id` · a non-chat-participant writing `shared_with` · creating a message with `message_type: "vote"`.
- [ ] **Rules Playground, allow case:** a participant creating a message with `message_type: "event_proposal"` — this is the case 15.2's rule currently denies.
