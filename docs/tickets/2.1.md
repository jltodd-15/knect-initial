**2 - The Architecture & Technical Details**

> **The model, in three lines.** This ticket adds no data and reads none. It installs `@react-native-firebase/firestore` and creates the single module that configures it. Persistence is a decision made here once, not a default inherited silently by twelve tickets.

- **Target Database Collection:** None.
- **Data model changes:** None.

**Why this is its own ticket.** Round 9 ruled offline persistence ON "in one Firestore config module" and propagated that to Project 0 — a conventions doc, which writes no code, so nothing owned it. Round 10 §7 assigned it to Project 2. 1.1 installs `@react-native-firebase/app`, `/auth` and `/analytics` and **deliberately does not install `/firestore`**; this ticket does.

**Current state, verified at `8493a36`.** `@react-native-firebase/firestore` is absent from `package.json`. There is not one occurrence of `firestore` or `Firestore` in any `.ts`, `.tsx` or `.js` file in the repo — a case-insensitive grep across the tree returns nothing outside `android/`. This is greenfield, not a repair.

**The Android artifact is already declared.** `android/app/build.gradle:121` has `implementation("com.google.firebase:firebase-firestore")` under the BOM at `:118` — the same situation Round 10 §5 found for analytics, where the Gradle line was already there and only the npm package was missing. Assume the JS install is the whole job and **stop and ask if a Gradle edit appears necessary**; 1.1 already reconciled that file.

**The config module.**

- One module, created new. Put it where Project 0's conventions say services live.
- It is the **only** place the Firestore instance is configured. Every later ticket imports the instance from here rather than calling the SDK's initializer again.
- **Persistence is set explicitly to on.** Do not set a cache size — the SDK's default is the decision, and writing an explicit number turns a default into a magic value someone has to justify later.
- It must run before any Firestore call. Import it at the app's entry point.

The native SDKs likely default persistence to on already. Setting it by hand is the point: it makes this a decision with one file to look at, rather than an inherited behavior that changes when the SDK does.

**Known bug this ticket's path touches.**

`.gitignore:78–79` are `*firebase*` and `*firestore*`, with `!*firebase*.kt*` on line 80 as the only exception. Verified with `git check-ignore`. **1.1 fixes these lines.** If 1.1 has not landed, any `firebase.json` this install produces is silently untracked — the file exists locally, works locally, and is missing for everyone else. There is no `firebase.json` in the repo today. **Do not edit `.gitignore` here** — it belongs to 1.1. If the lines are still unfixed when this ticket starts, stop and say so.

**4 - Security and Scope**

**In scope**

- Installing `@react-native-firebase/firestore` and whatever autolinking requires.
- One new Firestore config module, with persistence set explicitly on.
- Importing that module at the app entry point so it runs before any Firestore call.

**Explicitly out of scope**

- **Any read or write of application data.** `*2.2` owns the first write.
- **Collections, documents, types, and repository modules.** `*2.2`.
- **Security rules.** Project 3.
- **`.gitignore`.** 1.1 owns lines 78–80.
- **Connectivity banners, retry behavior, and offline error copy.** Those are Project 0's app-wide conventions, not this module's.
- **The Firestore emulator.** `FirebaseModule.kt:50–51` pointed auth *and* Firestore at port 8080 (Auth's emulator port is 9099) behind a hardcoded `debug = true` at `:37`, then reassigned `firebaseDB` at `:53` and discarded the config entirely. That file is deleted by 1.1. Do not reintroduce emulator wiring here — if it is wanted, it needs its own decision.

**Security rules changes:** None. This ticket touches no data.

**Files allowlist — touch nothing else.**

```
package.json                    — the @react-native-firebase/firestore dependency
<services dir>/<new module>     — the Firestore config module
index.js  or  App.tsx           — one import line, whichever is the entry point
```

**Stop and ask** rather than improvising if: the install appears to need a Gradle or Podfile edit (1.1 reconciled Gradle; 0.2 owns iOS); `.gitignore` still hides `firebase.json`; or configuring persistence seems to require a second initializer somewhere else.

**5 - Acceptance Criteria**

Verified by one method: **one Android device or emulator, against the live Firebase project.**

- `@react-native-firebase/firestore` appears in `package.json` dependencies.
- The app builds clean and boots to the login screen.
- Seed one document by hand in the Firebase Console. With the device online, the app reads it once through the config module's instance and logs the result.
- Kill the app, put the device in airplane mode, relaunch, and read the same document again — **it still resolves, from cache.** This is the criterion that actually proves persistence is on.
- `grep -rn "initializeFirestore\|firestore()" --include=*.ts --include=*.tsx .` returns hits in the config module and nowhere else.
- `npm run lint` passes.
- `npm test` passes.
