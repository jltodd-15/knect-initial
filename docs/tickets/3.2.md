# *3.2. Rules — the User Tree & Activities

**Status:** Not started. Drafted 2026-09-09.
**Depends on:** `*3.1` (the file, the deploy path and the test harness must exist)
**Blocks:** `*3.3`. Unblocks Project 11's like write and Project 12's Saved list, both of which are denied today.

---

**1 - Goals**

- Every collection under `/Users/{userId}` has a rule, including `Liked_Activities`, which has none today and is therefore denied by the catch-all.
- `Activities` stops requiring a `creator_id` that seeded rows do not have.
- Each of those documents gains a **field allowlist** — ownership was already correct; what a user could write *into* their own document was not constrained at all.
- Every allow and every deny is a test in `firestore-tests/`, run by `npm run test:rules`.

---

**2 - The Architecture & Technical Details**

> **The model, in three lines.** Everything under `/Users/{userId}` is owner-scoped: the document ID *is* the Auth UID, so ownership is a string comparison and never needs a `get()`. The Users document itself is readable by every signed-in user, which is why nothing private may ever live on it. `Activities` is public-read, and write access is gated on `source == "user_generated"` rather than on the presence of `creator_id`.

- **Target Database Collections:** `Users` and all five of its subcollections; `Activities`.
- **Data model changes:** **None.** Every field named below already exists in the Master Schema. **If a field you need is not on these lists, stop — do not add it to the rule.**

**Two shared helpers, at the top of the file.**

```
function signedIn()      { return request.auth != null; }
function isUser(uid)     { return signedIn() && request.auth.uid == uid; }
function changedKeys()   { return request.resource.data.diff(resource.data).affectedKeys(); }
```

**`Users/{userId}`**

```
match /Users/{userId} {
  allow read: if signedIn();

  allow create, update: if isUser(userId)
    && request.resource.data.keys().hasOnly([
         'name', 'name_lowercase', 'profile_info', 'profile_picture_url',
         'interests', 'current_status', 'status_visibility', 'status_expires_at'
       ]);

  allow delete: if isUser(userId);
}
```

`hasOnly` permits a **subset**, which is what makes this compatible with `*2.2` — that ticket writes five of the eight fields and deliberately omits the three status fields, and this rule allows exactly that.

> **`delete` is split out on purpose.** `allow write` would cover deletes too, and on a delete `request.resource` is null — so a single `allow write` carrying a `request.resource.data` check denies every delete with a null-reference error rather than an obvious permission error. Same pattern applies to every block below.

**`Users/{userId}/Private_info/main`** — **the document ID is pinned, not a wildcard.**

```
match /Users/{userId}/Private_info/main {
  allow read: if isUser(userId);

  allow create, update: if isUser(userId)
    && request.resource.data.keys().hasOnly([
         'location', 'geohash', 'email', 'blocked_users', 'fcm_tokens',
         'external_calendar_tokens', 'tag_affinity_scores',
         'tag_scores_last_decayed', 'liked_activity_ids'
       ]);

  allow delete: if isUser(userId);
}
```

The published rule matches `{privateId}` — any document ID at all. **This pins it to the literal `main`**, which R13 fixed and `*2.2` writes. A stray write to `Private_info/anything_else` is then denied rather than quietly creating a second document that nothing reads, which is the harder class of bug to find.

> ⚠️ **One thing reopens this: Decision Log F2.** If write contention on this document ever shows up, F2's answer is to split the hot-path fields — `tag_affinity_scores`, `location`, `geohash` — into a **second** owner-only document, and this rule denies that document until its path is added. *[Likely] it does not come up before launch* — it is a scale problem, and 13.2's 2-second debounce is what keeps us under Firestore's ~1 write/sec per-document ceiling at MVP volume. **If it does, it is a one-line rule edit on a day the schema is being edited anyway.** Named here so it reads as a known exit rather than a surprise denial.

**`Users/{userId}/Free_Busy/{blockId}`**

```
match /Users/{userId}/Free_Busy/{blockId} {
  allow read: if signedIn();

  allow create, update: if isUser(userId)
    && request.resource.data.keys().hasOnly(['start_time', 'end_time']);

  allow delete: if isUser(userId);
}
```

**Read stays open to any signed-in user, deliberately** — Q2, resolved. Free/busy is only ever surfaced between friends in the UI, so in practice nobody sees a stranger's. **This is UI-gating and it is not security:** someone hitting the API directly can read anyone's blocks. Accepted because a block reveals *that* you are busy and nothing about what you are doing. **If a title, a location, or a linked event is ever added to this document, this decision has to be reopened.**

16.2's Cloud Function writes these blocks with Admin SDK credentials, which bypass rules entirely. The owner-write clause here covers a user setting their own availability by hand and is not made redundant by that Function.

**`Users/{userId}/Friends/{friendId}`**

```
match /Users/{userId}/Friends/{friendId} {
  allow read: if signedIn();

  // Creating an entry: in your own doc you may only claim you sent a request.
  // In someone else's doc you may only claim you are requesting them.
  allow create: if signedIn()
    && request.resource.data.keys().hasOnly(['status'])
    && (
         (request.auth.uid == userId   && request.resource.data.status == 'request_sent')
      || (request.auth.uid == friendId && request.resource.data.status == 'pending')
       );

  allow update: if isUser(userId)
    && request.resource.data.keys().hasOnly(['status'])
    && request.resource.data.status in ['pending', 'request_sent', 'friend', 'close_friend'];

  allow delete: if signedIn()
    && (request.auth.uid == userId || request.auth.uid == friendId);
}
```

**Why `create` constrains the value, and this is not cosmetic.** The published rule permits either party to create the entry with **no constraint on what they write** — so any user can create `Users/{someone_else}/Friends/{me}` carrying `status: "close_friend"` and appear in that person's friends list without them ever acting. The clause above splits it by direction: writing into **your own** doc the only creatable value is `request_sent` ("I sent one"); writing into **someone else's** doc the only creatable value is `pending` ("someone is waiting on you"). Nobody can manufacture a friendship in anyone's list.

**`update` stays owner-only, and that is the ruling rather than a deferral.** This is B9, and the reasoning is worth keeping on the page because the rule looks broken on its own:

- Accepting a request is a two-sided write. Under this rule the second half — B updating `Users/A/Friends/B` — is **denied**, because B is not `userId`. A batch is all-or-nothing, so a client-side acceptance fails entirely.
- **Acceptance cannot be client-side anyway, for two reasons that have nothing to do with this rule.** O4 requires the block check against the recipient's `blocked_users`, which lives in `Private_info` and **no client can read**. S4 / 15.1 requires acceptance to find-or-create the 1-on-1 chat. Both are server work, so `acceptFriendRequest` has to run regardless.
- Given that, owner-only is not a broken rule — it is the **tightest** rule available, permitting strictly less than any alternative. Round 7's corollary ("a Function bypassing a broken rule is not a fixed rule") is satisfied: the rule is correct on its own merits, not merely bypassed.

⚠️ **The one condition attached to this ruling: Project 5's edit pass has to confirm no client-side acceptance path gets added.** If one ever is, this rule needs a narrow counterparty clause — `friendId` may update, `status` only, to `"friend"` only, and only from `"request_sent"`. **Written into `*3.4`'s audit as a check, not left as a bracket.**

> **Accepted cost, recorded so nobody reports it as a bug:** owner-only update means you can set **your own** copy to `"friend"` unilaterally, with nobody on the other end. Nothing stops it and nothing needs to — the other person's document does not move, so all it buys you is a wrong friends list on your own device. Not worth a rule.
>
> **`close_friend` is one-sided by design and needs no schema change.** The two documents are independent, so `Users/A/Friends/B == "close_friend"` while `Users/B/Friends/A == "friend"` is already valid. Starring someone is a write to your own document, which owner-only already permits. Project 5's Action D. **Do not treat `close_friend` as requiring the other party.**
- O4 then routed acceptance through the `acceptFriendRequest` Cloud Function, which uses the Admin SDK and bypasses rules. So **nothing is broken today.**
- Round 7's corollary is the reason this is still open: *a Function bypassing a broken rule is not a fixed rule.* If any acceptance path ever runs client-side, this denies it.

The two answers are (a) leave it owner-only and accept that acceptance is Function-only forever, or (b) add a narrow clause letting `friendId` update, constrained to `status` and only to the value `"friend"`. **Project 5 has not been through the edit pass yet, so the question of whether an acceptance path stays client-side is not answerable from here.** Carry the bracket into `*3.4`.

**`Users/{userId}/Activity_History/{historyId}`**

```
match /Users/{userId}/Activity_History/{historyId} {
  allow read: if isUser(userId);
  allow create, update: if isUser(userId)
    && request.resource.data.keys().hasOnly(['activity_reference', 'tapped_ads']);
  allow delete: if isUser(userId);
}
```

**🔴 `Users/{userId}/Liked_Activities/{activityId}` — this block does not exist today.**

```
match /Users/{userId}/Liked_Activities/{activityId} {
  allow read: if isUser(userId);
  allow create, update: if isUser(userId)
    && request.resource.data.keys().hasOnly(['saved_at']);
  allow delete: if isUser(userId);
}
```

There are blocks for `Private_info`, `Free_Busy`, `Friends` and `Activity_History` under `/Users/{userId}` and none for this one, so it falls to the catch-all deny. **Project 11's like write and Project 12's Saved list are both blocked today**, the same way Events is, and no ticket had it until it was found reading the mirrored rules on 2026-09-08.

**`Activities/{activityId}`** — the current rule requires `creator_id` on every document, which the schema does not have. The effect today is that seeded activities can be neither updated nor deleted, and user-created ones cannot be created at all.

```
match /Activities/{activityId} {
  allow read: if signedIn();

  allow create: if signedIn()
    && request.resource.data.source == "user_generated"
    && request.auth.uid == request.resource.data.creator_id
    && request.resource.data.keys().hasOnly([
         'name', 'description', 'cost', 'source', 'creator_id', 'category',
         'tags', 'pictures', 'location', 'geohash', 'is_location_based',
         'click_count', 'likes', 'created_at'
       ]);

  allow update, delete: if signedIn()
    && resource.data.source == "user_generated"
    && request.auth.uid == resource.data.creator_id;

  // Any signed-in user may increment engagement counters, and nothing else.
  allow update: if signedIn()
    && changedKeys().hasOnly(['click_count', 'likes']);
}
```

**Gating on `source` rather than on a missing `creator_id` is what makes this safe** — the rule evaluates a field that is always present rather than the absence of one, which is why `source` is required on every Activity. Practical effect: seeded activities cannot be edited from inside the app at all. CMS and Console edits use admin credentials and bypass rules.

The counter clause is what O6 requires — engagement counters run client-side through `FieldValue.increment()` behind one shared service module, not through a Function.

> ⚠️ **`is_active` and `updated_at` are deliberately absent from the create allowlist.** Q12 confirmed both are still deferred to 13.3. The Google Doc lists them without a deferral mark; that is a transcription gap, not a reversal. When 13.3 lands it adds them here.

**Known bugs to avoid:** none in this path. Verified at `8493a36` — no application code reads or writes Firestore, so nothing existing can be broken by tightening these rules. `*2.2` is the first write and it passes both the `Users` and `Private_info` clauses above.

**4 - Security and Scope**

**In scope**

- The seven rule blocks above, written into `firestore.rules`.
- The two shared helper functions.
- A test file per collection under `firestore-tests/`, each with its allow cases and its deny cases.
- One deploy after the suite is green.

**Explicitly out of scope**

- **`Chats`, `Messages`, `Votes`, `Events`, and the `Calendars` → `Events` rename.** All four are `*3.3`. Leave the `Calendars` block exactly as `*3.1` transcribed it — a half-renamed rules file is worse than an unrenamed one.
- **Type checks, required-field checks, and value validation** beyond the two places already ruled — `Friends.status`'s four values and `Activities.source`. The ruling is ownership plus a field allowlist; a `location` that is a string instead of a GeoPoint is not this ticket's problem.
- **A counterparty `update` clause on `Friends`.** Ruled out above — acceptance runs through `acceptFriendRequest`. `*3.4` re-checks the condition; this ticket does not add the clause.
- **Storage rules.** Project 6 / D9.
- **Composite indexes.** No query in this ticket.
- **Any application code.**

**Security rules changes:** **This ticket is the security rules change.** Seven blocks: `Users` and `Private_info` gain field allowlists, `Free_Busy` and `Activity_History` gain allowlists, `Friends` gains a direction-constrained `create`, an allowlist and a value check on `update`, and a `delete` split out from `create`; `Liked_Activities` is created from nothing; `Private_info`'s document ID is pinned to `main`, and `Activities` is rewritten to gate on `source`.

**Security notes:**

1. **Tightening a rule can break a write nobody has tested.** `*2.2` is the only ticket that writes any of these documents today, and its payload passes — but the acceptance suite must include a test that reproduces `*2.2`'s exact two-document batch, or this ticket can silently break signup.
2. **`Users` is readable by every signed-in user and the allowlist does not change that.** It constrains what the owner may write, not who may read. Nothing private goes on that document, ever — that is what `Private_info` is for.

**5 - Acceptance Criteria**

Verified by one method: **`npm run test:rules`.**

Allow cases — each must pass:

- A signed-in user reads any other user's `Users` document.
- A user creates their own `Users/{uid}` with `*2.2`'s exact five-field payload, and `Private_info/main` with `email`, `blocked_users: []`, `fcm_tokens: []`, **in one batch**.
- A user updates `current_status` on their own document.
- A user writes a `Free_Busy` block on their own subcollection, and reads a stranger's.
- A sends a request: `Users/A/Friends/B` created as `"request_sent"` **and** `Users/B/Friends/A` created as `"pending"`, both by A.
- B accepts their own half: B updates `Users/B/Friends/A` to `"friend"`.
- A stars B: A updates their **own** `Users/A/Friends/B` to `"close_friend"` while `Users/B/Friends/A` stays `"friend"` — the asymmetry is correct.
- Either party deletes a `Friends` entry (decline, cancel, unfriend, block).
- A user writes and reads their own `Liked_Activities/{activityId}` with `saved_at`.
- Any signed-in user updates only `click_count` and `likes` on a seeded activity.
- A user creates an Activity with `source: "user_generated"` and `creator_id` equal to their own UID.

Deny cases — each must be rejected:

- An **unauthenticated** client reads a `Users` document.
- User B writes to `Users/A`, to `Users/A/Private_info/main`, to `Users/A/Free_Busy/x`, to `Users/A/Activity_History/x`, or to `Users/A/Liked_Activities/x`.
- User B **reads** `Users/A/Private_info/main`, `Users/A/Activity_History/x`, or `Users/A/Liked_Activities/x`.
- A user writes `email` onto their own `Users` document.
- A user writes an undeclared field — `role`, `is_admin`, anything — onto their own `Users` document or their own `Private_info/main`.
- A user updates `Friends` `status` to a string outside the four values.
- **A creates `Users/B/Friends/A` with `"friend"` or `"close_friend"`** — forging a friendship in someone else's list. **This is the hole the published rule leaves open; it is the single most important deny case in this ticket.**
- A creates `Users/A/Friends/B` — their own doc — with `"pending"`, `"friend"` or `"close_friend"`. Only `"request_sent"` is creatable there.
- A `Friends` entry created carrying any field other than `status`.
- User B updates `Users/A/Friends/B` — **the acceptance case. It must fail, and the test must carry a comment saying acceptance runs through `acceptFriendRequest` by ruling**, so nobody later reads the failure as a bug and "fixes" it.
- A write to `Users/A/Private_info/not_main` by A themselves — **the pinned document ID.**
- A user creates an Activity with `source: "manual_diy"`, or with a `creator_id` that is not their own UID.
- A user updates or deletes a seeded activity (`source: "manual_diy"`).
- A user updates `likes` **and** `name` in the same write.
- A user creates an Activity carrying `is_active` or `updated_at`.

And:

- Every rule field name above appears in `Knect_Master_Schema.md` Part 1. Checked by eye, collection by collection.
- `npm run rules:deploy` succeeds and the Console reflects the new file.
- `npm test` still passes.
- `npm run lint` passes.
