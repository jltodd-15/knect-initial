**2 - The Architecture & Technical Details**

> **The model, in three lines.** By the time this runs, `firestore.rules` has been edited by `*3.2`, `*3.3`, and by 15.2, 16.1 and 17.1 adding to their own blocks. Nobody has read the whole file since. This ticket reads the whole file.

- **Target Database Collections:** all of them.
- **Data model changes:** **None** — and if the audit finds one is needed, that is a finding for Kyson, not a field to add.

**This ticket inherits no open brackets — it inherits three conditions to re-check.** All three questions were ruled on 2026-09-09; each ruling rests on something a later ticket could invalidate. **The audit's job is to confirm the ground has not moved, not to re-decide.**

| Ruling | From | What would invalidate it |
|---|---|---|
| 🔴 `Friends` `update` stays **owner-only**; acceptance is `acceptFriendRequest` | `*3.2` | **Project 5's edit pass adding a client-side acceptance path.** If one exists, this rule denies it, and the fix is a narrow counterparty clause: `friendId` may update, `status` only, to `"friend"` only, and only from `"request_sent"`. **Read Project 5 before signing this one off** |
| `Private_info`'s document ID is **pinned to `main`** | `*3.2` | **Decision Log F2's hot-path split.** If `tag_affinity_scores` / `location` / `geohash` moved to a second owner-only document, this rule denies it and the second path has to be added |
| `Votes.created_by` identifies who may cancel | `*3.3` | **17.1 not writing the field.** The create clause requires it, so if 17.1 omits it every vote creation is denied — a loud failure rather than a quiet one, but confirm it landed. Whether the cancel *button* was built is 17.2's and does not affect the rule |

**The audit, as a procedure.** Walk it in this order; each step is a different kind of mistake.

1. **Coverage.** List every collection and subcollection in `Knect_Master_Schema.md` Part 1. For each: a rule block exists, or the catch-all deny is the deliberate answer and that is written down. `Liked_Activities` fell through this exact gap once and it was found by reading the rules, not by anything failing.
2. **Field names.** Every string in a `hasOnly` list, every `resource.data.x`, against Part 1. A field that was renamed since `*3.2` produces a rule that silently denies.
3. **The trust boundary.** The list from START_HERE — `Events.status` (except `cancelled` by the owner), every vote result field, every chat preview field. For each, a deny case exists proving a client cannot write it.
4. **Admin-SDK bypass.** For every place a Cloud Function does something a client rule forbids, confirm the rule is still correct on its own merits. *A Function bypassing a broken rule is not a fixed rule* — that is the whole reason this ticket exists rather than the gaps being closed as they came up.
5. **UI-level enforcement.** `Free_Busy` visibility, device-local unread, and the block filter each put protection outside the server. Confirm all three are still written down as UI/device-level and that nothing in the app now describes them as enforced.
6. **Deny-case completeness.** Every `allow` in the file has at least one test that passes and one that fails. A rule with only allow cases has never been tested.
7. **The read.** Read the whole file top to bottom, out loud if it helps. It should be followable by someone who did not write it. **If it is not, that is the finding** — the file being checkable by Kyson is a requirement, not a nice-to-have.

**What the indexes need.** By now six or more tickets have added composite indexes to `firestore.indexes.json`. Confirm the file deploys (`firebase deploy --only firestore:indexes`) and that no query in the roadmap needs an index that is not in it. A missing composite fails at runtime with a create-index link — survivable in dev, a launch blocker in production.

**4 - Security and Scope**

**In scope**

- The seven-step audit above, with its findings written down.
- Re-checking the three inherited conditions above against the tickets that could have invalidated them, and recording the verdict for each.
- Filling deny-case gaps in the existing suite.
- Deploying rules and indexes.

**Explicitly out of scope**

- **Redesigning any rule that is correct.** The bar is "does this hold," not "would I write it this way now."
- **Adding schema fields.** A rule that needs a field the schema lacks is a finding for Kyson.
- **Storage rules.** Project 6 / D9 owns that file. If it does not exist by the time this runs, **that is a launch blocker to name, not scope to absorb.**
- **Performance work.** If the Messages `get()` turns out to cost more than `*3.3` measured, record the number and flag it.

**Security rules changes:** **Unknown until the audit runs, and that is the honest answer.** Everything decided is already in the file; this ticket finds what the schema learned since.

**Files allowlist**

```
firestore.rules
firestore.indexes.json
firestore-tests/**
```

**Stop and ask** rather than improvising if: the audit finds a gap whose fix needs a schema field; one of the three inherited conditions has moved — in particular if Project 5 added a client-side acceptance path; or a rule has to be loosened to make an existing ticket's acceptance criteria pass — **that is a ticket-versus-rules disagreement and it is Kyson's to resolve, not a rule to relax.**
