# 17.1. Vote Creation & Casting

**Status:** Not started
**Depends on:** 3 (the `/Events/` rule), 15.2 (messaging & listeners), 16.1 (proposals exist), 16.2 (the lifecycle a vote freezes), **D2 (Cloud Functions setup)** · **Blocks:** 17.2

> **Read `Knect_Project_16_Phase1_Decisions.md` first.** 17 inherits the Events lifecycle wholesale, and a vote's entire job is to interrupt it.
>
> **The one-line model:** a vote is a set of competing versions of one plan. The original is an option. Every alternative someone raises is another option. Whichever wins becomes the plan. A vote can also exist with no plan behind it at all — "where should we eat" — and that path shares the same document.

---

**1 - User Story**

As a User, I want to say "I can't make Thursday, what about Friday?" and have that become something the group taps once to answer, so that changing a plan doesn't turn into forty messages and nobody ends up guessing what everyone actually preferred.

---

**2 - The Architecture & Technical Details**

**Target Database Collections:** `Chats/{chatId}/Votes` (create, read, and update the two ballot maps) · `Events` (create candidates, read the original) · `Chats/{chatId}/Messages` (create, `message_type: "vote"`) · `Users/{uid}` (read, for voter names) · `Chats` (read, for `participants`)

**Data model changes:**

- ✏️ **`Votes.options` is no longer an Array of Strings.** An option is a whole competing version of the event, which a string can't carry. It becomes an array of objects:
  - `option_id` (String) — stable, generated at write. **`normal_votes` and `ranked_votes` reference these**, so they can never be regenerated or reordered.
  - `candidate_event_id` (String) — the `Events` document this option represents. Absent on a freeform vote.
  - `label` (String) — a human-readable summary of what this option *is* ("Friday 7pm — Bowling"). **This is not decoration.** Losing candidates get deleted at close (17.2), so the vote has to be able to render its own history after the events behind it are gone.
- ✏️ **`change_type` is renamed `vote_scope`**, with exactly two values: `"alternative"` (competing versions of an event; `linked_event_id` set) and `"open"` (freeform; no event). The old name described a field that never had a defined meaning.
- ✏️ **`vote_type` stays two values:** `"normal"` · `"ranked"`. Ranked requires at least 3 options, normal at least 2 — the validation `SocialDashboard.tsx:874` already does.
- ➕ **`resolves_at` (Timestamp) on `Votes`** — `created_at + 24h`, same window as a proposal. **Set once and never moved**, even when options are added.
- ➕ **`options_revision` (Integer)** — starts at 1, increments every time an option is added. Ballots record the revision they were cast against; that is how a stale ranked ballot is detected. See "Adding options" below.
- ➕ **`status` (String) on `Votes`** — `[DECISION: the value set. "open" | "closed" is the minimum and matches the prototype's 'active' | 'closed'. A third value for a vote the group abandoned or someone cancelled is probably wanted, but nothing has decided whether a vote can be cancelled at all — see the open item below.]`
- ✏️ **`Events.status` gains a fifth value: `"candidate"`.** A candidate is a real Events document that is not yet a plan. **The planner must filter it out and 16.2's sweep must never select it** — the sweep already queries `status == "proposed"`, so it is excluded by construction, but the planner's `shared_with array-contains` listener is not, and that is where a draft plan would otherwise appear on someone's calendar.
  > Recorded honestly: this puts a non-lifecycle state into a lifecycle enum. A candidate is not a stage a plan passes through — it is a plan that may never exist. Accepted because one field carrying all of it beats a parallel flag every query has to remember.
- ➕ **`vote_id` (String) on `Messages`** — exactly the gap `event_id` closed for proposals. A `message_type: "vote"` message with no pointer to its Vote can't render a ballot.
- **`normal_votes`** — Map keyed by uid, value is an `option_id`.
- **`ranked_votes`** — Map keyed by uid, value is `{ order: [option_id, ...], revision: Integer }`. **The prototype's `rankedVotes: [{ userId, order }]` array does not survive** — a uid-keyed map is what makes one-ballot-per-person structural instead of enforced in code.

**One vote per event, and it grows.** The first alternative *creates* the vote with two options: the original plan and the alternative. A third person raising a third alternative **adds an option to that same vote** — it does not open a second one. Parallel votes on one plan would need a rule for which one wins, and there isn't a good one.

**Creating a vote — three entry points, all of which already exist in the UI:**

1. **"Propose Change" on a proposal card.** `SocialDashboard.tsx:708` — renders only when `rsvps[me] === 'not_going'`. Saying no is what unlocks proposing an alternative, and that conditional is the intended social logic. Keep it.
2. **The ⋮ menu on a proposal card.** `SocialDashboard.tsx:638` → `handleEventMenu` → the event menu sheet. Any participant reaches the vote creator this way, not only someone who declined.
3. **The vote creator itself, freeform.** `renderVoteCreator` takes an arbitrary question and options with no event anywhere. That is the `"open"` scope.

**What creating an alternative actually writes** — one `WriteBatch`, same reasoning as 16.1's:

- A candidate `Events` document, `status: "candidate"`, copied from the original with the proposer's changes applied. **Everything not changed is carried over** — same `shared_with`, same `linked_chat_id`, same activity if the activity wasn't what changed.
- The `Votes` document (on first alternative) or an appended option (on later ones), with `options_revision` incremented.
- On first alternative only: a `message_type: "vote"` message carrying `vote_id`, and `Events.linked_vote_id` set on the original.

**How 16.2 knows an alternative is open — and it needs no new field.** 16.1 reserved a field for this. It turns out `Events.linked_vote_id` already is it: one vote per event means "an alternative is open" is exactly *`linked_vote_id` is set and that vote's `status` is `"open"`*.

`[DECISION: whether to keep it derived or denormalize it. Derived costs the sweep one extra read per event it evaluates, and can never disagree with itself. A denormalized boolean on the Event saves that read and introduces a field that can go stale. This closes Master Schema Q8 either way — 16.1's placeholder field is not needed.]`

**Casting a ballot:**

- A voter writes exactly one key — their own — in `normal_votes` or `ranked_votes`. Same shape as `rsvps`, so the rule is one line and dedup is structural.
- **Every participant writes the same document.** Firestore's ~1 write/sec per document ceiling is real when six people vote at once. Acceptable at MVP group sizes; it is written down here so it isn't discovered.
- Ballots are changeable while the vote is `"open"`.

**Adding options after voting has started — the hard part:**

- New options are allowed at any time until the vote closes. **The vote's `resolves_at` does not move.** A hard deadline is what keeps the plan it froze from being frozen indefinitely.
- **Ranked ballots go stale.** A ballot recorded against `options_revision: 2` when the vote is now at 4 ranked a shorter list, and treating the unranked newcomers as "last" is not what that person said — under IRV it materially changes the winner. Those voters get a re-rank prompt.
- **Pick-one ballots stand.** Your pick is still your pick; a new option doesn't change what you chose.
- `[DECISION: what the tally does with a ranked ballot that is still stale when the vote closes. Either treat unranked options as ranked last — which is the thing the re-rank prompt exists to avoid, just applied silently at the end — or drop that ballot from the ranked tally entirely, which discards a real preference because someone didn't see a notification. This is 17.2's rule but the data has to support it, so it belongs here.]`

**Known bugs and patterns to avoid:**

- **`utils/votingLogic.ts` is dead code and stays dead in this ticket.** Nothing imports it. **17.2 deletes it.** Do not wire it up.
- **`SocialDashboard.getRankedResults` (line 45) is a Borda count, not ranked choice** — `scores[optId] += (options.length - idx)`. It is what runs today, and it disagrees with the file named `calculateRankedChoiceResult`. **Neither survives.** 17.2 owns the tally; 17.1 renders whatever the vote document says.
- **No tallying in this ticket, at all.** Not even for display. Running results come from fields 17.2 maintains.
- **The prototype's `options: { id, text, votes[] }` shape** puts ballots inside the option. That is why its pick-one tally can double-count. Ballots live in the uid-keyed maps; options carry no votes.
- Every timestamp is a Firestore `Timestamp`, never `Date.now()`.
- **Do not rewrite the vote UI.** The vote card, the ranked card, `DraggableVoteList.tsx`, and the creator modal are roughly 500 lines of finished, working interface. This is a data-layer ticket.

**3 - The UI and Layout Requirements**

- **Loading / error states:** unchanged from the app-wide patterns. No new components.
- **Vote creator (exists):** the Normal/Ranked toggle, question field, dynamic options with "Add Option", and the prompt at 3+ options offering to switch to Ranked (`SocialDashboard.tsx:886`) all stay as built.
- **Alternative creator:** opening "Propose Change" prefills the create-event flow from the original event, so the proposer edits a copy rather than filling a blank form. Whatever they change is what makes it a different option.
- **Vote card — before you have voted:** options with their labels, no counts, no names. **You cannot see the running result until you have cast a ballot.** That is deliberate — a visible tally steers the next voter, and this is the cheapest way to keep the live read without the bandwagon.
- **Vote card — after you have voted:** counts per option **and who voted for what**, updating live. Plus how many of the invitees have voted at all.
- **Ranked ballot:** `DraggableVoteList` as built, drag to order, submit once.
- **Stale ranked ballot:** the card shows that options were added since you voted and offers a re-rank. `[DECISION: how loud this is — an inline banner on the card, or a push notification. Push is Project 20's and this is exactly the kind of thing it exists for, but it also means an interruption for something the person may not care about.]`
- **Closed vote:** the winner marked, final counts shown, no live buttons. 17.2 owns the state; 17.1 renders it.
- **On the proposal card, while a vote is open:** the event shows that it is being decided rather than sitting as a normal proposal. It cannot confirm while this is true, and the card should say so rather than looking stuck.

**4 - Security and Scope**

**In scope**

- The `Votes` document, its new `options` shape, `vote_scope`, `options_revision`, `resolves_at`, and `vote_id` on Messages.
- Creating a vote from all three entry points, as one batch.
- Candidate `Events` documents at `status: "candidate"`, and filtering them out of the planner.
- Casting and changing normal and ranked ballots.
- Adding options to an open vote, and the stale-ballot marker.
- Rendering the card, including results-after-you-vote.
- The rules below.

**Explicitly out of scope**

- **The tally. All of it.** No counting, no winner, no majority check, no elimination — **17.2**. 17.1 ships a vote that collects ballots and never concludes, and that is expected.
- Closing a vote, by any mechanism.
- Writing anything back to the original Event.
- Deleting losing candidates.
- Push notifications, including the re-rank prompt if that lands as a push — Project 20.
- Changing the Events lifecycle 16.2 defined.
- Vote history, past-votes browsing, or any analytics.

**Files this ticket may modify**

- `components/SocialDashboard.tsx` — the vote card, creator, and ballot writes
- `components/DraggableVoteList.tsx` — only if the ballot shape requires it
- New: a vote repository module (e.g. `services/voteRepository.ts`)
- `services/eventRepository.ts` — candidate creation only
- `types.ts` — `Vote`, `PollOption`, and `Message` shapes
- `firestore.rules` — the `Votes` block and the `Events` create rule
- `firestore.indexes.json`

Specifically **do not** touch `utils/votingLogic.ts` (17.2 deletes it), 16.2's Functions, or the RSVP path.

**Security rules changes**

- **Votes `create`:** requester is a participant of the parent chat.
- **Votes `read`:** participant of the parent chat.
- **Votes `update` — ballots:** a participant may write **only their own key** in `normal_votes` or `ranked_votes`, and only while `status == "open"`.
- **Votes `update` — options:** a participant may append to `options` and increment `options_revision`, while `status == "open"`. **Existing options may not be edited or removed** — `option_id` values are referenced by every ballot already cast.
- **Votes `update` — `status` and any result field:** **Admin SDK only. No client allowance at all.** This is the rule that makes the tally trustworthy; a client that can write `status` can declare its own winner.
- **Events `create`** already permits any authenticated user with `owner_id == request.auth.uid` (16.1). A candidate is an ordinary create under that rule — `[RESEARCH: confirm whether the rule should additionally require that a create with status "candidate" is made by a participant of the linked chat. As written, anyone can create a candidate for any event they can read, which is bounded but not tight.]`

**Composite indexes** — the planner listener now excludes candidates, which changes its index. Confirm against `firestore.indexes.json`.

**5 - Acceptance Criteria**

- [ ] Tapping NO on a proposal, then "Propose Change", opens the create flow prefilled from the original event.
- [ ] Submitting an alternative writes a candidate `Events` document, a `Votes` document with two options, a `message_type: "vote"` message carrying `vote_id`, and sets `linked_vote_id` on the original — all in one batch. Killing the network mid-write leaves none of them.
- [ ] The candidate Event has `status: "candidate"` and carries over every field the proposer did not change.
- [ ] A candidate Event appears on nobody's planner.
- [ ] A third alternative appends an option to the existing vote and increments `options_revision`. No second vote document is created.
- [ ] Adding an option does not change the vote's `resolves_at`.
- [ ] A ranked ballot records the `options_revision` it was cast against.
- [ ] After an option is added, everyone whose ranked ballot predates it sees the re-rank prompt; people who voted pick-one see nothing.
- [ ] Before you vote, the card shows no counts and no names.
- [ ] After you vote, the card shows counts and who voted for what, and updates on another device without a reload.
- [ ] A participant cannot write another user's key in `normal_votes` — denied by rules.
- [ ] A client cannot write `Votes.status` — denied by rules.
- [ ] A client cannot edit or remove an existing option — denied by rules.
- [ ] A non-participant cannot read the vote — denied by rules.
- [ ] A freeform vote (`vote_scope: "open"`) creates no candidate events and no `linked_event_id`.
- [ ] While a vote is open, the linked event's card says it is being decided.
- [ ] No tally logic exists anywhere in this ticket — a grep finds no counting of ballots in the client.
- [ ] `utils/votingLogic.ts` is still unimported.
