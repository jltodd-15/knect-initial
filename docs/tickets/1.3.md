# *1.3. Google & Apple Sign-In

**Status:** Not started. Reviewed 2026-09-03.
**Depends on:** 1.2, **0.2** (iOS setup — Apple sign-in cannot be built or verified without it)
**Blocks:** 1.4 (onboarding has to know both entry paths)

**Why this one is starred:** it gates App Review. Guideline 4.8 means shipping Google sign-in without an equivalent private option is a rejection, not a bug — and the fix arrives after a review cycle rather than after a build. It is also the only Project 1 ticket configuring providers outside the repo, where an error is invisible in the diff.

---

**Human setup required before this starts.** None of it can be done from the repo:

1. **A paid Apple Developer Program membership** (~$99/year). Sign in with Apple is a capability only paid accounts can enable. This is the only part of Project 1 that costs money.
2. **Register the debug *and* release SHA-1 signing fingerprints** on the Android app in the Firebase Console, then download the regenerated `google-services.json`. See section 2 — the committed one will not work.
3. **Enable the Google and Apple providers** in Firebase Console → Authentication.
4. **Turn off email enumeration protection** in Firebase Console → Authentication → Settings. The account-linking flow needs it off; section 2 explains what that costs.
5. **In the Apple Developer portal:** enable the Sign in with Apple capability on the App ID, create a Services ID, and generate a `.p8` private key — then enter the Services ID, Team ID, Key ID and key into Firebase's Apple provider. This is the fiddliest step in Project 1 and it is entirely manual.

**If this ticket is deferred, here is what it costs.** Deferring is reasonable — it is the only part of the app that needs a paid Apple account.

- **Nothing else in the roadmap breaks.** Projects 2 through 21, including the core loop of 15, 16 and 17, are Firestore, UI and logic work that never touch this ticket. Development continues normally.
- **No App Review problem while it is deferred.** Guideline 4.8 only applies once the app offers a third-party login at all; email/password alone is fine. **Google and Apple ship together or neither ships** — that is the rule to hold.

The expensive part of adding social sign-in later is not the wiring; it is a signup sequence that assumed everyone starts from a blank form. Build that shape now, and this ticket just passes an identity into it later.
- **Do not defer 0.2 along with it.** 0.2 needs no paid account, and it is what keeps the iOS side from silently rotting. See that ticket.

**1 - User Story**

As a user, I want to create my account and sign in with Google or Apple, so that I can get into Knect without inventing another password.

**2 - The Architecture & Technical Details**

> **The model, in three lines.** A Google or Apple sign-in produces the same thing an email/password sign-in produces — a Firebase Auth user with a UID — and everything downstream is identical. What differs is where the credential comes from: a native provider SDK returns a token, and `signInWithCredential` exchanges it for the Firebase session. **Nothing in this ticket writes to Firestore**; Project 2 still owns the `Users` document, and 1.4 still owns the sequence around it.

- **Target Authentication:** Firebase Auth — Google and Apple providers, alongside Email/Password.
- **Target Database Collection:** None.
- **Data model changes:** None. A social sign-in fills the same `Users` fields any other signup does.

**They ship together, and that's Apple's rule, not a preference.** App Store Guideline 4.8 requires that an app offering a third-party sign-in service also offer an equivalent option that limits data collection to name and email and lets the user keep their email private. Sign in with Apple qualifies. **Shipping Google alone gets the app rejected**, so these are one ticket rather than two.

**Two new native dependencies.** Google needs a native sign-in SDK; Apple needs Apple's own authentication services. Both are native modules, which means a rebuild rather than a reload. Pick the currently-maintained packages at implementation time rather than inheriting a name from an older doc — this is the layer where abandoned libraries are most common.

**🔴 `google-services.json` has to be regenerated.** Verified on the `auth` branch: the committed file at `android/app/google-services.json` has an **empty `oauth_client` array** and no `certificate_hash`. Google Sign-In reads its OAuth client from exactly that array, so it fails at **runtime** with a configuration error rather than at compile.

**Register the release fingerprint, not just debug.** Debug-only produces sign-in that works on every developer machine and fails for every real user — a bug that surfaces after launch rather than during testing.

**Account collision — prompt for the existing password and link the credentials.** A user who signed up with email/password and later taps Google with the same address hits `auth/account-exists-with-different-credential`. Firebase does not merge accounts on its own. The flow: recognize the collision, ask for the existing password, sign in with it, then `linkWithCredential` to attach the provider — so afterwards either method works.

**This needs email enumeration protection turned off, and that is a deliberate trade.** Firebase turns that protection on by default in newer projects, and it breaks the lookup this flow depends on — `fetchSignInMethodsForEmail` stops returning anything useful, and the collision error may not be thrown at all. It is off for Knect so the linking flow can work.

**What that costs, written down so nobody is surprised by it later:** with the protection off, Firebase's auth errors distinguish "this email has an account" from "it doesn't," so anyone can probe the API to learn whether an address is registered. That is the accepted price of not stranding users who signed up one way and came back another.

⚠️ **One consequence lands in 1.2, not here.** With the protection off, `sendPasswordResetEmail` throws `auth/user-not-found` for an unknown address instead of quietly succeeding. 1.2's rule still stands — the reset screen shows the same confirmation either way — but **the app now has to catch that error and show the confirmation anyway**, rather than getting the behavior free from Firebase. Flagged in 1.2 as well.

**What Apple hands back, and when.** Apple returns the user's name **only on the very first authorization** and never again, and the user may withhold it and may hide their real email behind a relay address. Two consequences worth writing down:

- Whatever arrives has to be captured on that first pass or it is gone. 1.4 collects a name when none arrives.
- A relay address is a real, working email. Do not validate it away, and do not assume the address in Firebase Auth is the one the user reads mail at.

**3 - The UI and Layout Requirements**

The buttons already exist — `App.tsx:144–151` renders Google and Apple in a `socialRow`, currently wired to `handleAuth` and disabled by 1.2. This ticket makes them real.

- **Idle.** Both buttons enabled. Apple's button has **branding requirements Apple enforces at review** — its own mark, approved wording, minimum size. The current generic pill (`App.tsx:223–224`) almost certainly does not meet them.
- **Submitting.** The provider sheet is system UI, but the app still needs a state for the moment after it dismisses and before Firebase resolves.
- **Cancelled.** ⚠️ **This is specifically about the Google/Apple provider sheet — the system popup that appears after tapping one of those two buttons.** If the user backs out of that sheet, taps outside it, or hits cancel, they changed their mind; that is not an error and must not render error text. **It has nothing to do with the email/password form.** A mistyped email or password on the normal sign-in form still shows an error — that is 1.2's wrong-password state, and it stays exactly as specified there. There is no password typed in the provider flow at all.
- **Provider error.** Distinct from a cancel and from an auth error — a misconfigured OAuth client, missing Play Services, a revoked token.
- **Collision.** A password prompt for the existing account, then linking. On success the user is signed in and both methods work from then on.
- **Apple on Android.** **Hide the Apple button on Android entirely.** No web flow, no disabled state. Guideline 4.8 is Apple's requirement for the iOS app; Android users get Google and email/password.
- **Success.** Identical to 1.2's — the tab tree, or 1.4's sequence for a new account.

**4 - Security and Scope**

**In scope**

- Google and Apple providers enabled; `google-services.json` regenerated with both SHA-1 fingerprints registered.
- The two native dependencies, installed and configured.
- `signInWithCredential` for both providers, wired to the two existing buttons.
- The collision flow: password prompt, then `linkWithCredential`.
- Hiding the Apple button on Android.
- Apple's button branding brought to spec.
- The UI states above, and sign-out covering a social session.

**Explicitly out of scope**

- **iOS project setup.** Ticket **0.2**, and a hard dependency for the Apple half.
- **Any other provider.** Facebook, phone, anonymous — none are in the roadmap.
- **Writing the `Users` document.** Project 2.
- **The onboarding sequence.** 1.4.
- **Account deletion**, including provider unlinking. Belongs to the unwritten settings ticket (D8), and it is an App Store requirement with no owner yet.
- **Security rules.** Project 3.

**Security rules changes:** No changes needed. This ticket touches no Firestore data.

**Security notes:**

- **Email enumeration protection is deliberately off**, and the trade is recorded in section 2. Do not turn it back on without also rewriting the collision flow — the two are tied together.
- **The provider token never leaves the device except into Firebase.** Exchange it for a Firebase credential and drop it. Do not persist it, and do not put it in the profile payload 1.4 hands to Project 2.
- **Do not treat a provider email as verified identity in any rule or query.** Apple relay addresses and Google addresses are both just strings on the Auth record; anything that matters keys on the UID, which is what the Master Schema already does.
- **The release SHA-1 is the one that gets forgotten.** See section 2.
- The regenerated `google-services.json` contains OAuth **client IDs**, which are public identifiers by design, not secrets. Nothing here adds a secret to the repo. The signing keystore stays out of it — `.gitignore:34–35` excludes `*.keystore` except `debug.keystore`, which is correct.

**Files allowlist — touch nothing else.**

```
App.tsx                              — the socialRow (:144–151) and its styles
android/app/google-services.json     — replaced wholesale with the regenerated file
package.json
android/app/build.gradle             — only if a provider SDK requires it
ios/                                 — only what a provider SDK requires; 0.2 owns the rest
```

Plus whatever auth module 1.2 created — the provider calls belong beside the email/password ones, not in `App.tsx`.

**Stop and ask** rather than improvising if: 0.2 has not landed; enumeration protection is still on; `google-services.json` has not been regenerated; or Google sign-in fails with a configuration error, which almost always means a fingerprint is missing rather than that the code is wrong.

**5 - Acceptance Criteria**

Verified by one method: **a physical Android device and a physical iOS device, with real Google and Apple accounts.**

- `android/app/google-services.json` contains a non-empty `oauth_client` array.
- A new user can create an account with Google and lands in the app.
- A returning Google user signs in without seeing the onboarding sequence again.
- A new user can create an account with Apple on iOS and lands in the app.
- An Apple sign-up where the user withholds their name still completes, and 1.4's sequence asks for one.
- An Apple sign-up using Hide My Email completes, and the relay address is accepted.
- The Apple button does not appear at all on Android.
- Dismissing either provider sheet returns to an idle login screen **with no error text**.
- A mistyped password on the email/password form still shows its error — the cancel behavior above did not suppress it.
- A user who signed up with email/password and then taps Google with the same address is asked for their existing password, and afterwards can sign in with either method.
- Signing out of a social session returns to the login screen, and reopening the app does not restore it.
- The Apple button meets Apple's branding requirements.
- A release-signed build signs in with Google on a device that has never run a debug build.
- `npm run lint` passes.
- `npm test` passes.
