# 18.1. Planner Shell

**1 - User Story**
As a User, I want to see my day and my month at a glance, with plans from friends clearly told apart from my own, so that I know when I'm free without scrolling through empty space.

**2 - The Architecture & Technical Details**
- **Target collections:** `Events` (read only, through 16.4's app-wide listener and repository). No new listener.
- **Data model changes:** None.
- **Views:** Day (default) and Month, switched through the "Day ▾" dropdown. Week is **not** a full view. It is a swipeable 7-day strip under the header. Swiping changes week; tapping a day opens it in Day view.
- **Header** collapses on scroll. Hour rows are **48pt**.
- **All-day row** sits above the hour grid. It shows `is_allday: true` events and any event that spans past midnight on the day shown.
- **Multi-day** is an event whose `end_time` is on a later calendar day than `event_time`. **Ruled (Kyson, 2026-10-09):** a *timed* multi-day event (e.g. Fri 6 PM to Sun 2 PM) renders as a **timed block on its first day** (6 PM to midnight) and **last day** (midnight to 2 PM), and as an **all-day-row chip on every day in between**, labelled with its span ("Day 2 of 3"). An *all-day* multi-day event is a chip on every day.
- **Status filter:** render `proposed`, `confirmed`, `cancelled` and `expired`. **Never render `candidate`** (those are vote options, 17.2).
- **Listener bound:** reuse 16.4's date bound. The month view must not open a second listener. If the bound doesn't cover a scrolled-to month, do a one-time `get()` for that month, not a listener.
- **Time zones:** stored as UTC `Timestamp`. Display in device local time. Convert at the boundary; no epoch-millisecond numbers in documents.
- **Keep:** the now-line, the cluster-overlap layout, and the `participants.length > 0` proposal rule (`EventPlanner.tsx:111`). Rebuild the visuals on 4.2's tokens. Do not rewrite the overlap math.

**3 - The UI and Layout Requirements** (per D-1.x)
- Loading: skeleton hour grid, no spinner over the whole tab.
- Empty: empty day shows the grid plus a single "Tap a time to add something" hint.
- Error: inline banner with retry; cached events stay visible.
- Success: **confirmed and personal events are solid** in the 700 shade of their `color` with white text. **Proposed events are a dashed outline** in their color. Events that don't count as busy look the same on the planner; "Free" shows only in the event's detail view. Cancelled and expired are muted with a label. (Kyson, 2026-10-09)

**4 - Security and Scope**
- **In scope:** Day and Month views, week strip, collapsing header, all-day row, multi-day rendering, status rendering, visual rebuild on tokens.
- **Out of scope:** creating or editing (18.2/18.3), friends' busy (18.4), recurrence, external calendars (19), notifications (20).
- **Security rules changes:** None needed.

**5 - Acceptance Criteria**
- [ ] Day and Month views match D-1.1 to D-1.4; the week strip swipes by week.
- [ ] A `candidate` event never appears in any view.
- [ ] An all-day event shows only in the all-day row; a 3-day event shows on all three days.
- [ ] Opening Month view does not add an Events listener (check the listener count).
- [ ] Cancelled and expired events render muted and labelled, never as live plans.

# 18.2. Create/Edit Sheet

**1 - User Story**
As a User, I want creating a plan to take one screen, with a sensible time already filled in, so that a normal one-evening plan takes seconds, while all-day and multi-day plans are still possible.

**2 - The Architecture & Technical Details**
- **Target collections:** `Events` (create, and update for personal events), through 16.2's repository. **No direct Firestore calls from the screen.**
- **Data model changes:** None. Uses `event_time`, `end_time`, `is_allday`, `event_title`, `color`, `activity_id` (optional), `location_text`, `shared_with`.
- **One sheet replaces the 4-step `CreateEventModal`.** Default: **one day, start rounded up to the next half hour, 1 hour long**. When opened from the planner, the tapped slot is the default. When opened from an activity, the activity's suggested duration is the default if it has one.
- **All-day toggle:** hides times; stores `is_allday: true`, `event_time` = start of first day, `end_time` = end of last day (local time, converted to UTC). `[DECISION: confirm the all-day end convention, inclusive end of day vs. exclusive midnight of the next day. Pick one and write it into the Master Schema; 19's sync will need it.]`
- **Multi-day:** an "Ends" row with its own day. Hidden until tapped. `[DECISION: is "Ends on a different day" a separate toggle, or just tapping the end date?]`
- **Busy never blocks sending (Kyson asked, 2026-10-09).** If the chosen time overlaps an invited friend's busy time, the sheet shows a heads-up naming who and when ("Marcus is busy 8:00 – 9:30"). The Send button stays the same. The friend can still answer yes, no, or suggest a time. This is a client-side check against 18.4's already-loaded Free_Busy data, with no new reads and no new fields. Design: `flows/CreateConflict`.
- **Proposal vs personal:** decided only by whether friends are picked (`participants.length > 0`). **A time is required for a proposal** (16.1). **Ruled (Kyson, 2026-10-09): all-day proposals are allowed** (a weekend trip, an all-day hike). An all-day day range counts as "having a time". `resolves_at = min(created_at + 24h, event_time)` still works, with `event_time` = start of the first day.
- **"Counts as busy" switch (new, Kyson 2026-10-09).** Every event gets a busy on/off control in the sheet, so a holiday or a "Mom's birthday" all-day marker doesn't block your day.
  - **Defaults:** timed events → **busy**. All-day events → **not busy**. The user flips it either way. [Likely] these defaults are right for the common case; the weekend trip is the case where the user flips all-day to busy.
  - **Field:** this needs a new Events field (working name `counts_as_busy`, Boolean). **18 does not add it.** Schema and rules never go in a UI ticket, so it goes into the Events schema ticket (16.1) as an amendment, and 18.2 waits on it.
  - **Ruled (Kyson, 2026-10-09): on a shared event the sender's setting applies to everyone automatically.** One Boolean on the Event, no per-person override for MVP. Per-person override is a possible later addition (a map keyed by uid, same pattern as `rsvps`).
  - **Busy only counts for people going.** A friend's Free_Busy block for a shared event exists only while their RSVP is `going` (16.8 already ties the block to confirmation and late `going`).
- **Itineraries inside a multi-day event (weekend trip with a hike Saturday at 9 AM):** **deferred, not in 18.** `[DECISION: confirm deferral.]` Reason: nesting needs a parent/child link between Events (e.g. `parent_event_id`), its own rules, and its own UI. It's a project, not a sub-ticket. **For MVP, the trip is one event and the hike is a separate event on the same day.** Busy time is a union of intervals, so overlapping busy blocks just merge. Nothing double-counts, and nothing breaks if itineraries come later.
- **Editing:** personal events only. Proposed and confirmed group events open read-only, with "Suggest a new time" (18.5) instead of edit.
- **Delete:** personal events only. Group events use 16.8's cancel.

**3 - The UI and Layout Requirements** (per D-2.x)
- Loading: Save button shows progress; sheet stays open.
- Error: inline under the field that failed (end before start, no time on a proposal); write errors as a banner with retry.
- Success: sheet closes, planner scrolls to the new event.
- Locked state: group events show why they can't be edited.

**4 - Security and Scope**
- **In scope:** the single sheet, all-day, multi-day, edit and delete of personal events, retiring the 4-step modal.
- **Out of scope:** planner gestures (18.3), friends' busy (18.4), changing a group event's time (18.5), recurrence, reminders.
- **Security rules changes:** None needed (16.1's `Events` block covers create and owner update). **Verify** that 16.1's rules reject a non-owner updating `event_time`; if not, flag to Project 3, don't patch here.

**5 - Acceptance Criteria**
- [ ] Creating a one-evening personal event takes one screen and one tap on Save.
- [ ] An all-day 3-day event saves with `is_allday: true` and renders on all three days in 18.1.
- [ ] Saving a proposal with no time is blocked in the UI.
- [ ] End before start cannot be saved.
- [ ] A proposed or confirmed group event cannot be edited from the sheet.
- [ ] `CreateEventModal`'s 4-step flow is gone and nothing imports it.

# *18.4. Friends' Busy Overlay

**2 - The Architecture & Technical Details**

- **Data model changes:** None.
- **Who:** only friends picked in the create sheet, or friends in the current chat. **Never a general "all my friends" overlay** (read cost).
- **Read bound:** one `get()` per picked friend for the visible day (or range, for multi-day). **Not a listener.** Cached for the session.
- **Visibility is UI-gated today** (rules are permissive, B22). This ticket must not widen who can read Free_Busy. Show only your friends'.
- **Display:** your own events render in their colors. **Ruled (Kyson, 2026-10-09):** friends' busy time is a **neutral hatch with the friend's initials**, not red. It carries no titles or details: Free_Busy has none, and the overlay must not imply it does.

  - A time change on a confirmed event (18.5) must move its Free_Busy block too.
  - 18.4 only reads, so it's unaffected beyond the label: "Busy" rather than "Busy with Knect plans".

**3 - The UI and Layout Requirements** (per D-4.x)

- Error: overlay hidden, small "Couldn't load friends' times".

**4 - Security and Scope**
- **In scope:** the overlay in the create sheet and the planner's draft mode, read-bounded.
- **Out of scope:** writing Free_Busy (16.8), tightening Free_Busy rules (Project 3, flagged), "find a time that works" suggestions.

# 18.5. Suggest a New Time

**1 - User Story**
As someone invited to a plan, when the time doesn't work for me, I want to suggest another time that the group votes on, so that we can move the plan without someone screenshotting a calendar into the chat.

**2 - The Architecture & Technical Details**
- **Target collections:** none directly. Calls 17.2's "create a vote" repository function with `vote_scope: "alternative"` and the suggested time as a candidate Event.
- **Data model changes:** None.
- **Entry points:** the proposed event's detail view, the long-press on a locked event (18.3), and the chat card after RSVPing "not going" (17.1's unlock).
- **Picking the suggested time** reuses 18.2's sheet in a "suggest" mode: time only, no title, no friends, Free_Busy overlay on (18.4).
- **Proposed and confirmed events (ruled, Kyson 2026-10-09).** Plans change even after everyone says yes, so a confirmed event can get a new-time vote too. **This reverses the current rule** (17.1: alternatives only while `proposed`; 16.1: confirmed events don't move, owner cancels and re-proposes). It's a **Project 17 change** (vote scope, close conditions, applying the winner), and 18.5's confirmed-event entry point waits on it.
  - **The fallback rule:** the event **stays confirmed at its current time** unless the new time wins. Nobody votes → keep. "Keep current time" wins → keep. That means **"Keep current time" must be an explicit option in every alternative vote**, not implied.
  - **Why the old lock existed still matters:** it protected `resolves_at`. A confirmed event has already resolved, so changing its `event_time` doesn't touch the sweep. [Likely] safe, but the 17 session must re-check this against 16.7.
  - **Ruled (Kyson, 2026-10-09): RSVPs carry over, and people can switch.** Carry-over already matches the Master Schema ("`rsvps` are preserved when a vote changes the plan").
  - ⚠️ **Switching conflicts with Q7 (Master Schema / `*3.3`).** On a resolved event, an existing `going` or `not_going` is **frozen**; only `pending` can be set, once. So after a confirmed event moves, nobody who already answered could change their answer under today's rule. `[DECISION for the Project 17 change + *3.3: how to reopen RSVPs once after a time change. Option, Likely: the winner write-back (Function) sets a per-uid "may re-answer" flag for every participant; the rule allows one change to your own key while your flag is set, and the same write must clear it. That keeps "set once" with no time math in rules. Alternative: reset everyone to pending, rejected above because it can un-confirm a plan.]`
  - **Who can start it: already decided in 17.1.** Any participant, through the ⋮ menu on the plan card. "Propose Change" also appears after you RSVP `not_going`. Keep both for confirmed events.
  - ⚠️ **Gap in 17.1: the vote deadline.** A vote's `resolves_at` is `created_at + 24h` and never moves. For a confirmed event happening in less than 24 hours, the vote would close after the plan already happened. `[DECISION for the Project 17 change: use the same formula as proposals, resolves_at = min(created_at + 24h, earliest of the original and candidate start times). Likely, and consistent with 16.1.]`
- **Overlaps on the planner (18.1):** overlapping events split the width side by side (keep the prototype's cluster math). Proposed events are dashed outlines, confirmed and personal are solid. A proposal that overlaps something you're `going` to gets an "Overlaps <title>" tag. These are rendering rules only; no data.
- **Planner display:** a proposed event with an open vote shows a "vote open" marker (D-5.4). Candidates stay hidden (18.1).
- **Depends on 17.2 existing.** If 17.2 isn't built, this sub-ticket waits; do not build a local vote stand-in.

**3 - The UI and Layout Requirements** (per D-5.x)
- Loading: the sheet's Send shows progress.
- Error: banner with retry; the suggestion is kept.
- Success: closes, chat shows the vote card (17.5).
- Blocked: on a cancelled or expired event, don't offer the action.

**4 - Security and Scope**
- **In scope:** the entry points, the suggest-mode sheet, calling 17.2, the planner marker.
- **Out of scope:** the vote card itself (17.5), tallying (17.6), closing (17.7), applying the winner (17.8).
- **Security rules changes:** None (17.1 owns Votes rules).

**5 - Acceptance Criteria**
- [ ] Suggesting a time on a proposed event creates one vote through 17.2 and no direct Firestore writes from the screen.
- [ ] The action is offered on proposed and confirmed events, and not on cancelled or expired ones.
- [ ] Every vote it creates includes "Keep current time" as an option.
- [ ] If nobody votes, a confirmed event stays confirmed at its original time.
- [ ] The candidate Event never appears on anyone's planner.
