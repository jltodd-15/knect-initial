# *3.3. Rules — Chats, Messages, Votes & Events

**Status:** Not started. Drafted 2026-09-09.
**Depends on:** `*3.2`
**Blocks:** 15.2, 16.1, 16.2, 17.1, 17.2. **Every Events read and write in the app is denied until this lands.**

---

**1 - Goals**

- `/Calendars/` becomes `/Events/`, which is the single change that unblocks 16.1, 16.2 and all of 17.
- `Messages` and `Votes` stop being `allow read, write` for any chat participant — today that permits overwriting someone else's ballot, forging a vote result, and deleting anyone's message.
- The trust boundary gets written down in rule form: **anything a client can write, a client can lie about.** Event `status` (except `cancelled` by the owner), every vote result field, and every chat preview field become Admin-SDK-only by having no client clause at all.
- Every one of those denials is a test.

---

**2 - The Architecture & Technical Details**

> **The model, in three lines.** Chat-scoped documents are secured by membership in the parent chat, which costs a `get()` on `Chats/{chatId}`; Events are secured by membership in `shared_with`, which does not. Both use the same shape for user-owned state — a map keyed by UID, where a participant may write only their own key. Everything that decides an outcome (event `status`, vote results, chat previews) is written by the Admin SDK and has no client clause anywhere.

- **Target Database Collections:** `Chats`, `Chats/{chatId}/Messages`, `Chats/{chatId}/Votes`, `Events`.
- **Data model changes:** ➕ **one field.** `Votes.created_by` (String — the UID of whoever opened the vote), written at creation by 17.1. Everything else named below is already in the Master Schema. **Ruled 2026-09-09** — see the cancel clause. It is the only schema addition in all of Project 3.

**`Chats/{chatId}`** — the current rule lets any participant modify any field, including removing someone else from `participants`, which contradicts 15.1's self-only leave.

```
match /Chats/{chatId} {
  allow create: if signedIn()
    && request.auth.uid in request.resource.data.participants
    && request.resource.data.keys().hasOnly([
         'participants', 'participant_hash', 'chat_origin', 'chat_name'
       ]);

  allow read: if signedIn() && request.auth.uid in resource.data.participants;

  allow update: if signedIn()
    && request.auth.uid in resource.data.participants
    && changedKeys().hasOnly(['chat_name', 'participants'])
    && (!('participants' in changedKeys()) || onlyRemovedSelf());

  // no delete clause
}

function onlyRemovedSelf() {
  return resource.data.participants
           .removeAll(request.resource.data.participants)
           .hasOnly([request.auth.uid]);
}
```

`onlyRemovedSelf()` says: **anyone dropped from the list must be you.** Additions are unconstrained, which is what 15.1's add-member needs; removals are limited to leaving. The four preview and identity fields — `participant_hash`, `chat_origin`, `recent_message`, `recent_message_timestamp`, `recent_message_sender_id` — are absent from the update allowlist, so no client can touch them. `chat_origin` never changes after creation and `participant_hash` is recomputed only inside the Cloud Function.

> **No `allow delete`, and that is inherited rather than decided.** The published rule has none either, so chats cannot be deleted by a client today and still cannot after this ticket. 15.1's skeleton raised whether that is intended and nothing has answered it. Not this ticket's to answer — recorded so it is a known state rather than an oversight.

**`Chats/{chatId}/Messages/{messageId}`**

```
match /Chats/{chatId}/Messages/{messageId} {
  function chatParticipants() {
    return get(/databases/$(database)/documents/Chats/$(chatId)).data.participants;
  }

  allow read: if signedIn() && request.auth.uid in chatParticipants();

  allow create: if signedIn()
    && request.auth.uid in chatParticipants()
    && request.resource.data.sender_id == request.auth.uid
    && request.resource.data.text.size() <= 2000
    && request.resource.data.message_type in ['text', 'activity', 'event_proposal', 'vote']
    && request.resource.data.keys().hasOnly([
         'sender_id', 'text', 'timestamp', 'message_type',
         'activity_id', 'event_title', 'event_id', 'vote_id'
       ]);

  allow update: if signedIn()
    && request.auth.uid == resource.data.sender_id
    && changedKeys().hasOnly(['text', 'deleted_at'])
    && request.resource.data.text == ''
    && request.resource.data.deleted_at == request.time;

  // no delete clause
}
```

- **The 2,000-character cap is enforced here, not only in the input field.** A cap enforced only in the UI is not enforced.
- **`deleted_at` is absent from the create allowlist**, so a message cannot be born a tombstone.
- **The update clause permits exactly one shape** — clear the text, stamp the time — which is what makes deleting a message a tombstone rather than a removal. There is no `allow delete` because there is no delete.
- **`"system"` is not in the `message_type` list.** The enum has five values and nothing writes `"system"` yet; 15.2's create rule permits only what something actually writes. When a ticket writes system messages it widens this list.
- ⚠️ **Values only, not shape.** Nothing here stops a malformed proposal or vote message pointing at nothing. It renders as a broken card rather than being rejected. Known and accepted.
- **The parent `get()` is kept rather than denormalizing `participants` onto every message.** *[Likely] Firestore caches identical `get()` calls within a single rule evaluation, so a 25-message page costs about one extra read rather than 25.* **This ticket is the first chance to verify that — measure it in the emulator and write down the real number.**

**🔴 Blocking is not enforced by any rule, and this ticket closes that item rather than leaving it open.**

Round 9 ruled that Project 3 owned the durable fix. **Ruled 2026-09-09: it stays receive-side for MVP.** The reasoning, so it is a posture and not a shortcut:

- `blocked_users` lives in `Private_info`, which only its owner can read. **No client and no security rule can check whether the *recipient* blocked the sender** without a new, readable block record — which is a schema addition, a Project 5 write, and a billed `get()` on every message sent.
- 15.2's receive-side filter is the actual protection, and the only person who can bypass a receive-side filter is the person it protects. This is how iMessage behaves.
- *[Likely] Apple Guideline 1.2's "ability to block abusive users" is satisfied by that filter* — a reviewer tests whether a blocked user's messages stop appearing, and they do.

**The accepted cost, written down:** a blocked user's messages are still created, stored and delivered before being filtered out. **Blocking is UI/device-level and must never be described as enforced.** Same class as `Free_Busy` visibility and device-local unread — three deliberate decisions to put protection outside the server where the cheap version is good enough, not three unrelated shortcuts. **Revisit if reporting (13.3) needs a server-side record of who blocked whom.**

**`Chats/{chatId}/Votes/{voteId}`** — a rule already exists and is `allow read, write` for any chat participant, which permits overwriting someone else's ballot and forging a result.

```
match /Chats/{chatId}/Votes/{voteId} {
  function inChat() {
    return signedIn() && request.auth.uid
      in get(/databases/$(database)/documents/Chats/$(chatId)).data.participants;
  }

  allow read: if inChat();

  allow create: if inChat()
    && request.resource.data.status == 'open'
    && request.resource.data.options_revision == 1
    && request.resource.data.created_by == request.auth.uid;

  // A participant may write their own ballot, and only their own, while the vote is open.
  allow update: if inChat()
    && resource.data.status == 'open'
    && changedKeys().hasOnly(['normal_votes'])
    && request.resource.data.normal_votes.diff(resource.data.normal_votes)
         .affectedKeys().hasOnly([request.auth.uid]);

  allow update: if inChat()
    && resource.data.status == 'open'
    && changedKeys().hasOnly(['ranked_votes'])
    && request.resource.data.ranked_votes.diff(resource.data.ranked_votes)
         .affectedKeys().hasOnly([request.auth.uid]);

  // Options may be appended. Never edited, never removed.
  allow update: if inChat()
    && resource.data.status == 'open'
    && changedKeys().hasOnly(['options', 'options_revision'])
    && request.resource.data.options.size() == resource.data.options.size() + 1
    && request.resource.data.options[0:resource.data.options.size()] == resource.data.options
    && request.resource.data.options_revision == resource.data.options_revision + 1;

  // no delete clause
}
```

**`status: "closed"`, `winning_option_id`, `closed_at`, `close_reason` and `final_counts` have no client clause at all.** That single omission is what makes every result in the app trustworthy, and it is the most important line in this ticket. 17.2's tally writes them with the Admin SDK.

> ⚠️ **The append-only check uses list slicing (`options[0:n]`) to prove the existing options were not touched.** *[Likely] Firestore rules support range indexing on lists.* **This is the single most likely thing in this ticket to not compile.** If it does not, the fallback is to check `options.size()` growth plus `options_revision` and accept that an append could also rewrite an earlier option — which is materially weaker, because every `option_id` is already referenced by cast ballots. **Try the slice first; if it fails, stop and ask rather than silently taking the weaker version.**

**`created_by` is a new field, and it exists because the cancel rule cannot be written without it.** Master Schema Part 2 item 4 says `status` may go to `"cancelled"` by "the vote's creator only" — and the `Votes` document had no field naming its creator. **Ruled 2026-09-09: add `created_by`.**

The alternative was reading the creator off the linked event's `owner_id`, and it fails twice. **The person who opens a vote is usually not the event's owner** — 16.1's proposer owns the event, but any chat participant may raise an alternative, and raising the first alternative is what creates the vote. And **a freeform vote (`vote_scope: "open"`) has no linked event at all**, so there would be nothing to read.

The create clause above requires `created_by == request.auth.uid`, so a vote cannot be created attributed to someone else. The cancel clause is then three lines:

```
  // status → cancelled, by whoever opened the vote, only while it is open.
  allow update: if inChat()
    && request.auth.uid == resource.data.created_by
    && changedKeys().hasOnly(['status'])
    && request.resource.data.status == 'cancelled'
    && resource.data.status == 'open';
```

> **Q9's separate question is still 17.2's and is not answered here: whether the cancel *button* gets built for MVP.** The rule is written now regardless, because it is additive and it means 17.2 needs no rules change either way. **It is also safe with nothing behind it** — 16.2's sweep skips an event only while its `linked_vote_id` points at a vote whose status is `"open"`, so a cancelled vote un-skips the event automatically. Nothing is left stranded by a cancel that no server logic follows up on.
>
> ⚠️ **`close_reason` still has no value for a cancellation, and this does not settle that.** A cancelled vote has no winner and no `final_counts`. If 17.2 builds the path it either adds a fourth `close_reason` value or a cancelled vote carries none. **17.2 decides; do not invent one.**

**`Events/{eventId}`** — replaces the `Calendars` block entirely.

```
match /Events/{eventId} {
  allow create: if signedIn()
    && request.resource.data.owner_id == request.auth.uid;

  allow read: if signedIn() && request.auth.uid in resource.data.shared_with;

  // RSVPs — your own key only, and the three windows from Q7.
  allow update: if signedIn()
    && request.auth.uid in resource.data.shared_with
    && changedKeys().hasOnly(['rsvps'])
    && request.resource.data.rsvps.diff(resource.data.rsvps)
         .affectedKeys().hasOnly([request.auth.uid])
    && resource.data.event_time > request.time
    && (
         resource.data.status == 'proposed'
         || (request.auth.uid in resource.data.rsvps
             && resource.data.rsvps[request.auth.uid] == 'pending')
       );

  // shared_with — any participant of the linked chat.
  allow update: if signedIn()
    && changedKeys().hasOnly(['shared_with'])
    && request.auth.uid in get(
         /databases/$(database)/documents/Chats/$(resource.data.linked_chat_id)
       ).data.participants;

  // status → cancelled, by the owner, from a non-terminal state.
  allow update: if signedIn()
    && request.auth.uid == resource.data.owner_id
    && changedKeys().hasOnly(['status'])
    && request.resource.data.status == 'cancelled'
    && resource.data.status in ['proposed', 'confirmed'];

  // no delete clause
}
```

**The RSVP clause is the awkward one, and the whole of Q7 is in that last condition.** Read it as three windows:

| Window | What the clause does |
|---|---|
| `event_time` has passed | `event_time > request.time` is false → **denied**, every time |
| `status == "proposed"`, event still ahead | First branch is true → **write and change your key freely** |
| Resolved, event still ahead | Only passes while your key holds `"pending"` → **answer once, then frozen** |

The third window is self-limiting: the moment you write `"going"`, your key is no longer `"pending"` and the same clause denies the next attempt. That is the "set it once" behavior with no extra state.

> **`resolves_at` can never go stale, and now neither can this rule** — 16.1 disables drag and resize on proposed events specifically so `event_time` cannot move while a proposal is open. Anyone who re-enables dragging there breaks the sweep **and** this clause, which reads `event_time`.

**Three things about the Events block that are decided but worth seeing before they surprise someone:**

1. **`read` requires membership in `shared_with`, with no owner fallback.** The published `Calendars` rule had `owner_id == uid || uid in shared_with`; the schema's decided text dropped the owner half. An owner who is somehow not in their own `shared_with` cannot read their own event. `shared_with` mirrors the chat's `participants` and the proposer is always a participant, so this should never happen — **there is a deny case for it below, and if that behavior is wrong it is a one-line change, not a redesign.**
2. **The `shared_with` clause costs a `get()` on the linked chat**, and it errors — and therefore denies — if `linked_chat_id` is absent. A `"candidate"` event created by 17.1 needs one for this clause to work at all. **Flag for 17.1.**
3. **`status: "confirmed"` and `"expired"` have no client clause, and neither does applying a winning alternative.** Admin SDK only. Losing candidates are deleted by the Admin SDK too — **do not add a client `allow delete` for them.** An event is cancelled, never deleted.

**Known bugs to avoid:** none in this path. Verified at `8493a36` — no application code reads or writes Firestore, and `grep -rniE "calendars"` returns only `CreateEventModal.tsx:360` and `:508`, both local render-step names with no Firestore behind them.

**4 - Security and Scope**

**In scope**

- The four rule blocks above.
- Deleting the `Calendars` block outright.
- A test file per collection, with the deny cases carrying most of the weight.
- Measuring the real read cost of the Messages parent `get()` in the emulator, and writing the number down.
- One deploy after the suite is green.

**Explicitly out of scope**

- **Everything in `*3.2`'s blocks.** Do not revisit the user tree or `Activities`.
- **The cancel *button*, and `close_reason`'s fourth value.** The rule is written; whether the UI exists is 17.2's, and so is what `close_reason` holds on a cancelled vote.
- **The `Friends` acceptance clause.** `*3.2`'s bracket, carried to `*3.4`.
- **Composite indexes.** 15.2, 16.1 and 16.2 each add their own to the file `*3.1` created. **In particular, do not add the `status` + `resolves_at` or `shared_with array-contains` indexes here** — a rules ticket that also writes indexes is two jobs.
- **Storage rules.** Project 6 / D9.
- **Cloud Functions.** Nothing in this ticket runs server-side. Rules are what constrain clients; the Admin SDK ignores all of it by design.
- **Any application code.**

**Security rules changes:** **This ticket is the security rules change.** `Chats` update is narrowed to `chat_name` plus self-removal; `Messages` gains a sender check, a length cap, a type check, a field allowlist and a tombstone-only update; `Votes` is rewritten from `allow read, write` to per-key ballot writes and append-only options; `Calendars` is deleted and `Events` is created with the three-window RSVP clause. Five categories of field become Admin-SDK-only.

**Security notes:**

1. 🔴 **This is the ticket where a mistake is invisible and expensive.** Every one of the four blocks currently permits something it should not, and none of it is observable from the app, because no code touches Firestore yet. The test suite is the only thing standing between a wrong rule here and finding out at 17.2.
2. **Blocking is not enforced by a rule and this ticket does not add one.** Ruled above. Do not describe it as enforced anywhere.
3. **`Free_Busy` read stays open to any signed-in user** — `*3.2`'s decision, restated because 16.2 writes those blocks from an Event and it is easy to assume the visibility tightened along with it. It did not.

**Files allowlist — touch nothing else.**

**Stop and ask** rather than improvising if: the `options[0:n]` slice does not compile; a rule needs a field that is not in the Master Schema; the RSVP clause cannot express all three windows in one clause and looks like it needs two; or the `shared_with` `get()` needs a fallback for events with no `linked_chat_id`.

**5 - Acceptance Criteria**

Verified by one method: **`npm run test:rules`.**

Allow cases:

- A user creates a `Chats` document including their own UID, reads it, renames it, adds a participant, and removes **themselves**.
- A participant creates a `"text"` message with `sender_id` equal to their own UID and 2,000 characters exactly, and reads the thread.
- A participant tombstones **their own** message — `text` to `""`, `deleted_at` set — and the document survives.
- A participant creates a vote with `status: "open"`, `options_revision: 1` and `created_by` equal to their own UID, writes their own key into `normal_votes`, then into `ranked_votes`, then appends a third option and increments `options_revision` to 2.
- The vote's `created_by` sets `status` to `"cancelled"` while it is `"open"`.
- An owner creates an Event with `owner_id` equal to their own UID; a member of `shared_with` reads it.
- A `shared_with` member writes their own `rsvps` key on a `"proposed"` event, then changes it.
- On a `"confirmed"` event with `event_time` in the future, a member whose key holds `"pending"` sets it to `"going"` — **once**.
- A chat participant updates `shared_with` on an event whose `linked_chat_id` points at their chat.
- The owner sets `status` to `"cancelled"` from `"proposed"`, and from `"confirmed"`.

Deny cases — this is where the ticket earns its star:

- A non-participant reads a `Chats` document, a message, or a vote.
- A participant removes **someone else** from `participants`.
- A participant writes `recent_message`, `recent_message_timestamp`, `recent_message_sender_id`, `participant_hash`, or `chat_origin`.
- A participant creates a message with `sender_id` set to **someone else's** UID.
- A message of 2,001 characters.
- A message with `message_type: "system"`, or any value outside the four.
- A message created carrying `deleted_at`.
- A participant tombstones **someone else's** message; **deletes** any message; or edits a message's `text` to anything other than `""`.
- A participant overwrites **another user's** key in `normal_votes` or in `ranked_votes`.
- A participant writes a ballot on a vote whose `status` is `"closed"`.
- A participant writes `winning_option_id`, `closed_at`, `close_reason`, `final_counts`, or `status: "closed"`.
- A participant creates a vote with `created_by` set to **someone else's** UID.
- A participant who is **not** `created_by` sets `status` to `"cancelled"`.
- `created_by` sets `status` to `"cancelled"` on a vote that is already `"closed"` or `"cancelled"`.
- A participant **edits** an existing option's `label`, **removes** an option, or appends one **without** incrementing `options_revision`.
- A user creates an Event with `owner_id` set to someone else's UID.
- A user **not** in `shared_with` reads the event — **including the `owner_id` holder when they are absent from `shared_with`.** Comment this test with the note from §2 so nobody reads it as a bug.
- A member writes **another member's** `rsvps` key.
- A member writes their own `rsvps` key on an event whose `event_time` has **passed** — `"proposed"` and `"confirmed"` both.
- A member whose key holds `"going"` changes it on a `"confirmed"` event with `event_time` still ahead.
- A client writes `status: "confirmed"`, `status: "expired"`, or `confirmed_participants`.
- The owner sets `status` to `"cancelled"` from `"expired"` or from `"cancelled"`.
- Any client **deletes** an Event.
- Any read or write to `/Calendars/{id}` — **the old collection must be dead**, not merely unused.

And:

- The number of billed reads for a 25-message page under the parent `get()` is measured and written into the ticket's §2 as a verified figure, replacing the `[Likely]`.
- Every rule field name appears in `Knect_Master_Schema.md` Part 1.
- `npm run rules:deploy` succeeds.
- `npm test` still passes and `npm run lint` passes.
