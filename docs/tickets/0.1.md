**2 - The Architecture & Technical Details**

- **Target Database Collection:** None. This ticket touches no Firestore data.
- **Data model changes:** None. One TypeScript type is restored (`UserStatus.timestamp`) — that's a local type, not a schema change.

Five fixes, in this order. The first is what lets you see the rest fail properly.

**Fix 1 — `index.js` registers the wrong component.**

`ErrorBoundary` is written, wraps `App` inside a `Root` component, and then `Root` is never used:

```js
const Root = () => (<ErrorBoundary><App /></ErrorBoundary>);
AppRegistry.registerComponent(appName, () => App);   // ← should be Root
```

One line. Do it first so everything below fails visibly instead of red-screening.

**Fix 2 — `StatusService.ts` throws at module load.**

Two bugs in the constructor's path. Between them they take down the Planner tab *and* the status composer, since both import this module.

- Line 84: `private save() { storage.setItem(...) }` — the module imports `localStorage`, not `storage`. `storage` is undefined. ReferenceError on every write path.
- `timestamp` is read and written at lines 27, 37, 52, 67 and 77, but it was commented out of the `UserStatus` type (`types.ts:6`, behind a `// TODO: reenable this`). At runtime `new Date(undefined).getDate()` is `NaN`, so the day-rollover check always fires and wipes the status.

Fix the undefined reference. For `timestamp`, **restore the field to the `UserStatus` type** rather than stripping the five usages. The expiry logic is wanted — it's just typed wrong, and `StatusComposer.tsx:54` already tells the user *"Your status will stay on for the next hour."* Stripping it would make the app lie harder, not less. What the field should ultimately become — the schema's `Users.status_expires_at`, with a real TTL — is **D5's** job (the user-status ticket, ruled in at Decision Log O8). Restore it as-is here.

> **Correction applied 2026-09-05:** this ticket previously pointed at "Project 15.3." **No such ticket exists** — 15 has 15.1 and 15.2 only, and user status was given its own light ticket, **D5**, on 2026-08-25.

**One behavior note the async conversion creates here.** Once `loadStatus()` is properly awaited it becomes async, and the constructor cannot await it. So on first mount `getStatus()` returns the hardcoded default until the load resolves and `notify()` fires. **That is correct and wants no loading flag** — the only two consumers are `StatusComposer.tsx:15`, which subscribes and re-renders on notify, and `EventPlanner.tsx:135`, which only calls `clearStatus()`. Do not make the constructor block, and do not add a loading gate to the composer.

**Fix 3 — delete `geminiService.ts`, replace the Discover data source with a local mock.**

`services/geminiService.ts:4` constructs `new GoogleGenAI({ apiKey: process.env.API_KEY })` at module scope. `.env.local` names the variable `GEMINI_API_KEY`, and there's no dotenv babel plugin anyway, so it's `undefined` either way and the constructor throws at import — taking the Discover tab with it.

- Delete `services/geminiService.ts`, `@google/genai` from `devDependencies`, `.env.local`, and `.env.example`.
- `getSmartSchedulingSuggestions` has zero call sites. Nothing to replace.
- `getDiscoveryFeed` has exactly one caller: `DiscoveryFeed.tsx:5`.

Replace it with a local mock file — roughly five activities, **shaped to the `Activities` master schema**, not to the current `DiscoveryItem` type. Write it as `services/mockActivities.ts` so the file it replaces stays obvious.

Two reasons for schema-shaped rather than a copy of the old shape: the Discover tab stays visually testable while you work on other tickets, and the mock doubles as a shape reference for Project 11.

**The shape, pinned against the Master Schema so the mock doesn't seed a wrong one:**

```
name              String
description       String
cost              String  — exactly one of "Free" | "$" | "$$" | "$$$"
source            String  — "manual_diy" on every mock row
tags              Array of Strings
pictures          Array of Strings — placeholder URLs
is_location_based Boolean — false on every mock row
click_count       Integer — 0
likes             Integer — 0
created_at        Timestamp
```

Three deliberate omissions, each with a reason — **do not fill them in:**

- **`location` and `geohash`** are omitted, which is why `is_location_based` is `false` on every row. Nothing in the app captures a user's location yet (that's D4), so a mock claiming to be location-based would be pointing at a distance calculation that has nothing to compare against.
- **`category`** is omitted because it is **open — Master Schema Q4**. Its absence here is not a ruling against it.
- **`creator_id`** is omitted because the schema puts it on `source == "user_generated"` rows only, and these are seeded.

**The `tags` strings on these rows are placeholder and bind nothing.** The real vocabulary contract — that `Activities.tags` and 1.4's 35 interest strings have to be one vocabulary, or 13.2's `tag_affinity_scores` silently start empty for every user — is **still unowned** (Round 10 §11). Project 9 writes the real tags. Keep the mock content obviously placeholder; the activity list is being rewritten in Project 9 and shouldn't be pre-empted here.

**Do not write a Firestore query.** That is Project 11.

**Fix 4 — the `localStorage` naming bug, and the async conversion it caused.**

The root cause of most of the above, and the largest piece of this ticket.

`utils/storage.ts:4` exports an **async** API under the name of the browser's **synchronous** one:

```ts
export const localStorage = createAsyncStorage("user_data");
```

Consumers were then written against the browser API — `const data = localStorage.getItem(KEY); JSON.parse(data)`. A Promise is always truthy, so `JSON.parse` stringifies it to `"[object Promise]"` and throws. Unconditional, not a race. The codebase already disagrees with itself about this: `ProfilePage.tsx:28` awaits correctly, `ChatService.ts:14` doesn't.

- **Rename the export** to something that can't be mistaken for a sync API — `userStore` unless you'd rather it were called something else. The rename is the point: while the name stays, this bug keeps getting written into new code. The import itself is fine — `createAsyncStorage` is a real export of `@react-native-async-storage/async-storage` v3, verified against the published package.
- **`ChatService.ts` has 14 unawaited call sites** — 6 `getItem` (lines 14, 21, 83, 106, 122, 129) which throw, and 8 `setItem` (58, 78, 98, 112, 119, 125, 155, 166) which are fire-and-forget. There is no `async`, `await`, `.then` or `Promise` anywhere in the file. *(Re-verified 2026-09-05. `Knect_Codebase_Audit.md` §5 says 15 — that count is wrong; 14 is correct.)*
- All 10 `ChatService` methods become `async`. That propagates to the **11 call sites** in `SocialDashboard.tsx`, `EventPlanner.tsx` (140–141) and `CreateEventModal.tsx`, which become async too.
- `StatusService.ts:22` — same bug.
- `ProfilePage.tsx:76` — `setItem` unawaited, while line 28 awaits correctly. Fix 76.
- `utils/storage.ts:16` — `keyChain.userLogin` calls `Keychain.setGenericPassword` without awaiting inside a try/catch, so the catch can never see a rejection. Same class, one line.

> ⚠️ **Flag, not a blocker: `keyChain` may not survive.** 1.2 carries an open `[DECISION: delete `keyChain` (`utils/storage.ts:13–21`) or leave it dormant?]`. This ticket lands first and fixes the missing `await` regardless. If 1.2 later deletes the block, one line of this work is thrown away — which is cheaper than shipping a `catch` that can't catch. **Do not resolve that decision here.**

**Fix 5 — `ProfilePage.tsx`'s loader never runs.**

Lines 26–37 are `useEffect(() => { (async () => { ... }) }, [])` — the async function is defined and thrown away. The trailing `()` is missing, so the saved profile is never read and `handleSaveProfile` (line 73) is write-only.

Add the `()`. Every field is guarded (`if (data.name) setName(data.name)`) and the state has hardcoded defaults, so nothing changes visually until something has actually been saved.

**Known bug to avoid:** `deleteConversation` (line 115) issues two independent unsequenced writes at 119 and 125. Once these are properly awaited, sequence them — an interruption between the two orphans the message blob permanently.

**The storage backend stays AsyncStorage.** This ticket makes the existing code honest about being async; it does not change where data lives. Firestore is Projects 15.1 and 15.2.

**3 - The UI and Layout Requirements**

No new UI, no layout changes, no visual design decisions. Four state notes, because the async conversion touches them:

- **Loading state:** async call sites need loading handling they don't currently have. Use whatever indicators already exist on those screens. Do not build new ones — the shared components in Appendix B cover that, and wiring them up is a later ticket.
- **Empty state:** the Discover tab renders the mock array rather than an empty state. The conversation list's existing empty state stays as-is.
- **Error state:** the main visible change in this ticket. A throw anywhere in the tree now renders the `ErrorBoundary` fallback instead of crashing the app. Whatever that fallback currently looks like is fine — do not redesign it.
- **Success state:** no visual change. Chat messages and statuses persist across navigation, which they currently don't.
