# 11\. Discover tab Frontend fetch

### `Discover Tab Frontend Fetch & Infinite Scroll`

**`1. User Story`**

* `As a User, I want to have a personalized and curateable Discover feed that gives me the best activities for me and my friends. I want to be able to curate it for the type of activity I am looking for at the moment, or be able to scroll through it generally when I don’t know what specifically I want to do.`

**`2. The Architecture & Technical Details`**

* **`Target Database:`** `Collection: Activities`  
* **`Pagination Logic:`** `We don’t want to incur high fetching costs from Firebase. To best do this, it would be best to have the first 5 activities loaded for every filter. If they are adjusting filters, allow a couple seconds before fetching so that we don’t have to fetch a whole new batch for every filter they change one after the other. This makes it so they can change multiple filters without us incurring high costs.`  
  	`Using React Native’s onEndReached prop, load 5 activity cards at a time. It should trigger this when there are 2 cards from the bottom of the list. Once they start scrolling it is likely that they will continue looking, but if they haven’t yet, we can likely get away with only 5 loading, in case they tap away.`  
* **`Location Filtering:`** `We will need to adjust the filters that are there already (as will be outlined in project 13), one of which will certainly be the location filter. We will have the filter to allow for a 10, 15(default), and 25 mile radius. That means that the activities loading must be within one of those categories.`  
  `Important note: Because Firebase doesn’t allow “OR” queries, we will need to make a second query that also adds in activities without locations attached.`  
  `E.g.`  
  `Query A: Fetch location based activities within the user’s 15-mile radius using the geohashes.`  
  `Query B: Fetch all activities where(“is_location_based”, “==”, false).`  
* **`Multiple Filters issue:`** `Unfortunately, Firebase can only do one inequality operator per query. Meaning that you can’t look for both a place under “$$$” and less than 15 miles away at the same time.`   
  `There are 2 solutions to this:`  
  * `We can create Composite Indexes for every single combination of filters possible. This requires a ton of work ahead of time, but reduces cost. The issue is if we don’t have a filter combination premade, nothing will show up. Also, if we add activities we will need to manually put them in every time, severely limiting scale and growth.`  
  * `We can have the app do it client-side. This would have us use Firebase for the biggest potential filter (like category or location), then use React Native to hide activities that don’t fit the other filters. We can also use caches through Firestore to limit reads and improve speed. This looks like: get({ source: 'default' }), for it to prioritize caches then the database, I believe.`   
* **`The "Like" Button Logic:`** `When a user likes an activity, we need to have them be able to update that activity’s data (as outlined in project 8, Engagement tracking). We will also need to add that activity ID to that User’s liked_activities.`   
* **`The “Shuffle”:`** `Client-Side Feed Assembly Logic`  
  * `Step 1: Fetch Array A (Local): Execute the geo-query for activities where is_location_based == true within the active radius.`  
  * `Step 2: Fetch Array B (At-Home/Anywhere): Execute a standard query for a sample of activities where is_location_based == false.`  
  * `Step 3: The Interleave Merge: Don’t append Array B to the end of Array A. Instead, write a client-side utility function that injects one item from Array B into Array A every 4 activity cards.`  
  * `Step 4: The Fallback State: If Array A returns 0 results (even after a radius expansion), render Array B in its entirety. The user should never hit a completely empty screen.`  
* **`Repeats (optional):`** `We don’t want to flood the user with repeat ideas. This will hopefully be addressed easier when we have a bigger activities database (through User Generated Content and API connections). For now though, we want to give them the chance to see new things more often than old ones. Because this is a bit different from Instagram or other social media platforms, repetition, I don’t believe, is quite as bad. They will be able to save what they like, but also some ideas might be appealing at different times.` 

  `For this, I would like to have a timer or something that makes it so that they only see repeat activities after a week of previously seeing them. This might be difficult or unnecessary at this point, so if it is a hindrance, it is optional.`

**`3. UI & Layout Requirements`**

* **`The Feed Display:`** `This is a vertically scrolling screen with every card slightly smaller than the user’s screen. This makes the user interested in what comes next, meaning they will be more likely to scroll.`  
  [`Previously explained in project 8.`]()  
* **`Initial Loading State:`** `Before anything loads, we should have a skeleton structure of the card that is grayed out. This doesn’t need any identifying features other than the split of the picture being slightly more gray than the text.`   
* **`Liking:`** `When someone likes an activity, the heart should automatically go from a black/white outline, to a filled in red heart, no outline. This should happen whether the database registers it or not, but if there is an error adding it to the database, it should go away immediately. If this can be an animation easily, that would be great, but don’t add it if it would take too much time. This action is updated in the database under liked_activities for the user and likes for the activity.`  
* **`The Empty/End States:`** `If a user has no internet connection or is unable to connect to the database for whatever reason, there should be an error similar to the profile picture error state, “If they lose internet during this stage there should be a symbol of a circle with an “!” in it and the statement, “Sorry, We couldn’t load anything right now”.` 

  `If they reach the end  of the activities page, there should be a message that says, “Sorry, we don’t have any more activities that fit these filters. Please try again with a new combination.”`

**`4. Acceptance Criteria`**

- [ ] `When you open the activities tab, there should be cards that load.`  
- [ ] `Those cards should have correctly filled out information, and any missing information should lead to the activity not showing up.`  
- [ ] `When scrolling down, more activities should load beneath the original ones.`  
- [ ] `When liking an activity, it successfully updates the UI and the database.`  
- [ ] `The UI should be clear and include error states when activities don’t load or run out.`
