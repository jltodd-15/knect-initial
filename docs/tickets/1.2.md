**2 - The Architecture & Technical Details**

> **The model, in three lines.** Firebase Auth owns identity and nothing else — the UID and the email/password credential. **Nothing in this ticket writes to Firestore**; the `Users` document keyed by that UID belongs to Project 2, and the field list lives there and only there. Session persistence is `@react-native-firebase/auth`'s own, read back through `onAuthStateChanged` rather than through a value the app stores itself.

- **Target Authentication:** Firebase Auth, **Email/Password provider**, enabled in the Firebase Console. Google and Apple sign-in are in for MVP but belong to `*1.3`.
- **Target Database Collection:** None.
- **Data model changes:** None.

**This ticket no longer creates the user document.** That was decided in the roadmap edit pass (Decision Log R12): Project 1 owns Auth — provider config, persistence, error states — and **Project 2 owns the Firestore document and is the single source for the field list.** The original ticket's "Fields to Write on Creation" list is deleted here, not copied into Project 2's.

Two reasons that mattered. Projects 1 and 2 were specifying *different* documents while being the two tickets most likely to be built first. And the original list wrote `email` onto the `Users` document — which every authenticated user can read — while the schema had already moved it into the owner-only `Private_info` subcollection.

**The five flows.**

1. **Sign in.** `signInWithEmailAndPassword` with the email and password from the login form. There is no such call anywhere in the repo today — `authenticateUser()` only ever read `auth.currentUser` to check whether a session already existed, so the credentials a user typed were never sent to Firebase. Sign-in is not buggy; it is unimplemented.
2. **Sign up.** `createUserWithEmailAndPassword`, using the credentials handed up from `CreateProfilePage` — see the credential handoff below.
3. **Sign out.** `signOut`. `handleLogout` (`App.tsx:66–68`) currently only flips local state.
4. **Session restore.** An `onAuthStateChanged` subscription decides whether the app renders the login screen or the tab tree, replacing the `isAuth` boolean as the source of truth (`App.tsx:19`, gating at `:95`). **Unsubscribe on unmount** — the app-wide listener convention from 15.2 applies to this one too, and it is the first listener in the codebase.
5. **Password reset.** In for MVP. `sendPasswordResetEmail` — Firebase sends and hosts both the reset email and the reset page, so there is no backend and no template work here beyond what the Console offers. **This is greenfield UI**: the login screen has no forgot-password affordance today (`App.tsx:108–152`).

⚠️ **One thing about the reset flow that comes from `*1.3`.** Email enumeration protection is turned off on this Firebase project, because `*1.3`'s account-linking flow needs it off. With it off, `sendPasswordResetEmail` throws `auth/user-not-found` for an address that has no account, instead of quietly succeeding. **The rule below still stands — the screen shows the same confirmation either way — but the app has to catch that error and show the confirmation anyway** rather than getting the behavior for free from Firebase.

**The credential handoff.** The email and password are typed into `CreateProfilePage` (`:23–24`) and never leave it — `onComplete` carries only `{ name, role, interests, avatar }` (`:206`). **`CreateProfilePage` passes the credentials up through `onComplete`.**

Keep the edit to that screen as small as it can be — **this ticket touches the `onComplete` payload and its `Props` type, and nothing else in that file.** The step machine, the validation rules and the sequence are all broken in their own ways and they belong to **1.4**, which owns the screen. Two tickets editing one file back to back is fine as long as the line between them is this narrow.

On the App side, `handleProfileComplete` (`App.tsx:60–64`) takes no arguments today and drops the payload on the floor; it also passes `App.tsx`'s own `email`/`password` state (`:27–28`), which is bound to the **sign-in** form and is empty on the sign-up path. Both halves go: it receives the payload and uses the credentials in it.

> **On editing hand-written files:** earlier tickets warned against touching certain files because Jonathan might have uncommitted work in them. That no longer applies — he has signed off on Claude Code making the edits and is helping run the process. Where a ticket says leave a file alone, it is a scope boundary now, not a warning about stepping on someone's work.

**Persistence, stated concretely.** The original ticket said auth state persistence is "usually the default in mobile frameworks." That is a guess written into a spec. With `@react-native-firebase/auth` the native SDKs persist the session themselves and `onAuthStateChanged` fires with the restored user on cold start — **no AsyncStorage wiring, no `getReactNativePersistence`, and nothing for the app to store.** That distinction mattered when the SDK was undecided; J1 decided it.

**The password policy is enforced server-side, and the client mirrors it.** ✅ **RULED 2026-09-11 — the rule is: 8 to 24 characters, at least one capital letter, at least one number.** It is configured in **Firebase Console → Authentication → Settings → Password policy**, which means Firebase rejects a non-conforming password on its own whether or not the client checks first.

That has a consequence worth stating: **a server-side policy produces its own error code.** When `createUserWithEmailAndPassword` is rejected by the policy, RNFirebase surfaces `auth/password-does-not-meet-requirements` *(**[Likely]** — confirm the exact code on a device the first time it fires, and map whatever actually arrives)*. **Map it to the same copy as the client-side rule**, so a policy the client somehow missed still produces a readable message instead of raw error text.

⚠️ **The client regex and the Console policy must say the same thing.** They are two enforcement points for one rule and they will drift — someone tightens the Console and nobody touches the regex, and the app starts rejecting nothing while Firebase rejects everything. If they ever disagree, **the Console is authoritative** and the regex is the bug.

**Known bugs in this exact code path.**

- **`App.tsx:42–52` — the fake 5-second delay and the Promise-truthiness bug.** `handleAuth` wraps everything in `setTimeout(..., 5000)`, a mock delay inherited from the AI Studio baseline. Inside it, `if (FirebaseModule.authenticateUser() == true)` compares a Promise to `true`, which is always false, so the else branch runs every time — and then puts the Promise object itself into error state (`App.tsx:49`) to be rendered inside a `<Text>` (`:127`). The delay goes; the real loading state is the duration of the actual call.
- **`App.tsx:44` — `knect_session` is written and never read.** Nothing reads it, and `handleLogout` never removes it. The `useEffect` that used to restore it was deleted since the AI Studio commit and is now just `setIsDarkMode(false)` (`App.tsx:36–38`). **Delete the write.** With the SDK persisting the session, a second app-managed session flag is a second source of truth that can disagree with the first.
- **`utils/storage.ts:13–21` — `keyChain.userLogin` would store the user's plaintext password in the Keychain.** It is imported at `App.tsx:14` and `CreateProfilePage.tsx:7` and **called from nowhere**. ✅ **RULED 2026-09-11: delete it**, along with its two imports. RNFirebase persists the session natively, and with a password-reset flow in scope there is no reason this app ever holds a password after the sign-in call returns. A dead credential-storage helper sitting in the signup screen's imports is an invitation. **Note for 0.1:** that ticket fixes this block's missing `await` and lands first; one line of its work is discarded here, which is the cheaper outcome.

**Error states, and what they map from.** RNFirebase rejects with structured auth error codes; the UI needs a mapping from those codes to copy, not raw error text rendered into a `<Text>`. ✅ **RULED 2026-09-11 — the copy:**

| Condition | Copy |
|---|---|
| Malformed email | "Email is badly formatted" |
| Password fails the rule (client check, or `auth/password-does-not-meet-requirements`) | "Password must be at least 8 characters and include a capital letter and a number" |
| Wrong password, or no account for that address | **"Email or password are incorrect"** |
| `auth/email-already-in-use` | "Email already in use" |
| Reset email requested | "Password reset email sent" |
| Network failure | Distinct from every message above — see section 3 |

⚠️ **The wrong-password and no-such-account cases share one message deliberately.** Distinguishing them tells a stranger which addresses are registered, which is the same enumeration leak the reset flow is written to avoid. This is why the acceptance criterion below asks for *a credential error distinct from the network error*, rather than a wrong-password message specifically.

⚠️ **The password rule is a signup rule and belongs on the signup path.** Do not validate password shape before a **sign-in** call — an account created before the policy existed may not satisfy it, and length-checking someone's login attempt tells them about the rule rather than about their password. 1.4 owns enforcement at signup; this ticket maps Firebase's rejection to copy.

**Ruled out of this ticket, explicitly: email verification is not required for MVP.** No verification send, no verified-only gating, no "check your inbox" state. Recorded so it isn't quietly added back by an implementer who expects it.

**3 - The UI and Layout Requirements**

The login screen exists (`App.tsx:95–156`) and its layout is not being redesigned. The original ticket's "The screen should be set up already" was a note to Jonathan rather than a spec, and it left every state unwritten. These are the states:

- **Idle.** The form as it renders today — email, password, SIGN IN, CREATE ACCOUNT.
- **Submitting.** The button already swaps its label to `PROCESSING...` and disables (`App.tsx:130–131`). Keep the treatment; drive it from the real call instead of the 5-second timer.
- **Auth error, per field.** The screen has one shared error line (`App.tsx:126–128`) that prefixes everything with `Unable to sign in:`. A **malformed** email renders against the email field. A **credential failure** — wrong password or no such account — renders as the shared "Email or password are incorrect," because by design it cannot be attributed to one field. This is the biggest visible change in the ticket.
- **Network error.** Distinct from an auth rejection, and currently indistinguishable — an unreachable Firebase and a wrong password both land in the same string. A user who is offline should be told that, not told their credentials are wrong.
- **Forgot password.** New. An affordance on the login screen, a prompt for the email address, and a confirmation state after `sendPasswordResetEmail` resolves. **Confirm the same way whether or not the address has an account** — telling a stranger which emails are registered is an account-enumeration leak, and Firebase's own newer behavior is to not distinguish.
- **Success.** The tab tree renders. **Land the user wherever `App.tsx:18` already defaults** (`AppTab.PLANNER`) — do not build routing. The five-tab decision (Planner, Discover, Search, Circle, Profile) and the React Navigation migration are both real and both belong to other tickets; `types.ts:136–141` still has four tabs and the switch at `App.tsx:162–185` is hand-rolled. Leave all of it alone.
- **Restoring.** New state, and the one most likely to be skipped. On cold start there is a moment before `onAuthStateChanged` reports, and neither the login screen nor the tab tree is the right answer during it — showing the login form to an already-signed-in user for half a second is the bug this state exists to prevent.

**The Google and Apple buttons** (`App.tsx:144–151`) are wired to `handleAuth`, the email/password handler. Both providers are in for MVP, and `*1.3` implements them. **Until then, disable the two buttons** rather than leaving them attempting a password login. Do not delete them — `*1.3` wants them exactly where they are.

- Disabling the Google and Apple buttons pending `*1.3`.

**Explicitly out of scope**

- **Creating the `Users` document, and the field list that used to live in this ticket.** Project 2, per R12. This ticket must not write a single Firestore field.
- **Email verification.** Out for MVP — decided, not an oversight.
- **Google and Apple sign-in.** `*1.3`.
- **The onboarding sequence, `CreateProfilePage`'s step machine, and its password validation.** 1.4 owns all of it, including enforcing the password rule at signup. This ticket's edit to that file is the `onComplete` payload and nothing else.
- **Profile pictures** — Project 6. `CreateProfilePage.tsx:51–63` cycles four hardcoded Unsplash URLs and says so in its own comment. Leave it.
- **React Navigation, and the fifth tab.** Both real, both other tickets.

- **iOS.** Ticket 0.2 owns it; see also `*1.3`.
- **Security rules** — Project 3.

**Security rules changes:** No changes needed. This ticket touches no Firestore data.

**Security notes:**

- **Do not distinguish registered from unregistered addresses** — in the reset flow, or in the credential error. Both are the same leak.
- The old `createUserData(email, password)` call (`App.tsx:61`) hit a Kotlin signature of `createUserData(displayName, email, promise)` (`FirebaseModule.kt:74`), so position 2 — the `email` field — received the **password**. Had that write ever succeeded, a plaintext password would have been written into a Firestore field readable by every authenticated user. It dies with 1.1's deletion. It is recorded here because it is the exact reason the document write belongs to Project 2 and this ticket writes nothing: credentials and profile fields should never travel through the same call. **The credential handoff added above must not turn into a credential-plus-profile payload that some later ticket writes wholesale.**
- `keyChain.userLogin` is deleted here, not left dormant. Do not reintroduce it.

**Files allowlist — touch nothing else.**

```
App.tsx
components/CreateProfilePage.tsx   — the `Props.onComplete` type and the call at :206 ONLY
utils/storage.ts                   — the keyChain block at :13–21, deleted
package.json                       — only if a new dependency proves necessary; stop and ask first
```

A new module for the auth calls is fine and expected — put it wherever Project 0's conventions say services live.

**Stop and ask** rather than improvising if: a fix appears to require editing a file not on this list; the edit to `CreateProfilePage` starts growing past the payload; or `onAuthStateChanged` seems to need a value stored outside Firebase to work. That last one usually means a second source of truth is being reintroduced.

**5 - Acceptance Criteria**

Verified by one method: **a real Android device or emulator, against a Firebase project with the Email/Password provider enabled and the password policy set to 8–24 characters with a capital and a number.**

- A user can register a new account with the email and password typed on the create-account screen, and Firebase Auth accepts the credentials.
- A user can sign in with those credentials and lands on the tab tree.
- A user can sign out and is returned to the login screen.
- Closing the app entirely and reopening it lands the user on the tab tree without re-entering credentials.
- After signing out, closing and reopening the app lands on the login screen.
- Requesting a password reset for a registered address delivers Firebase's reset email, and the new password works on the next sign-in.
- Requesting a reset for an unregistered address shows the **same** confirmation as a registered one.
- An invalid email shows "Email is badly formatted" against the email field, not in a shared line prefixed `Unable to sign in:`.
- A wrong password on a real account, and a sign-in attempt against an address with no account, show **the same** message: "Email or password are incorrect".
- **A password rejected by Firebase's own policy shows the password-rule copy, not a raw error code.** Verify by temporarily bypassing the client-side check.
- With the device offline, a sign-in attempt shows a network error distinct from every auth error above.
- Signing up with an address that already has an account shows "Email already in use".
- `grep -rn "keyChain" .` returns nothing outside `.git/`.
- The Google and Apple buttons are visibly disabled and do nothing.
- Sign-in resolves in the time the network takes. `grep -n "setTimeout" App.tsx` returns nothing in the auth path.
- `grep -rn "knect_session" .` returns nothing outside `.git/`.
- No Firestore document is created by any path in this ticket — verified in the Firebase Console after a successful registration.
- `npm run lint` passes.
- `npm test` passes.
