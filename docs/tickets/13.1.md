# 13.1. Discover Tab Search bar & Algorithm

### `Discover Search Bar & Algorithm`

**`1. User Story`**

* `As a User, I want to be able to find activity ideas relevant to me and my interests, quickly and with as little interference to the experience as possible. I want to be able to scroll through ideas when I don’t have specific constraints, but also be able to search for more precise categories of ideas.`

**`2. The Architecture & Technical Details`**

* **`Search:`** `The search function should start in Firebase by reducing the activity pool to all activities within a 25 mile radius.`   
  `After that we will need to filter from within the app, due to Firebase’s limitations (that’s what my research told me about Firebase at least?). We will allow users to filter by two methods, the search bar and a filter.`   
  `The Filter: As of now I think it will be best to simply have a filter for cost. This would be a simple dropdown with the options of, “Free”, “$”, “$$”, “$$$”, and “--”(or null, so that if they aren’t sure and are just scrolling they get all options).`  
  `The Search bar: Use a 150ms debounce. The search should use a Levenshtein score to create a fuzzy search on the name and tags. I am not an expert on this, so if it is too hard to implement, we can do something simpler. But from what I understand, this will allow us to get a score from 0.0 (exact match) to 1.0 (no match), and can give results from that. It also said we can use the Fuse.js library to make it. Let me know when you get here though.`  
  `The Levenshtein score should act as a hard filter that returns results with a score below 0.5. After that the Heuristic scoring formula should define the order of activities.`  
* **`The Base Heuristic Scoring Formula:`** `The algorithm to decide the order of scrolling will use a points system to balance 3-4 things.`  
  `1. Popularity score: Any like/save is worth 10 points, any click is worth 1. Popularity scores would be capped at 400, in order to not overload the Discover feed with high liked activities only.`  
  `2. Proximity Score: This score is capped at 300 points. Every mile away from the user, the score drops 12 points. At the absolute edge of the User, it would get 0 points. If the activity has no location, they should get a score of 150. This keeps them balanced and reliant mostly on the other scores for high placements.`   
  `3. Tag Affinity score: This is similar to the popularity score, but specific to the user. It is also capped at 300 points. This uses the tags in an activity and compares them to the tags a user has in their clicked activities, their liked activities, their user profile, and their planned activities. Each click of an activity is 1 point, like/save is 5 points, tags/interests in their profile, and actual planned activities are 10 points.`  
  `4. Cold start score: If the activity is newer it won’t have many likes or clicks. That means we need to give it a boost. Any activity that was added less than 72 hours ago should get a +300 point boost. This should last until those 72 hours are up. I added a created_at timestamp to the schema in the activities dataset for this.`   
* **`The Randomness factor:`** `We don’t want to create echo chambers after users like or save a couple of activities with the same tags. Eventually we want to add a randomness factor that adds completely random activities after every 5th activity or so. This can wait until after the MVP though.`

**`3. UI & Layout Requirements`**

* **`The Search Bar & Filter:`** `The search bar should be at the top of the Discover tab, under the “Discover” header. It should have a magnifying glass and be rounded. It should extend from one side to the other (until the filter).`  
  `The Cost filter should be to the right of the search bar, taking up about 1/5th of that row. It should drop down with the aforementioned options. It should default to blank when a user first opens the discover tab.`   
* **`Keyboard Behavior:`** `The keyboard should pop up when they click on the search bar. It should only start updating the activities after 150ms due to the debounce.`   
* **`The Empty State:`** `If there are no results due to location, there should be a message that says, “Sorry, we couldn’t find any activities in your location”. If it is due to search constraints, say, “We couldn’t find any results under those criteria”. And if it’s a wifi issue, use the same message and symbol from earlier projects, “Sorry, We couldn’t load anything right now”.`   
* **`The Loading State:`** `When activities are loading, you should have skeleton activities that show a greyed out version of what an activity card looks like, not a spinning loading animation. This would be preferable in all loading scenarios, as it subtly shows an app’s quality.`

**`4. Acceptance Criteria`**

- [ ] `The search bar and filter properly return results that are relevant to the new filter/search. E.g. typing “Climbing” returns results with “Rock Climbing” as tags.`   
- [ ] `The Algorithm gives scores to activities based on all four (three if not new) criteria`  
- [ ] `New activities get a 300 point boost for 72 hours`  
- [ ] `The cold start boost ends after the 72 hours`  
- [ ] `Higher scored activities get put at the top of the feed`  
- [ ] `Empty filter and search should return simply highly scored activities. The Cost filter should be null and the search bar empty when first loaded.`  
- [ ] `Skeleton loaders appear while loading activities`  
- [ ] `Empty states display the correct messages`
