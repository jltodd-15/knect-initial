# *5.3. Friend Actions — the App's Data Layer

**Status:** Written in the Project 5 edit pass, 2026-10-10. No open decisions. Not reviewed.
**Depends on:** 4.4 and 4.6 (`services/FriendsService.ts`, `services/friendsList.ts`), `*3.2` (the rules these writes rely on), `*5.2` (the callable Accept uses)
**Blocks:** 5.4 (the buttons), 7 (the profile's friend button), 15.2 (reads `blocked_users`)

> ⭐ **Starred:** it writes `blocked_users`, and blocking gates App Review (Guideline 1.2).

**1 - User Story**
As a User, I need sending, accepting, declining, starring, removing, blocking and unblocking to each change the database correctly on both sides, before any button exists for them.

**2 - Architecture & Technical Details**

> **The model, in three lines.** `Users/{uid}/Friends/{friendId}` holds one field, `status`: `"request_sent"`, `"pending"`, `"friend"` or `"close_friend"`. A relationship is two documents, one in each person's list. `Users/{uid}/Private_info/main.blocked_users` is the list of people this user has blocked; only its owner can read it.

- **Target collections:** `Users/{uid}/Friends` (read, write), `Users/{uid}/Private_info/main` (read own, write own `blocked_users`).
- **Data model changes:** None. **A `Friends` document carries `status` and nothing else:** no `friend_name`, no `friend_profile_picture_url` (Master Schema Q3; the rules reject any other field, `firestore.rules:113`).
- **The actions.** Each is one function in `services/FriendsService.ts`. Every multi-document action is one batched write, so it lands whole or not at all.

| Action | Writes | Allowed today by |
|---|---|---|
| Send a request (A → B) | Batch: create `Users/B/Friends/A` = `pending`; create `Users/A/Friends/B` = `request_sent` | `firestore.rules:112-118`; test `friends.test.ts:68` |
| Accept (B accepts A) | **No client write.** Calls `acceptFriendRequest({ requesterId })` | `*5.2` |
| Decline (B declines A) | Batch: delete both documents | `firestore.rules:133-134`; tests `friends.test.ts:93`, `:98` |
| Star / un-star | Update the user's **own** document to `close_friend` or back to `friend` | `firestore.rules:129-131`; test `friends.test.ts:82` |
| Remove a friend | Batch: delete both documents, whatever their status | as Decline |
| Block (A blocks B) | Batch: `arrayUnion(B)` on A's own `blocked_users`; delete both `Friends` documents (a delete of a missing document is fine) | `firestore.rules:81-86` and `:133-134` |
| Unblock | `arrayRemove(B)` on A's own `blocked_users`. **Nothing else** | `firestore.rules:81-86` |

- **Sending to someone who has blocked you is denied by the rules** (`firestore.rules:56-59`, `:117`; tests `friends.test.ts:224`, `:229`), and the whole batch fails. The client cannot tell why, and must not try to. This replaces the original ticket's unenforceable acceptance criterion.
- **Blocking is destructive, by ruling:** it removes the friendship on both sides, unblocking does not bring it back, and the other person can see you are gone from their friends list (Decision Log, "Blocking removes the friendship"). **Never describe blocking as enforced** (`CLAUDE.md`): this stops new friend requests, not messages.
- **Reading a relationship:** `getRelationship(otherUid)` returns one of `none`, `request_sent`, `pending`, `friend`, `close_friend`, `blocked_by_me`, from one read of the user's own `Friends` document and their own `blocked_users`. A one-time read, not a listener. This is what a button shows; it is **not** proof of friendship (`CLAUDE.md`: anything that grants access checks the other person's document).
- **Keep the logic pure.** Mapping a status to a relationship, and which next statuses are legal, are plain functions in `services/friendsList.ts`, tested first.
- **Calling the Function:** through `@react-native-firebase/functions`, a new dependency in the app. The region is `us-central1`, the one 5.1 deploys to, named once.
- **Errors:** every action rejects on failure and leaves it to the caller (5.4) to show it. No action retries by itself.

**3 - UI & Layout**
No UI. This is a data-layer ticket.

**4 - Security and Scope**
- **In scope:** the seven actions, the relationship read, their pure rules, their tests.
- **Out of scope:** every button and screen (5.4, 7); cancelling a request you sent (not in the original ticket; the "Sent" state is disabled, Appendix B.1); hiding a blocked person's messages (15.2, receive-side); what a blocked person's existing chats and events show (not decided; out of MVP per the Change List); notifications; any rules change.
- **Files allowlist:** `services/FriendsService.ts`, `services/friendsList.ts`, `types.ts` (a relationship type only), `package.json` and `package-lock.json` (one dependency), and their tests. `firestore-tests/friends.test.ts` only to add a test for the block batch and the unblock write if none exists.
- **New dependency:** `@react-native-firebase/functions`, same version line as the other `@react-native-firebase` packages (`package.json:17-20`). It has native parts: the app needs a fresh native build afterwards.
- **Security rules changes:** No changes needed. Every client write above is already allowed and already tested, as cited.

**5 - Acceptance Criteria** (all by `npm test`; the last one by `npm run test:rules`)
- [ ] Send: one batch, two creates, the paths and statuses in the table, and no other field.
- [ ] Accept calls `acceptFriendRequest` with the requester's uid and writes nothing itself.
- [ ] Decline and Remove: one batch, two deletes.
- [ ] Star and un-star touch only the user's own document.
- [ ] Block: one batch holding the `arrayUnion` and both deletes. Unblock: one `arrayRemove`, no `Friends` write.
- [ ] `getRelationship` returns each of the six values for the matching data, and `blocked_by_me` wins over any leftover status.
- [ ] A failed write rejects; nothing is swallowed.
- [ ] With nobody signed in, every action rejects without touching Firestore.
- [ ] `grep -rn "friend_name\|friend_profile_picture_url" services components` finds nothing.
- [ ] `npm run test:rules` passes, including the block batch and the unblock write.
