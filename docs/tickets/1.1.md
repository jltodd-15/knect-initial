# 1.1. Replace the Native Bridge with react-native-firebase

**Status:** Not started. Reviewed 2026-09-03.
**Depends on:** 0 (stack & conventions), 0.1 (repair the boot path)
**Blocks:** 1.2 — and through it, `*1.3`, 1.4, 2 and 3

---

**1 - Goals**

- The hand-written Kotlin Firebase bridge is deleted, and `@react-native-firebase/app`, `/auth` and `/analytics` are installed and initializing on Android.
- The app still builds and still boots with all four tabs rendering, exactly as 0.1 left it.
- **No auth behavior changes in this ticket.** Sign-in is still broken when this lands — it is broken in TypeScript instead of in Kotlin, and 1.2 is what fixes it.

This is a swap-the-foundation ticket. Nothing user-facing changes.

---

**2 - The Architecture & Technical Details**

> **The model, in three lines.** Firebase reaches the app through exactly one SDK — `@react-native-firebase` — on both platforms. There is no hand-written native bridge and no `NativeModules.FirebaseModule`. Firestore is not touched here at all; Project 2 is the first ticket that reads or writes a document, and it also owns the offline-persistence config module.

- **Target Database Collection:** None. This ticket touches no Firestore data.
- **Data model changes:** None.

**Why the bridge is deleted rather than fixed.** The SDK question was settled in favour of `react-native-firebase` (Decision Log, J1), and the consequence was written down at the time: the Kotlin bridge gets **deleted, not repaired**. Most of the audit's bug inventory disappears with the file, and none of it is worth a ticket. Specifically, all of the following stop existing rather than getting fixed:

- The inverted existence guard and the empty `SetOptions.mergeFields()` in `writeUserData` (`FirebaseModule.kt:120`, `:121`) — two independent reasons no user document has ever been written.
- `getActiveUser` with an empty body that neither resolves nor rejects (`FirebaseModule.kt:109–112`), so any JS `await` on it hangs forever.
- `authState` declared `lateinit` and never initialized or registered (`FirebaseModule.kt:32`) — the reason no session-persistence mechanism exists today.
- `authenticateUser`'s catch calling `promise.resolve(e.toString())` instead of rejecting (`FirebaseModule.kt:105`), so JS cannot tell success from failure by promise state.
- `user!!` NPE-ing on cold start when `currentUser` is null (`FirebaseModule.kt:102`).
- `auth.useEmulator("10.0.2.2", 8080)` pointing Auth traffic at Firestore's emulator port (`FirebaseModule.kt:50`), and `firebaseDB` being reassigned on the next line (`FirebaseModule.kt:53`) so Firestore talks to production while `debug` is `true`.
- `runBlocking` on the bridge thread for network I/O (`FirebaseModule.kt:116`, `:134`).
- `collection("users")` lowercase against the schema's `Users` (`FirebaseModule.kt:118`, `:135`). **This closes the casing question** — the file that writes lowercase is the file being deleted.
- `dbConnection: DBService` (`FirebaseModule.kt:30`), pointing at a class gutted to a five-line TODO (`DBService.kt:3–5`).

**Delete.**

- `android/app/src/main/java/com/knect/FirebaseModule.kt`
- `android/app/src/main/java/com/knect/FirebasePackage.kt`
- `android/app/src/main/java/com/knect/services/DBService.kt`
- The manual package registration — `add(FirebasePackage())` at `MainApplication.kt:19`. RNFirebase autolinks; nothing replaces this line.

**Install.** `@react-native-firebase/app`, `@react-native-firebase/auth` and `@react-native-firebase/analytics` as `dependencies` in `package.json`. **Not `@react-native-firebase/firestore`** — nothing in Project 1 touches Firestore, and Project 2 is the first ticket that does.

**Analytics stays.** Firebase Analytics is in for MVP. `android/app/build.gradle:119` already declares `firebase-analytics`; it keeps its place and gains the RNFirebase module above. Two consequences, neither of them this ticket's to resolve:

- `[DECISION: what actually gets logged?]` Installing the SDK is not the same as having an analytics plan. No ticket owns event naming, screen tracking, or user properties. **New unowned item** — surface it in the Running Order rather than letting Claude Code invent an event taxonomy on some later screen ticket.
- ⚠️ **`ios/AwesomeProject/PrivacyInfo.xcprivacy` will become inaccurate.** It currently declares `NSPrivacyCollectedDataTypes` as an empty array and `NSPrivacyTracking` as `false`. Analytics collects data, so the manifest has to be filled in before submission or the upload is rejected. That belongs to **0.2**, which owns the iOS manifest — noted here so it arrives with an owner rather than at App Review.

**Reconcile the Android build config.** Four things in there predate the SDK decision and now conflict with it. There should be **one source of version truth**, and after this ticket it is RNFirebase.

| Where | What's there now | Why it's wrong |
|---|---|---|
| `android/build.gradle:37` | `apply plugin: "com.google.gms.google-services"` at the **root** project | There is no `google-services.json` at the root. The plugin belongs on the app module, where it already is |
| `android/app/build.gradle:130` | The same plugin, applied correctly | Correct. Keep it |
| `android/app/build.gradle:117` | `implementation("com.google.gms:google-services:4.4.4")` | A Gradle *plugin* artifact declared as an app runtime dependency. The classpath entry at `android/build.gradle:32` is the one that matters |
| `android/app/build.gradle:118–121` | `firebase-bom` plus direct `firebase-analytics` / `-auth` / `-firestore` declarations | RNFirebase manages these. Two sources of version truth is how you get a build that works on one machine and not another. Analytics and Auth stay as capabilities; `firebase-firestore` goes — Project 2 brings it back through RNFirebase |

> **Correction to the reconciliation doc:** `Knect_Codebase_Reconciliation.md` §3 says the google-services plugin is applied to the root project "not `android/app`, where it would actually process `google-services.json`." That is half right — it is applied in **both** places (`android/build.gradle:37` **and** `android/app/build.gradle:130`). The app-level application is already correct; the root-level one is the one to remove.

`android/app/google-services.json` is already present and correct for this package — project `knect-db`, client `com.knect`. Leave it where it is; RNFirebase reads it from exactly that path. **`*1.3` will need it regenerated** — see that ticket.

**`kotlinx-coroutines-play-services` is moot.** The reconciliation flagged it as undeclared while `kotlinx.coroutines.tasks.await` was imported. The only file importing it (`FirebaseModule.kt:23`) is being deleted.

**What breaks in JavaScript, and what this ticket does about it.** `App.tsx:34` destructures `NativeModules.FirebaseModule`, and three call sites use it — `App.tsx:43`, `:49`, `:61`. Once the native module is gone those are references to `undefined`. **This ticket makes them stop crashing the app; it does not implement auth.** Leave the sign-in and sign-up paths inert and obviously unimplemented — 1.2 owns what they become. Do not write `signInWithEmailAndPassword` here. A half-migrated auth path reviewed alongside a native-module deletion is exactly the two-kinds-of-failure-at-once problem this split exists to avoid.

**4 - Security and Scope**

**In scope**

- Delete `FirebaseModule.kt`, `FirebasePackage.kt`, `DBService.kt`.
- Remove `add(FirebasePackage())` from `MainApplication.kt`.
- Add `@react-native-firebase/app`, `/auth` and `/analytics` to `package.json`.
- Reconcile the four Gradle items in the table above.
- Make `App.tsx`'s three `FirebaseModule` call sites inert without crashing.
- Fix the `.gitignore` patterns — see the security note below.

**Explicitly out of scope**

- **Any auth implementation.** No sign-in, no sign-up, no `onAuthStateChanged`, no error mapping. That is 1.2, in full.
- **Google and Apple sign-in.** In for MVP, owned by `*1.3` — including the `google-services.json` regeneration those providers require.
- **`@react-native-firebase/firestore` and offline persistence.** **Project 2 owns the Firestore config module**, including turning offline persistence on at the default cache size. Nothing here touches Firestore.
- **An analytics event taxonomy.** The SDK is installed; nothing is instrumented.
- **iOS.** There is no iOS Firebase integration and this ticket does not create one. `ios/GoogleService-Info.plist` does not exist, the Podfile target is `Knect` (`ios/Podfile:17`) while the Xcode project and `PRODUCT_NAME` are still `AwesomeProject`, and no Firebase pods are declared. **iOS setup is now ticket 0.2**, which owns all of it. Nothing under `ios/` is touched here.
- **`CreateProfilePage.tsx`** — unchanged in this ticket. 1.2 makes one narrow edit; 1.4 owns the screen.
- **The React Navigation migration.** `App.tsx`'s hand-rolled `AppTab` switch (`App.tsx:162–185`) stays exactly as it is.

**Security rules changes:** No changes needed. This ticket touches no Firestore data.

**Security notes:**

1. 🔴 **`.gitignore` will silently untrack every Firebase config file this project is about to create.** Lines 78–80 read `*firebase*`, `*firestore*`, `!*firebase*.kt*`. Verified with `git check-ignore`: RNFirebase's root `firebase.json`, and Project 3's `firestore.rules` and `firestore.indexes.json`, are **all three matched and would be silently excluded**. The negation on line 80 only rescues Kotlin files, which are the ones being deleted. Fix the patterns here; discovering it at Project 3 means discovering it as "why aren't my rules deploying."
2. **The public repo is deliberate.** It has to be cloneable so collaborators can reach it — private sharing was a problem without an enterprise plan. Two things worth separating, because they are not the same risk:
   - `android/app/google-services.json` is a **client** config, not a secret. It ships inside every APK and is designed to be readable. Public repo or not, the thing standing between it and abuse is the security rules — which is Project 3's job, and another reason that ticket matters more than its position suggests.
   - `.env.local`'s live `GEMINI_API_KEY` **is** a real secret, and it is a different problem. 0.1 deletes the file, which does not remove the value from history at commit `71a7c07`. **The key still has to be revoked by hand**, and a public repo makes that urgent rather than tidy.
   - One correction for the Decision Log's J6 entry: no `.gitignore` pattern matches `google-services.json`, so "committed despite `.gitignore` patterns that should have excluded it" isn't accurate. It was simply never ignored.

**Files allowlist — touch nothing else.**

```
android/build.gradle
android/app/build.gradle
android/app/src/main/java/com/knect/MainApplication.kt
android/app/src/main/java/com/knect/FirebaseModule.kt          (delete)
android/app/src/main/java/com/knect/FirebasePackage.kt         (delete)
android/app/src/main/java/com/knect/services/DBService.kt      (delete)
package.json
.gitignore
App.tsx        (lines 34, 43, 49, 61 only — the FirebaseModule references)
```

**Stop and ask** rather than improvising if: the Android build fails for a reason not in the table above; RNFirebase's autolinking requires a change to a file not on this list; or `App.tsx` looks like it needs real auth code to compile. That last one means the scope line between 1.1 and 1.2 is in the wrong place, and that is a decision, not an implementation detail.
