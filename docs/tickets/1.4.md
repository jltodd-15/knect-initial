# 1.4. Onboarding Sequence

**Status:** Not started. Reviewed 2026-09-03. **Password bracket resolved 2026-09-11; rule revised the same day to match the Firebase policy.**
**Depends on:** 1.2, `*1.3`, **and 2**. See the note on build order below.
**Blocks:** nothing directly. Project 13.2's tag affinity depends on interests existing, which this collects.

> **The number is a home, not a build position.** This was D7 — the onboarding ticket that had no home — and it was folded into Project 1 for lack of a better one. Its **build order is after Project 2**, because it hands a payload to a `Users` write that Project 2 owns. ✅ **Resolved 2026-09-07: it stays 1.4.** Renumbering it into `2.x` costs a cross-reference sweep for nothing, and doc order and build order are already two separate lists.

> **If `*1.3` is deferred, this ticket still gets built** — but build the sequence so it *accepts* a pre-filled identity (an email, and optionally a name) even while email/password is the only thing supplying one. The costly part of adding social sign-in later is not the wiring; it is a signup sequence that assumed everyone starts from a blank form.

---

**1 - Goals**

- Signing up is one sequence with one owner, instead of three tickets each describing a piece of it.
- The two-step create-account screen actually advances between steps.
- Interests are collected at signup, because the Discover algorithm is built on them and nothing else ever asks.
- Every user leaves onboarding with a profile picture, even if they never upload one.

**Why this exists.** Signup currently spans Projects 1, 2 and 6 — each specifying a fragment, none owning the flow. Interests are the clearest casualty: 13.2 scores them at +10 per interest and no ticket in the roadmap collects them.

---

**2 - The Architecture & Technical Details**

> **The model, in three lines.** Onboarding is a client-side sequence that collects a profile and hands it off; it owns no schema of its own. Firebase Auth creates the account (1.2, or `*1.3` for a social account), this ticket collects `name`, `interests` and a picture, and **Project 2 writes the `Users` document** — the field list lives there and only there. Nothing here writes to Firestore.

- **Target Database Collection:** None directly. The payload this collects is written by `*2.2`.
- **Data model changes:** None. Every field it gathers already exists on the `Users` document in the Master Schema.

**The sequence, and its two entry paths.**

| Entry | Comes from | Already known on arrival |
|---|---|---|
| Email + password | 1.2 | The email and password. Nothing else |
| Google or Apple | `*1.3` | Email, and usually a display name — Apple's is first-login-only, and a user may withhold it |

**Do not build this as an email/password flow with social bolted on.** The sequence has to skip what it already has and ask for what it doesn't, and Apple in particular can hand back no name at all, which is a state the screen must handle rather than a bug. `*1.3` lands before this ticket for exactly this reason — and if `*1.3` is deferred, the sequence is still built to take an identity it did not collect itself.

**Interests are a fixed list.** Free text was rejected because it fragments the vocabulary that 13.1 searches and 13.2 scores. The list, exactly:

```
Hiking · Art · Fashion · Style · Photography · Board games · Movies · TV Shows ·
Video Games · Baking · Cooking · Fast Food · Fine Dining · Running · Bodybuilding ·
Camping · Outdoors · Indoors · Music · Concerts · Dancing · Musicals & Theater ·
Travel · Family · Pets & Animals · Dating · Tech · Basketball · Baseball ·
Football · Hockey · Soccer · Sports · Reading · History
```

Thirty-five values, stored as `interests` (Array of Strings) on the `Users` document per the Master Schema.

⚠️ **The one thing that will quietly break this: these strings have to be the same vocabulary as `Activities.tags`.** 13.2 seeds `tag_affinity_scores` at +10 per interest, and those scores are matched against activity tags. If a user's interest is `"Board games"` and the seeded activities are tagged `"boardgames"` or `"board_games"`, the seeding scores nothing and the whole affinity system starts empty for every user. **Project 9 writes the tags, so Project 9's session has to adopt this list as its tag vocabulary** — or an explicit normalization has to exist and be owned somewhere. Flagged rather than solved here; it is a cross-ticket contract, not this screen's decision.

Two smaller notes on the list: it contains deliberate overlaps (`Sports` alongside five specific sports; `Outdoors`/`Indoors`; `Fashion`/`Style`), so a user picking `Sports` and `Basketball` contributes to both — fine for interests, worth knowing when 13.2's scoring is tuned. And this is a **third** vocabulary, alongside `Activities.tags` and the 15–20 `category` values that drive the Discover illustrations. Three different lists; don't conflate them.

**`CreateProfilePage.tsx:35` uppercases each interest on add.** With a fixed list that transform is either applied to the whole list consistently or dropped. Dropped is better — the stored value should be exactly what Project 9 tags with.

**A profile picture is mandatory, with a generated initials avatar as the floor.** Nobody leaves onboarding without one, and nobody is forced to upload.

**The initials avatar is rendered on the device from the user's name — no image is generated or uploaded.** No Storage write at signup and no upload dependency. The consequence, stated plainly: `profile_picture_url` stays `""` for a user who never uploads, so "mandatory" means *every screen always shows a picture*, not *the field is always populated*.

That is the pattern the app needs anyway. Removing the denormalized name and picture fields already means every screen showing a person needs a placeholder for a user who resolves to nothing — the "Deleted user" fallback. This is the same component doing the same job, so it is one piece of work, not two.

**Known bugs in this exact code path.** All in `CreateProfilePage.tsx`, and this ticket owns the file.

- **`:80` — `{ true && (` renders step one permanently.** A literal `true` where the step condition belongs.
- **`:31` — `var hideButton = false` is a plain variable, not state.** `handleNextStep` (`:40–45`) assigns to it, which does not re-render, so the NEXT button never hides. With the bug above, both steps render at once after NEXT.
- **The password rule had three different answers** — `:67` validated with a `{2,24}` regex, the message at `:112` said 12–24 characters, and Project 1's original acceptance quoted Firebase's 6-character minimum. ✅ **RULED 2026-09-11 — one rule: 8 to 24 characters, at least one capital letter, at least one number.** It applies in the regex at `:67` and in the copy at `:112`, and the copy is 1.2's mapped string: *"Password must be at least 8 characters and include a capital letter and a number."*
  - ⚠️ **This same rule is configured server-side in Firebase Console → Authentication → Settings → Password policy.** Two enforcement points, one rule. **If they ever disagree, the Console is authoritative and the regex is the bug** — a tightened Console with a stale regex means the app accepts what Firebase then rejects, and the user sees a failure the form said wouldn't happen. 1.2 maps Firebase's own policy rejection to the same copy as a safety net.
  - ⚠️ **Enforced at signup only.** Do not length- or shape-check a password before a **sign-in** call. An account created before the policy existed may not satisfy it, and telling an existing user their working password is invalid is worse than not checking. 1.2 carries the same note from the other side.
- **`:51–63` — `handleImageUpload` cycles four hardcoded Unsplash URLs**, with a comment admitting it is a mock. Real upload is **Project 6**. Replace the mock with the initials avatar; do not build an image picker.

**When the profile write fails: retry, then sign the user out.** Auth succeeds and the profile write fails, leaving an Auth user with no `Users` document. **2.3 owns the retry, the two-attempt limit and the sign-out;** this ticket owns what happens next.

⚠️ **Signing out does not undo the Auth account, and that is the part that bites.** The user's email is now taken, so signing up again fails with `email-already-in-use`, and signing *in* lands an authenticated user with no profile document in an app that has no handling for that state. **So the app needs one more rule: on sign-in, an authenticated user with no `Users` document is routed into this sequence rather than into the app.** That single rule turns a stuck account into a resumed signup, and it is what makes "sign out" a safe answer rather than a trap. **2.3 owns the detection; this ticket owns the routing and the screen**, and replaces 2.3's one-line interim branch when it lands.

**3 - The UI and Layout Requirements**

- **Step one — credentials.** As it renders today (`:81–132`), minus the two bugs. Skipped entirely on the social path.
- **Step two — profile.** Name, interests, picture. Advancing to it must actually hide step one.
- **Back.** There is no way back from step two today. A user who typo'd their email has no route to fix it.
- **Interests picker.** Thirty-five fixed options, multi-select. Zero selected is a valid finishing state.
- **Avatar.** The initials avatar renders immediately from the name as typed, so the user sees their picture before they've done anything. An upload affordance may be shown, but it routes nowhere until Project 6.
- **Loading.** Account creation and the profile write are both network calls with no indicator on this screen.
- **Error.** Per-field validation exists for email and password (`:96–98`, `:111–113`); step two has none. An `email-already-in-use` rejection arrives on this screen and has nowhere to render — 1.2's copy for it is "Email already in use".
- **Password requirements are shown before the user fails them.** The rule is rendered near the field as guidance, not only as an error after a rejected submit. With three conditions to satisfy, discovering them one rejection at a time is the version people abandon.
- **Profile-write failure.** The retry, and then the signed-out state with an explanation of what happened and what to do.
- **Success.** The user lands in the app. **Land wherever `App.tsx:18` already defaults** — do not build routing.
- **Partial-identity, social path.** Name present, name absent, and name-present-but-user-wants-to-change-it are three different renderings of step two.
- **Resumed signup.** An authenticated user with no profile document re-enters here, past step one.

**4 - Security and Scope**

**In scope**

- The step machine in `CreateProfilePage.tsx` — the two bugs at `:31` and `:80`.
- The full sequence for both entry paths, plus a back route and the resumed-signup entry.
- The fixed interests picker.
- The initials avatar component, replacing the Unsplash mock.
- **The password rule — 8–24 characters, one capital, one number — applied identically in the regex at `:67` and the copy at `:112`, and shown as guidance before submit.**
- Routing a missing-profile user back into this sequence.

**Explicitly out of scope**

- **Writing the `Users` document, and detecting a missing one.** `*2.2` writes, 2.3 detects. This ticket collects, hands off, and renders the outcome.
- **Creating the auth account.** 1.2 for email/password, `*1.3` for social.
- **The retry and sign-out mechanism itself.** 2.3.
- **Configuring the Firebase password policy.** A Console action, not build scope — see the pre-flight checklist in the Implementation Start Guide.
- **Profile picture upload and Firebase Storage.** Project 6 — and Storage is not in `build.gradle` at all today.
- **The own-profile edit screen.** D6. Editing interests *after* signup is that ticket's; collecting them at signup is this one's.
- **The `Activities` tag vocabulary.** Project 9 — see the flag in section 2.
- **React Navigation.** The sequence is rendered by `App.tsx`'s existing conditional (`:84–93`).
- **Any Firestore read or write.**

**Security rules changes:** No changes needed. This ticket touches no Firestore data.

**Security note:** step one holds a password in component state through step two. Keep it there and nowhere else — not in AsyncStorage, not in the Keychain (1.2 deletes `keyChain` outright), and not in the payload handed to the profile write. Credentials and profile fields travel separately; that separation is why 1.2 writes no document.

**Files allowlist — touch nothing else.**

```
components/CreateProfilePage.tsx
App.tsx        — the create-profile branch (:84–93) and handleProfileComplete (:60–64) only
```

Plus one new component for the initials avatar, wherever Project 0's conventions say shared components live — **and add it to Appendix B**, since the "Deleted user" placeholder is the same component doing the same job.

**Stop and ask** rather than improvising if: the handoff needs a shape `*2.2` hasn't defined; or the sequence appears to need a navigation library.

**5 - Acceptance Criteria**

Verified by one method: **a real Android device or emulator, signing up from scratch.**

- Tapping NEXT on step one hides step one and shows step two. Only one step is on screen at a time.
- A user can go back from step two to step one, change the email, and the change sticks.
- **`Passw0rd` (8 chars, capital, number) is accepted. `Passw0r` (7) is rejected. `password1` (no capital) is rejected. `Password` (no number) is rejected. A 25-character password is rejected.**
- **The regex at `:67` and the message at `:112` state the same rule**, and that rule is the same one configured in the Firebase Console — verified by signing up with a password the client accepts and confirming Firebase does not reject it.
- The password requirements are visible on the form before a failed submit.
- The interests picker offers exactly the 35 listed values and no free-text entry.
- Selected interests are stored verbatim — no uppercasing, no reformatting.
- A user with no uploaded picture sees an initials avatar generated from their name, and it updates as the name is typed.
- Completing the sequence produces one payload containing name, interests and picture, complete before the profile write fires.
- Signing up with an email that already has an account shows "Email already in use" on this screen rather than failing silently.
- A social sign-up arriving with a display name skips asking for it; one arriving without a name asks for it.
- After a failed profile write and sign-out, signing in with the same credentials returns the user to step two rather than into a broken app.
- The sequence shows a loading indicator during account creation and during the profile write.
- Finishing lands the user on the tab tree.
- No password is written to AsyncStorage or the Keychain — `grep -rn "keyChain\|setItem" components/CreateProfilePage.tsx` returns nothing.
- `npm run lint` passes.
- `npm test` passes.
