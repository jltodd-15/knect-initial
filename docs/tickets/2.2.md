# `*2.2`. The Users Document — Schema, Types & the Creation Write

**Status:** Not started. Reviewed 2026-09-08.
**Depends on:** 1.2, 2.1
**Blocks:** 2.3, 1.4, 4, 5, 6, 7, 13.2

⭐ **Starred.** It defines the canonical shape of the document every other ticket in the app reads. A wrong field name here is invisible in the UI and expensive to unwind once other tickets are built on it.

---

**1 - User Story**

As a system developer, I need a standardized profile document created for every new user at the moment they sign up, so that search, the friend graph and the Discover algorithm all have the fields they expect instead of discovering them missing three tickets later.

---

**2 - The Architecture & Technical Details**

> **The model, in three lines.** One `Users/{uid}` document whose ID **is** the Firebase Auth UID, plus one `Users/{uid}/Private_info/main` document for anything the rest of the app shouldn't see. Both are written together in a single batch immediately after `createUserWithEmailAndPassword` resolves — both land or neither does. Everything readable by other users lives on the root document; everything owner-only lives in `Private_info`.

- **Target Database Collections:** `Users`, and the `Private_info` subcollection.
- **Data model changes:** None. Every field below already exists in the Master Schema; this ticket is the first code that writes any of them.

**This ticket is the single source for the creation payload.** Decision Log R12 moved it here from Project 1, which owns Auth and nothing else. Project 1's field list was deleted rather than copied, so if this document and an older ticket disagree, this one is right.

### The Users document

Document ID **must** equal the Firebase Auth UID. Not a generated ID, not the email.

| Field | Type | Value at creation |
|---|---|---|
| `name` | String | From the signup payload |
| `name_lowercase` | String | `name.toLowerCase()`, computed at write time |
| `profile_info` | String | From the payload's `role` — see below |
| `profile_picture_url` | String | `""` — see below |
| `interests` | Array of Strings | From the payload, written verbatim |

**No `email` on this document.** Every authenticated user can read `Users/{uid}`, so `email` lives in `Private_info` and only there (R11).

**`name_lowercase` is a stored field, and it has to be.** The value is computed with `.toLowerCase()` at write time, and the field itself is written to the document and stays there. Both halves matter.

It cannot be a query-time transform. Project 4's search is a Firestore range query evaluated **server-side against stored data** — Firestore has no `LOWER()`, no case-insensitive mode, and orders by raw bytes, so `"John Smith"` sorts before `"joh"` (`J` is `0x4A`, `j` is `0x6A`). Without the stored field the only options left are downloading every user to filter on the device, or paying for a search service. **Do not "optimize" it away**, and do not let a later ticket derive it at read time.

**`role` maps to `profile_info`.** `CreateProfilePage.tsx:206` sends `{ name, role, interests, avatar }`, and there is no `role` field anywhere in the Master Schema. `role` is the bio line the prototype renders on the profile header (`ProfilePage.tsx:23`, `'DIGITAL NOMAD • SAN FRANCISCO'`), so it maps to `profile_info`. **Do not add a `role` field.** Relabelling that input on the signup screen is 1.4's, not this ticket's.

**`profile_picture_url` is written as `""`.** Round 10 §11 made a profile picture mandatory with an initials avatar as the floor — **rendered on-device from the name, with nothing generated or uploaded** — so signup produces no URL to store. The empty string is the honest record of that. Project 6 owns the first real upload.

**Three fields are deliberately absent:** `current_status`, `status_visibility`, `status_expires_at`. **D5 owns the status feature and owns the first write**, and `status_visibility` has no defined value set anywhere in the schema — so there is no correct value to initialize it to. They are left off the document rather than written empty. Anything reading them must handle undefined.

### The Private_info document

**Document ID is the literal string `main`** — `Users/{uid}/Private_info/main` (R13). Six tickets touch this subcollection; without a fixed ID each one invents its own convention.

| Field | Type | Value at creation |
|---|---|---|
| `email` | String | The address used to create the Auth account |
| `blocked_users` | Array of Strings | `[]` |
| `fcm_tokens` | Array of Strings | `[]` |

**Everything else in `Private_info` is deliberately absent**, each because another ticket owns both the value and the vocabulary: `location` and `geohash` (location capture, which has no ticket yet — see the flag below), `tag_affinity_scores` and `tag_scores_last_decayed` (13.2), `liked_activity_ids` (Project 11), `external_calendar_tokens` (Project 19, deferred).

The two empty arrays are written rather than omitted because both have a decided type and an unambiguous empty value, and an absent array is a different thing from an empty one to any rule that reads it.

### Subcollections that are NOT created

`Free_Busy`, `Friends`, `Activity_History` and `Liked_Activities` are **not** initialized at signup — they cost writes and Firestore has no empty subcollections anyway. The original ticket's rule stands. `Private_info` is the one exception, because it holds `email`, which has to exist from the first moment.

### The write

A single **batch**, client-side, immediately after `createUserWithEmailAndPassword` resolves in 1.2's sign-up flow. Two documents, one commit. A batch is all-or-nothing, which is the whole point: a `Users` document with no `Private_info` is a user with no email on record and no way to be blocked.

Build it as a repository module rather than inline in `App.tsx`. This ticket's only edit to `App.tsx` is that `handleProfileComplete` calls the repository after the auth call resolves — **the loading states, the failure handling and the routing gate around that call all belong to 2.3.**

### Types

Add schema-shaped types for both documents. **Do not modify `types.ts:9–18`.** That `User` interface is prototype scaffolding — `id`, `avatar`, `bio`, `location: string`, `isAvailable` — camelCase and disagreeing with the schema on nearly every field. Its only consumer is `CURRENT_USER` at `constants.ts:3`, and it dies when the screens are repointed at Firestore, which is not this ticket. Add alongside it; delete nothing.

### Known bugs and divergences in this exact path

- **`FirebaseModule.kt:39–45` — `UserSchema` disagrees with the Master Schema on every field.** `userId`, `displayName`, `email`, `profilePictureUrl`, `interests` — camelCase, and it puts `email` on the root document. **Do not port it.** 1.1 deletes the file.
- **`FirebaseModule.kt:115–131` — `writeUserData` could never write a new user, for two independent reasons.** The existence guard is inverted (`if (userDoc.get().await().get("userId") != null)` — a new user's document doesn't exist, so it returns false and writes nothing), and `SetOptions.mergeFields()` with no arguments merges zero fields even when reached. It also writes to `collection("users")` (`:118`), lowercase, which is a different collection from `Users`. All of it dies with 1.1. **The app has never successfully written a field to Firestore; this ticket is the first one that does.**
- **`CreateProfilePage.tsx:35` uppercases every interest** before it reaches the payload. That transform is 1.4's to fix along with the rest of that screen. **This ticket writes `interests` exactly as handed to it and normalizes nothing** — see the vocabulary flag below.

### ⚠️ Flag — the interests vocabulary is still unowned

1.4 fixes a list of 35 interest strings. 13.2 seeds `tag_affinity_scores` at +10 per interest and matches them against `Activities.tags`, which Project 9 writes. `"Board games"` against a seeded `"boardgames"` scores nothing, and **nothing looks broken** — every user's affinity simply starts empty. This ticket is the code that stores the strings, so it is worth naming here, but the contract belongs to Project 9's session or to a normalization step that has no home yet.

**4 - Security and Scope**

**In scope**

- The repository module: the batched two-document creation write.
- Schema-shaped types for the `Users` document and the `Private_info` document.
- One call from `handleProfileComplete` into the repository, after the auth call resolves.

**Explicitly out of scope**

- **Loading, failure and success states, and routing.** 2.3.
- **Detecting an authenticated user with no `Users` document.** 2.3 owns detection; 1.4 owns the routing into onboarding.
- **The onboarding sequence, the interests picker, the step machine and the password rule.** 1.4 owns that screen. This ticket does not edit `CreateProfilePage.tsx` at all — the payload it needs is already at `:206`.
- **Auth calls.** 1.2 owns all five flows. This ticket writes no credentials and calls no auth method.
- **The user's `location` and `geohash`.** Capture has no ticket — see the flag below.
- **Profile picture upload and Firebase Storage.** Project 6. Storage is not in `android/app/build.gradle` at all today.
- **The status feature.** D5.
- **Reading the document back anywhere.** Nothing renders from Firestore yet.
- **`types.ts:9–18` and `constants.ts`.** Leave the prototype mocks alone.
- **Security rules.** Project 3.

**Security rules changes:** None authored here — `*3.1` moves the rules into the repo and writes them, right after this ticket.

**Both writes are already permitted by the published rules**, which are dated 5/11/26 and live in the Firebase Console (mirrored in the "Firebase Master Schemas" Doc under *Current Firebase rules*):

```
match /Users/{userId} {
  allow read: if request.auth != null;
  allow create, update, delete: if request.auth != null && request.auth.uid == userId;

  match /Private_info/{privateId} {
    allow read, write: if request.auth != null && request.auth.uid == userId;
  }
}
```

The `Users` create clause is satisfied because the document ID **is** the Auth UID, and `Private_info` is owner-only read/write at any document ID, so `main` passes. Firestore evaluates each write in a batch against the rules independently, so the two-document batch is permitted as a whole. **No rule change is needed for this ticket to work.**

Two things still follow, and both should be stated rather than assumed:

1. **Passing the criteria below is evidence the client is correct, not that the rules are right.** The rule above lets a user write *any* shape into their own document — there is no field validation, no type checking, and nothing stopping a client from adding fields this ticket doesn't list. `*3.1` and `*3.2` own tightening that.
2. **`email` must land in `Private_info` and nowhere else.** The whole reason `Private_info` exists is that `Users/{uid}` is readable by every authenticated user — the rule above says `allow read: if request.auth != null`, with no relationship check at all.

**Security note.** The old `createUserData(email, password)` call at `App.tsx:61` hit a Kotlin signature of `createUserData(displayName, email, promise)` (`FirebaseModule.kt:74`), so position two — the `email` field — received the **password**. Had that write ever succeeded, a plaintext password would have been written into a Firestore field every authenticated user can read. It dies with 1.1. It is recorded here because it is the reason credentials and profile fields never travel through the same call: **the payload this ticket writes must never carry a password**, and the repository must not accept one.

**Files allowlist — touch nothing else.**

```
types.ts                        — ADD the two new types. Do not modify the `User` interface at :9–18
<services dir>/<new module>     — the Users repository
App.tsx                         — `handleProfileComplete` ONLY, and only the call into the repository
```

**Stop and ask** rather than improvising if: a field you need isn't in the Master Schema; the write appears to need more than two documents; `handleProfileComplete` starts growing loading or error handling (that is 2.3); or the payload from `CreateProfilePage` seems to be missing something.

**5 - Acceptance Criteria**

Verified by one method: **one Android device or emulator, plus the Firebase Console, signing up from scratch.**

- Signing up creates exactly one document in `Users`, and its **document ID is identical to the new Auth UID** shown in the Firebase Auth console.
- That document contains exactly `name`, `name_lowercase`, `profile_info`, `profile_picture_url` and `interests` — and nothing else.
- `name_lowercase` is the entered name in all lowercase.
- `profile_info` holds the value typed into the signup screen's `role` input.
- `profile_picture_url` is an empty string.
- `interests` is an array, not a string.
- **`current_status`, `status_visibility` and `status_expires_at` are absent from the document**, not present-and-empty.
- **`email` does not appear on the `Users` document.**
- `Users/{uid}/Private_info/main` exists, at that exact document ID, containing `email`, `blocked_users` and `fcm_tokens` — with the two arrays empty.
- `email` matches the address used to register.
- No `Free_Busy`, `Friends`, `Activity_History` or `Liked_Activities` subcollection exists under the new user.
- With the device offline at submit, **no partial document appears in the Console**; when connectivity returns, both documents appear together.
- `grep -rn "collection('users')\|collection(\"users\")" .` returns nothing outside `.git/` — the collection is `Users`.
- `npm run lint` passes.
- `npm test` passes.
