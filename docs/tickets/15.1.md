# 15.1. Group Chat Infrastructure

### `Group Chat Infrastructure - Chat Creation & Participant Management`

**`1. User Story`**

* `As a User, I want to have real time chats with my friends to better use the tools in Knect, share its information, and be able to easily coordinate, all within the app.`

**`2. The Architecture & Technical Details`**

* **`Target Database Collection:`** `Chats (reads Users / Users/{uid} for live profile picture lookups on 1-on-1 chats)`  
* **`Data model changes (to fit master schema doc):`**  
  * `Rename title → chat_name, lastMessage → recent_message, lastMessageTimestamp → recent_message_timestamp. Caution: title is also a field on CalendarEvent in types.ts — a global find/replace will catch both. Manual pass through types.ts, ChatService.ts, SocialDashboard.tsx, and EventPlanner.tsx, not a mechanical rename.`  
  * `Drop admins (unused everywhere except being set at creation; not in schema; every participant has equal rename/leave ability for MVP).`  
  * `Drop image (hardcoded placeholder, never actually written to; not in schema). 1-on-1 avatars resolve at render time from the other participant's live profile_picture_url.`  
  * `Drop isGroup. It's a rendering-only switch (group avatar row + sender labels vs. single avatar, no sender labels) — derive from participants.length at render time instead of storing it.`  
  * `Add chat_origin (String: "direct" or "group"). "direct" = created by friend-accept; "group" = created by event creation. Included in every find-or-create query alongside participant_hash.`  
* **`Chat creation triggers:`**  
  * `Automatically when an event is created (any participant count) — assumes Project 16 hands off a participant list at event-creation time.`  
  * `Automatically when a friend request is accepted (ties into Project 5's Action B — that batch write will need to also create-or-check-for the 1-on-1 chat; flagging as an addition needed to Project 5, not just this ticket).`  
  * `Manual creation (profile "message" button, floating "+" button) — explicitly out of scope, see Section 4.`  
* **`Find-or-create logic:`** `Handled by a callable Cloud Function, not client-side. All three entry points (event creation, friend-accept, recompute on leave) call the same function, so the recipe exists in one file and cannot drift between call sites. The function computes participant_hash as the participant UIDs sorted in ascending byte order, joined with a single underscore — e.g. AbC123_Xy9Zqq_m4Nop7. Firebase Auth UIDs are ASCII alphanumeric, so the sort is unambiguous and _ cannot appear inside a UID. Nothing is cryptographically hashed despite the field name; the value is the plain joined string. The function queries on participant_hash and chat_origin, returns the existing chat if found, creates one if not. Clients never compute this value. Replaces the in-memory array scan in ChatService.findConversation, which only works locally.`  
* **`Renaming:`** `Any participant can update chat_name at any time — no admin gate.`  
* **`Leaving a chat:`** `Self-service only — a participant removes their own UID from participants. No participant can remove another. participant_hash must be recomputed on leave so a future find-or-create for the original full group doesn't match the now-smaller chat. A group chat that shrinks to two participants stays a "group" chat — chat_origin never changes after creation. The pair may see both threads; the group thread is distinguishable by its event name.`  
* **`Blocking:`** `No effect on existing chat membership or history — restricts new message sends only. Not implemented in this ticket, see Section 4.`  
* **`Known bug pattern to avoid:`** `ChatService.ts/StatusService.ts currently call localStorage.getItem/setItem without await. Treat every Firestore call in this rewrite as async by default.`

**`3 - The UI and Layout Requirements`**

* **`Loading state:`** `Greyed-out skeleton pattern (matching the Discover tab's existing skeleton), applied here to the conversation list — placeholder blocks in the shape of avatar circle + two text lines. (Note: this is actually an app-wide standard starting now)`  
* **`Empty state:`** `"No conversations yet." with a "Find a friend" button, Knect green, routing to the Search tab (Project 4).`  
* **`Error state:`** `Same wifi-lost visual pattern used elsewhere (circle with "!"), text reads "Connection lost."`  
* **`Success state (mostly already built, reusable):`**  
  * `Conversation list: Instagram-style overlapping profile picture bubbles for group chats (renderGroupAvatar, already implemented); single avatar for 1-on-1s, now resolved live.`  
  * `Chat name as headline — other person's name (1-on-1) or event name/custom rename (group) — white/black depending on dark mode (already built). If no Event name, default to a list of Usernames.`  
  * `Subtitle below the name, gray, minimal: most recent message. Group chats prefix with sender name — Jordan: sounds good (new requirement; current code shows raw message text with no prefix).`  
* **`Manual chat creation UI:`** `explicitly deferred, not part of this ticket.`

**`4 - Security and Scope`**

* **`In scope:`** `Chat creation (event + friend-accept triggers), find-or-create via participant_hash, rename (any participant), leave chat (self-only, with hash recompute), field renames/removals per Section 2.`  
* **`Out of scope:`** `Manual "message this person" entry point, floating "+" button, real-time message sync/Messages subcollection/listeners (Project 15.2), enforcement of the blocked-users-can't-message rule.`  
* **`Security rules changes — required before code is written:`**  
  * `Chats create: keep existing rule (creator's UID must be in participants).`  
  * `Chats update: current rule (request.auth.uid in resource.data.participants) lets any participant modify any field, including removing someone else from participants — inconsistent with self-only leave. Needs tightening (e.g. diff().affectedKeys() limiting participant-array removals to the requester's own UID); full rewrite deferred to the security-rules overhaul project per your direction — documenting the requirement here so it isn't lost.`  
  * `Blocked-users-can't-message: requirement only, no rule written here. Belongs in Messages rules (15.2) and/or the security-rules overhaul.`

**`5 - Acceptance Criteria`**

- [ ] `Creating an event with a group of friends creates a Chats doc if no chat with that exact participant set exists yet.`  
- [ ] `Creating a second event with the same group reuses the existing chat.`  
- [ ] `Accepting a friend request creates (or finds) a 1-on-1 chat.`  
- [ ] `Any participant can rename chat_name.`  
- [ ] `A participant can leave; their UID is removed from participants and participant_hash is recomputed.`  
- [ ] `No participant can remove another participant.`  
- [ ] `Blocking a user does not remove/hide any existing shared chat.`  
- [ ] `1-on-1 chat avatars reflect the other participant's current profile picture.`  
- [ ] `Group chat subtitles show the message.`  
- [ ] `admins, image, and isGroup are absent from newly created Chats documents.`  
- [ ] `participant_hash is computed only by the Cloud Function; no client-side computation exists in the codebase.`  
- [ ] `A 3-person group chat reduced to 2 participants does not collide with, or get returned in place of, those two users' existing 1-on-1 chat.`
