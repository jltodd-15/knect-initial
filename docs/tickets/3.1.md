**1 - Goals**

- The security rules live in the repo as `firestore.rules`, deployed by CLI, instead of being edited by hand in a Console where nothing is version-controlled.
- There is a way to run a rule against a fake request and get a pass/fail back **that a machine checks and re-checks** — the Firestore emulator plus a rules test file.
- **No rule policy changes in this ticket.** The rules file is a transcription of whatever is published today, so the first deploy is a no-op. `*3.2` and `*3.3` are where the rules actually change.

This is a plumbing ticket. Nothing about the app's behavior changes, and that is the point — a deploy pipeline you can only test by changing something is a pipeline you find out about during an outage.

---

**2 - The Architecture & Technical Details**

> **The model, in three lines.** `firestore.rules` in the repo root is the source of truth; `firebase deploy --only firestore:rules` is the only thing that moves it to Firebase. There is no automatic sync in either direction, so the Console is a viewer from here on and an edit made there will be silently overwritten by the next deploy. Rules are tested against a local emulator, never against `knect-db`.

- **Target Database Collection:** None. This ticket reads and writes no application data.
- **Data model changes:** None.

**The four files that connect the repo to Firebase.**

| File | What it does |
|---|---|
| `firebase.json` | Points `firestore.rules` and `firestore.indexes.json` at Firebase, and declares the emulator ports |
| `.firebaserc` | Pins the deploy target to the `knect-db` project. Without it, `firebase deploy` on a fresh clone has no idea where to go |
| `firestore.rules` | The rules themselves |
| `firestore.indexes.json` | Composite indexes. **Created empty here** — per restructure plan §8, each ticket adds the index its own query needs |

**`firestore.rules` starts as a transcription, not a rewrite.** Copy what is published today, character for character, into the file. Then deploy it. The deploy has to be a **no-op** — the Console shows the same rules afterward and nothing in the app changes behavior. That is the proof the pipeline works, and it is the only chance to get that proof without also risking a behavior change.

> If what is published today turns out to be open test-mode rules rather than the 5/11/26 set, transcribe the open rules anyway and say so in the commit message. Leaving them live is acceptable *only* while there is no real user data in `knect-db` — and `*2.2` is the first ticket that writes any. `*3.2` is what closes that window.

**The test harness, and one thing not to do with it.**

Rules tests use **`@firebase/rules-unit-testing`**, which talks to the emulator through the **`firebase` web JS SDK** — not `@react-native-firebase`. Both go in `devDependencies` and **neither is ever imported by application code.** Rules are SDK-agnostic, so testing them through the web SDK tests the real thing.

> ⚠️ **Do not wire the web `firebase` package into the app, and do not "reconcile" it with `@react-native-firebase`.** They are two unrelated things that share a name. Anything under `firestore-tests/` is the only place the web SDK may appear. This is a stop-and-ask, not a judgment call.

**Rules tests do not join `npm test`.** `jest.config.js:2` is `preset: 'react-native'`, which is wrong for a Node test that talks to an emulator. A second config — `jest.rules.config.js`, `testEnvironment: 'node'`, matching only `firestore-tests/` — keeps them apart. **This matters beyond tidiness:** almost every ticket in the roadmap has `npm test` passes as an acceptance criterion, and folding rules tests into that script would make every one of those tickets require a JDK and a running emulator.

Two scripts in `package.json`:

```json
"test:rules": "firebase emulators:exec --only firestore \"jest --config jest.rules.config.js\"",
"rules:deploy": "firebase deploy --only firestore:rules"
```

`emulators:exec` starts the emulator, runs the tests, and shuts it down — so there is no long-running process to remember to kill.

**The one test this ticket writes.** A single file proving the harness works end to end, against the catch-all deny that already exists at the bottom of the published rules:

- An authenticated user reading `/SomeCollectionThatDoesNotExist/doc` is **denied**.
- An authenticated user reading their own `/Users/{uid}` is **allowed**.

Two cases, one allow and one deny, so a harness that silently passes everything is caught immediately. **`*3.2` and `*3.3` write the real suite.**

**Known bugs to avoid:** none in this path — nothing in the repo touches Firestore today. Verified at `8493a36`: there is no `firestore.rules`, no `firebase.json`, no `functions/`, and not one occurrence of `firestore` in any `.ts`, `.tsx` or `.js` file.

**In scope**

- Add `firebase-tools` and initialize the CLI in the repo (`firebase.json`, `.firebaserc` targeting `knect-db`).
- Create `firestore.rules` as an exact transcription of the currently published rules.
- Create `firestore.indexes.json`, empty.

- Add the `test:rules` and `rules:deploy` scripts.
- Write the two-case harness test.
- Run one deploy and confirm it changed nothing.

**Explicitly out of scope**

- **Every rule policy change.** The `Calendars` → `Events` rename, the `Activities` rewrite, the missing `Liked_Activities` block, field allowlists — all of it belongs to `*3.2` and `*3.3`. **If this ticket's diff changes what any rule permits, it is wrong.**
- **Storage rules.** A separate file with separate syntax; Project 6 / D9 owns it.
- **Composite indexes.** The file is created empty on purpose.
- **Cloud Functions.** No `functions/` directory, no emulator beyond Firestore. D2 owns Functions setup.
- **The Auth emulator.** `authenticatedContext()` fakes a UID without one.
- **Any application code.** Nothing under `components/`, `services/`, `utils/`, `App.tsx` or `android/` is touched.

**Security rules changes:** **None.** The rules file is created and deployed, and what it permits is byte-identical to what is already live. This is the only ticket in Project 3 where that line reads "none."

**5 - Acceptance Criteria**

Verified by one method: **`npm run test:rules` on the Mac, plus reading one deploy's output.**

- `java -version` reports 11 or higher.
- `git check-ignore -v firebase.json .firebaserc firestore.rules firestore.indexes.json` reports **no match for any of the four**.
- `.firebaserc` names the project `knect-db`.
- `firestore.rules` is character-identical to the rules shown in the Firebase Console before the deploy.
- `npm run test:rules` starts the emulator, runs two tests, passes both, and exits cleanly with no emulator process left running.
- The deny case genuinely fails when it should: temporarily flip `allow read, write: if false;` to `if true;` in the catch-all, re-run, and the deny test **fails**. Revert it.
- `npm run rules:deploy` succeeds, and the Console afterward shows the same rules it showed before.
- `npm test` still passes and does **not** start an emulator.
- `grep -rn "@firebase/rules-unit-testing\|from 'firebase/" --include=*.ts --include=*.tsx . | grep -v firestore-tests` returns nothing.
- `firestore.indexes.json` contains an empty index array.
- `npm run lint` passes.
